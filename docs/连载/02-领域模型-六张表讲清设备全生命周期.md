# 领域模型：六张表讲清设备全生命周期

## 一、场景：一台注塑机的一生

第 1 章那台停了三天的 EQ-INJ-001，后来我把它的全部档案翻了出来，按时间排了一遍。这一排，整个系统的六张表就浮出来了。

2022 年 6 月 20 日，这台 HTF160 注塑机采购到厂，价格 38 万，保修到 2025 年 6 月 19 日，责任人是二车间的设备员，工号 1002。设备科在台账上给它建了一条记录：编号 EQ-INJ-001、分类"注塑"、位置"二车间"、状态"运行"。这是**第一条记录，也是后面所有记录的锚点**。

2022 年 7 月，设备科给它排了两条保养计划：月度保养，周期 1 个月，提前 3 天出单，内容是"液压油位/油温检查、导轨润滑、模温机滤网清洗"；季度保养，周期 3 个月，提前 7 天出单，内容是"液压泵压力测试、锁模机构间隙检查、电气柜除尘"。每条计划都带三个关键字段：周期类型、周期数值、提前天数。

之后每个月，系统会在到期前 3 天生成一张保养工单：工单号 `MO-20261110-1`，来源计划 ID、设备 ID、计划保养日期、状态"待执行"。李师傅或他的徒弟领单、开工、填结果、完工。这是**保养工单**。

2026 年 11 月 8 日，液压系统压力不足，操作工张三报修，生成一张维修工单：工单号 `RO-20261108-001`，故障描述"液压系统压力不足，合模无力"，优先级"高"，状态"待派工"。调度派给李师傅（工号 1002），状态变"已派工"，记派工时间；李师傅到场开工，状态变"维修中"，记开始时间；换完密封件完工，状态变"待验收"，记完成时间和维修记录；设备科验收通过，状态变"已完成"，记验收记录。这是**维修工单**。

换件的时候，李师傅去库房领了 1 包液压密封件包。库管老周在系统里做出库：备件 ID 2、数量 1、关联工单号 `RO-20261108-001`、操作人"李四"。系统校验库存 3 包够扣，扣成 2 包，同时写一条出库流水。这是**备件**和**备件流水**。

2029 年，这台机器到了报废年限，设备科把状态改成"报废"，停用两条保养计划。台账记录还在，历史工单还在，备件流水还在——**设备死了，档案不能死**，因为后面还要算这台机器的全生命周期成本。

把这段流水账抽象一下，就是六个动作、六张表：

| 时间 | 动作 | 落到的表 | 关键行为 |
|------|------|---------|---------|
| 2022-06-20 | 采购入库，建台账 | `eam_asset` | 生成唯一 asset_no，初始化 status=RUNNING |
| 2022-07 | 排保养计划 | `eam_maintain_plan` | 定 cycle_type/cycle_value/advance_days/next_maintain_time |
| 每月到期 | 生成保养工单 | `eam_maintain_order` | 引擎算出到期，写工单，推进计划 |
| 2026-11-08 | 故障报修 | `eam_repair_order` | 建单，status=PENDING_DISPATCH |
| 2026-11-08 | 领件换件 | `eam_spare_part` + `eam_spare_record` | 校验库存、扣减、写流水 |
| 2029 | 报废 | `eam_asset` + `eam_maintain_plan` | status=SCRAPPED，计划停用 |

六张表，正好接住一台设备从生到死的六个动作。不多一张，也不少一张。

## 二、六张表与 ER：不用图，用一张表说清关系

很多文章讲数据模型喜欢放一张 ER 图。这个连载不放——studio 不渲染 mermaid，放了也是一堆源码。我用一张表格把关系说清楚，效果一样，还能直接看出"关联键是什么、基数是多少、为什么这么连"。

| 主表 | 从表 | 基数 | 关联键 | 为什么这么连 |
|------|------|------|--------|-------------|
| `eam_asset` | `eam_maintain_plan` | 1 : N | `plan.asset_id → asset.id` | 一台设备可以有多条计划（月度、季度、年度） |
| `eam_maintain_plan` | `eam_maintain_order` | 1 : N | `order.plan_id → plan.id` | 一条计划会周期性生成很多张工单 |
| `eam_asset` | `eam_maintain_order` | 1 : N | `order.asset_id → asset.id` | 冗余关联：工单要能脱离计划直接按设备查 |
| `eam_asset` | `eam_repair_order` | 1 : N | `order.asset_id → asset.id` | 一台设备一生会坏很多次 |
| `eam_spare_part` | `eam_spare_record` | 1 : N | `record.part_id → part.id` | 一个备件的每一次出入库都是一条流水 |
| `eam_spare_part` | `eam_asset` | N : N | `part.asset_ids`（JSONB 数组） | 一个备件可用于多台设备，用 JSONB 反范式代替关联表 |
| `eam_repair_order` | `eam_spare_record` | 1 : N（弱） | `record.biz_order_no = order.order_no` | 流水要能挂到工单，但不能被工单外键绑死（采购入库也要用流水） |

这张表里有三个"不寻常"的地方，后面会逐一展开：工单冗余了 `asset_id`、备件用 JSONB 数组表达多对多、流水和工单是字符串弱关联。先把六张表逐张过一遍。

### 2.1 eam_asset：设备的身份证

台账表是整个系统的主数据锚点。它的字段不多，但每个都有讲究：

```sql
CREATE TABLE IF NOT EXISTS eam_asset (
    id                  BIGSERIAL PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL DEFAULT 1,
    asset_no            VARCHAR(64)  NOT NULL,                -- 设备编号，租户内唯一，如 EQ-CNC-001
    name                VARCHAR(128) NOT NULL,                -- 设备名称
    model               VARCHAR(128),                         -- 规格型号
    category            VARCHAR(64),                          -- 设备分类，如 机加/注塑/装配
    location            VARCHAR(128),                         -- 安装位置，如 一车间-A线
    status              SMALLINT     NOT NULL DEFAULT 1,      -- 1=运行 2=停机 3=维修中 4=报废
    purchase_date       DATE,                                 -- 采购日期
    warranty_until      DATE,                                 -- 质保到期日
    responsible_user_id BIGINT,                               -- 责任人用户 ID
    attributes          JSONB        NOT NULL DEFAULT '{}',   -- 扩展属性，如 {"power":"15kW","vendor":"沈阳机床"}
    remark              VARCHAR(512) NOT NULL DEFAULT '',
    creator             VARCHAR(64),
    create_time          TIMESTAMP    NOT NULL DEFAULT NOW(),
    updater             VARCHAR(64),
    update_time          TIMESTAMP    NOT NULL DEFAULT NOW(),
    deleted             BOOLEAN      NOT NULL DEFAULT FALSE,
    UNIQUE (tenant_id, asset_no)
);

CREATE INDEX IF NOT EXISTS idx_eam_asset_status   ON eam_asset(status);
CREATE INDEX IF NOT EXISTS idx_eam_asset_category ON eam_asset(category);
```

几个设计点：

**`asset_no` 是业务主键，`id` 是技术主键。** 车间里没人记 `id=3`，大家说的是"EQ-INJ-001 那台注塑机"。所以 `asset_no` 必须唯一，而且是租户内唯一——`UNIQUE (tenant_id, asset_no)`，不是全局唯一。多租户系统里，A 厂和 B 厂都可以有 `EQ-CNC-001`，这很正常。

**`status` 用 SMALLINT，四个值。** 1=运行、2=停机、3=维修中、4=报废。注意"停机"和"维修中"是两回事：停机可能是没订单、等料、计划检修；维修中是正在修。分开这两个状态，才能算"故障停机时长"和"计划停机时长"。

**`warranty_until` 是很多人会漏的字段。** 保修期内坏了，应该走供应商索赔，而不是自己掏钱修。系统里保留这个日期，后面可以在报修时提示"该设备仍在保修期内"。这是个很小的字段，但一年能给工厂省下几万块。

**`responsible_user_id` 存用户 ID，不存姓名。** 姓名会变、会重名，ID 不会。前端展示时再关联用户表取名字。这是所有业务表都应该遵守的规矩：**存标识，不存展示值**。

### 2.2 eam_maintain_plan：保养的"闹钟"

```sql
CREATE TABLE IF NOT EXISTS eam_maintain_plan (
    id                 BIGSERIAL PRIMARY KEY,
    tenant_id          BIGINT       NOT NULL DEFAULT 1,
    plan_no            VARCHAR(64)  NOT NULL,                -- 计划编号，租户内唯一，如 MP-2026-001
    asset_id           BIGINT       NOT NULL REFERENCES eam_asset(id),
    plan_name          VARCHAR(128) NOT NULL,
    cycle_type         SMALLINT     NOT NULL,                -- 1=按天数 2=按周数 3=按月数
    cycle_value        INT          NOT NULL,                -- 周期数值，如 1（个月）
    advance_days       INT          NOT NULL DEFAULT 0,      -- 提前几天生成工单
    last_maintain_time TIMESTAMP,                            -- 上次保养时间
    next_maintain_time TIMESTAMP,                            -- 下次保养时间（录入时初始化）
    status             SMALLINT     NOT NULL DEFAULT 1,      -- 0=停用 1=启用
    remark             VARCHAR(512) NOT NULL DEFAULT '',
    creator            VARCHAR(64),
    create_time         TIMESTAMP    NOT NULL DEFAULT NOW(),
    updater            VARCHAR(64),
    update_time         TIMESTAMP    NOT NULL DEFAULT NOW(),
    deleted            BOOLEAN      NOT NULL DEFAULT FALSE,
    UNIQUE (tenant_id, plan_no)
);

CREATE INDEX IF NOT EXISTS idx_eam_maintain_plan_asset  ON eam_maintain_plan(asset_id);
CREATE INDEX IF NOT EXISTS idx_eam_maintain_plan_status ON eam_maintain_plan(status);
```

这张表最核心的是三个字段：`cycle_type`、`cycle_value`、`advance_days`。它们一起定义了"这台设备多久保养一次、提前几天提醒"。

`cycle_type` 只有三个值：按天、按周、按月。为什么不做"按年"？因为按年可以用"按月 × 12"表达，没必要多一个枚举值。为什么不做"按运行小时"？因为那需要 SCADA 提供累计运行时长，超出了这个演示版本的边界——第 3 章会专门讲这个缺口。

`last_maintain_time` 和 `next_maintain_time` 是一对。注意 `next_maintain_time` 的注释写的是"录入时初始化"，不是"系统自动算"。这是刻意的：**引擎不替脏数据猜**。一条计划录入时，设备科必须明确告诉系统"下一次是什么时候"，引擎只负责从这个基准往后推进。如果让引擎自己猜（比如拿 `now()` 加上周期），那录入时就会引入一次隐式误差，而且无法复现。

`advance_days` 这个字段看起来不起眼，但它解决了一个真实问题：保养工单不能"当天到期当天出"，因为维修班要排人、要备料、要和生产协调停机窗口。提前 3 天出单，是给现场留缓冲。种子数据里，月度计划提前 3 天，季度计划提前 7 天，就是这个考虑。

### 2.3 eam_maintain_order：一次保养的执行

保养工单的关键字段是 `order_no`、`plan_id`、`asset_id`、`plan_date`、`status`、`assignee_id`、`version`，另外还有 `start_time`、`finish_time`、`content`、`result_note` 四个执行字段。

保养工单的状态只有四个：待执行、执行中、已完成、已取消。流转是线性的：1→2→3，任意非终态可以到 4。只有三条迁移边，所以 Service 层直接用 `if` 校验，没有再抽一个状态机——这是刻意的"不对称设计"：维修工单六状态五条边才值得上状态机，保养工单三条边不值得。**复杂度匹配问题规模，不为了统一而统一。**

`plan_id` 允许为空，是给"手工补录"留的口子。有些保养是临时加的（比如设备刚搬迁完，要做一次全面检查），没有对应的计划。这时候 `plan_id` 为空，`asset_id` 必须有——工单可以没有计划，但不能没有设备。

`version` 是乐观锁。保养工单可能同时在移动端和 PC 端打开，两个维修工同时点"开工"，没有版本号就会互相覆盖。这个字段的具体机制第 8 章讲。

### 2.4 eam_repair_order：一次故障的闭环

维修工单的字段比保养工单厚得多：`order_no`、`asset_id`、`fault_desc`、`priority`、`status`，加上 `reporter`、`assignee_id`、`dispatch_time`、`start_time`、`finish_time`、`repair_note`、`accept_note`，最后是 `version`。

维修工单是六张表里字段最"厚"的一张，因为它要承载一条完整的时间线：报修 → 派工 → 开工 → 完工 → 验收。四个时间戳（`create_time`、`dispatch_time`、`start_time`、`finish_time`）分别对应四个动作，这也是 MTBF/MTTR 能算出来的前提。

`reporter` 存的是姓名字符串，不是用户 ID。这是个例外——报修人可能是操作工、班组长、甚至门卫，不一定有系统账号。`assignee_id` 则是用户 ID，因为维修人必须是系统里的用户，要能登录、要领料、要签字。**不是所有"人"都值得建账号，但所有"责任人"必须可追溯。**

`priority` 四档：低、中、高、紧急。演示版本只把它当标识用，没有实现"紧急工单插队"的抢占逻辑。这个取舍要诚实说明：优先级字段有了，调度算法还没做。商用版本应该在派工时按优先级排序，或者给紧急工单设 SLA 计时。

### 2.5 eam_spare_part：备件主数据 + 当前库存

备件表的核心字段是 `part_no`、`name`、`spec`、`unit`、`stock`、`safety_stock`、`asset_ids`、`location`。

备件表有两个"库存"字段：`stock` 是当前库存，`safety_stock` 是安全库存。前者是事实，后者是阈值。`stock` 的注释写得很重："只能由出入库流水改变"。这是这张表的铁律——任何直接 `UPDATE stock` 的代码都是 bug，因为那样库存和流水就对不上账了。Service 层的 `updateSparePart` 方法里，`stock` 被刻意排除在更新字段之外，只更新主数据和 `safety_stock`。

`asset_ids` 是 JSONB 数组，存适用设备 ID。这个设计后面会专门讲，它有明显的收益，也有明显的局限。

### 2.6 eam_spare_record：只增不改的审计轨迹

流水表只有六个业务字段：`part_id`、`type`、`quantity`、`biz_order_no`、`operator`、`remark`。

流水表的设计有三个关键点。

**第一，`quantity` 恒为正数，方向由 `type` 表达。** 不搞"入库 +5、出库 -5"的有符号数量。因为有符号数量会让所有统计 SQL 都变成 `SUM(quantity)` ——看起来简单，但一旦有人把 `type` 和符号搞混，就会出现"入库 5 条、出库 5 条、总和 0"的诡异结果。用无符号数量 + 类型，至少方向是显式的。

**第二，流水只增不改。** 没有 `updateRecord` 方法，只有 `createRecord` 和查询。错了怎么办？用反向流水冲正——出库错了就入库一笔，而不是改原来那条。这是审计的基本要求：**历史可以补充，不能篡改**。

**第三，`biz_order_no` 是字符串，没有外键。** 因为它不只挂维修工单，还可能挂采购单、退库单、盘点单。用一个字符串统一表达"这笔流水属于哪个业务动作"，比建四张关联表简单得多。代价是没有引用完整性，填错了系统不知道。这个取舍第 5 章会详细讲。

## 三、取舍一：attributes 为什么用 JSONB，而不是 20 个扩展字段

现在讲这张表里最有争议的设计：`eam_asset.attributes`。

假设不用 JSONB，要给设备建扩展属性，最直接的做法是加列：`power`、`voltage`、`vendor`、`serial_no`、`clamping_force`、`spindle_speed`、`travel_x`、`travel_y`、`air_flow`、`pressure`…… 一开始觉得十几个够了，做着做着发现不够，因为不同行业的设备属性完全不一样：

| 设备类型 | 关心的属性 |
|---------|-----------|
| 注塑机 | 锁模力、注射量、模温、油泵压力 |
| 数控车床 | 最大回转直径、主轴转速、行程、刀位数 |
| 加工中心 | 工作台尺寸、主轴功率、刀库容量、定位精度 |
| 空压机 | 排气量、排气压力、储气罐容积、电机功率 |
| 装配线 | 节拍、工位数、输送方式、定位精度 |

五类设备就有二十多个不同的属性，而且每来一个新行业就可能加几个。如果用列来表达，会发生三件事：

第一，**稀疏列**。200 台设备里，注塑机的 `clamping_force` 有值，数控车床的这一列永远是 NULL。表越来越宽，有效数据密度越来越低。

第二，**DDL 变更成本**。每加一个属性都要改表结构、改 DO、改 VO、改前端表单。在生产环境改表，哪怕是加一个可空列，也要走变更流程、评估锁表时间。

第三，**DO 膨胀**。`EamAssetDO` 会有三十个字段，其中二十个是"某个行业才用"的。新人看这个类，根本分不清哪些是核心字段、哪些是扩展字段。

JSONB 把这些问题一次性解决了。属性放在一个字段里，值是一段 JSON：`{"power":"37kW","clampingForce":"160T","vendor":"海天","serialNo":"HT20220620"}`。

加一个新属性不需要改表，前端表单按设备分类动态渲染，Java 侧只用一个 `Map<String, Object>` 接。PostgreSQL 的 JSONB 还支持 GIN 索引和 `->>` 取值，真要做统计也能做（比如"查所有功率大于 30kW 的设备"）。

代价也很明确，必须说清楚：

**其一，没有 schema 校验。** `power` 写成 `"37KW"`、`"37kw"`、`37`，数据库都收。解法是在应用层做校验，或者用 JSON Schema 约束。演示版本没做，这是个已知缺口。

**其二，类型弱。** `Map<String, Object>` 里的值是 Object，取出来要自己转 String/Integer/Double。跨行聚合（比如"平均功率"）要显式 cast，写起来比普通列麻烦。

**其三，ORM 需要额外配置。** 这是最容易踩的坑。MyBatis-Plus 默认不认识 JSONB，你必须在 `@TableName` 上加 `autoResultMap = true`，并在字段上加 `@TableField(typeHandler = JacksonTypeHandler.class)`：

```java
// dal/dataobject/EamAssetDO.java（节选）
@Data
@TableName(value = "eam_asset", autoResultMap = true)
public class EamAssetDO implements Serializable {

    @Serial
    private static final long serialVersionUID = 1L;

    @TableId(type = IdType.AUTO)
    private Long id;

    /** 设备编号，租户内唯一，如 EQ-CNC-001 */
    private String assetNo;

    /** 1=运行 2=停机 3=维修中 4=报废 */
    private Integer status;

    /** 设备扩展属性（JSONB），如 {"power":"15kW","vendor":"沈阳机床","serialNo":"SY20240315"} */
    @TableField(typeHandler = JacksonTypeHandler.class)
    private Map<String, Object> attributes;

    private String remark;
    private Boolean deleted;
}
```

`autoResultMap = true` 这行如果漏了，插入是正常的（`JacksonTypeHandler` 会生效），但查询回来 `attributes` 是 null——因为 MyBatis-Plus 默认的 resultMap 不包含 typeHandler。我第一次写的时候就踩了这个坑，查了半天 SQL 没问题，最后发现是注解漏了。**凡是 JSONB 字段，`@TableName` 上的 `autoResultMap` 和字段上的 `typeHandler` 必须成对出现。**

那什么时候不该用 JSONB？我的判断标准是：**要参与高频查询、排序、聚合、外键约束的字段，必须是实体列；只是"附带信息"的，才放 JSONB。** 所以 `category`、`location`、`status` 这些要用来筛选的，都是实体列，还建了索引；`power`、`vendor`、`serialNo` 这些只用来展示的，才放进 `attributes`。这个边界很重要——如果反过来，把 `status` 塞进 JSONB，那每次查"所有运行中的设备"都要全表扫，性能会崩。

## 四、取舍二：备件的 assetIds 为什么用 JSONB 数组

第二个反范式设计是 `eam_spare_part.asset_ids`。

正常的关系建模，备件和设备的"多对多"应该建一张关联表：

```sql
CREATE TABLE eam_spare_asset (
    part_id  BIGINT NOT NULL REFERENCES eam_spare_part(id),
    asset_id BIGINT NOT NULL REFERENCES eam_asset(id),
    PRIMARY KEY (part_id, asset_id)
);
```

这是教科书答案，第三范式，引用完整，查询灵活。但我最后没用，而是用一个 JSONB 数组 `[1,2]` 存。原因有三条。

**第一，写入简单。** 关联表意味着新增一个备件要先插主表、再插 N 条关联；修改适用设备要"先删后插"。而 JSONB 数组是一次 insert/update 就完事，前端传什么就存什么。

**第二，读取简单。** 备件列表页要展示"适用设备"，关联表要 JOIN，或者一次批量查再在内存里拼；JSONB 直接把数组带出来，前端拿 ID 列表去匹配设备名即可。

**第三，规模小。** 中小厂的备件数量通常在几百到几千，每个备件适用的设备通常是个位数到几十。这个规模下，反范式的收益远大于代价。

Java 侧同样用 `JacksonTypeHandler` 映射成 `List<Long>`，`@TableName` 上同样要开 `autoResultMap = true`，和 `attributes` 的写法完全一致。

局限同样要说清楚，而且比 `attributes` 的局限更硬：

**其一，反向查询要全表扫。** "这台设备用哪些备件"是最常见的需求之一。用 JSONB 数组，SQL 是 `SELECT * FROM eam_spare_part WHERE asset_ids @> '[3]'::jsonb AND deleted = FALSE`。`@>` 是 JSONB 的包含操作符，语义没问题；但没有 GIN 索引时，这是**全表扫描 + 逐行解析 JSON**。几百行无所谓，几万行就明显了。解法是加 GIN 索引：

```sql
CREATE INDEX idx_eam_spare_part_asset_ids
    ON eam_spare_part USING GIN (asset_ids);
```

**其二，没有引用完整性。** 设备报废或删除后，`asset_ids` 里残留的 ID 不会被自动清理，也不会报错。查出来是一串"幽灵设备"。商用版本需要定期跑一致性校验，或者改成关联表 + 外键。

**其三，表达不了"关系上的属性"。** 关联表可以加 `quantity_per_asset`（单机用量）、`install_position`（装配位置）、`last_replaced_at`（上次更换时间）。JSONB 数组只能表达"有没有关系"，表达不了"关系是什么"。如果业务需要算"这台设备的备件年消耗量"，JSONB 就不够了。

所以我的结论是：**备件适用设备这种"弱多对多、只读展示、规模小"的关系，JSONB 数组是合适的反范式；一旦需要记录关系属性、需要反向高频查询、或者规模上万，就应该拆关联表。** 这不是"哪个更先进"的问题，是"哪个匹配当前规模"的问题。

## 五、取舍三：工单为什么冗余 assetId，而不只存 planId

第三个设计决策藏在 `eam_maintain_order` 里：这张表既有 `plan_id`，又有 `asset_id`。按第三范式，`plan_id` 已经能推出 `asset_id`（计划表里有），工单表再存一份就是冗余。

但我还是存了，理由有三个。

**第一，工单是"事实"，计划是"规则"。** 计划是"这台设备每月保养一次"这条规则；工单是"2026 年 11 月 10 日，这台设备做了一次保养"这个事实。事实必须自包含——十年后计划被改了、被删了，工单还要能独立回答"当时是哪台设备"。如果工单只存 `plan_id`，那计划一删，历史工单就成了孤儿。

**第二，查询性能。** "查这台设备的所有保养工单"是最高频的查询。如果只存 `plan_id`，SQL 要先 JOIN 计划表才能按设备过滤：

```sql
SELECT o.* FROM eam_maintain_order o
JOIN eam_maintain_plan p ON o.plan_id = p.id
WHERE p.asset_id = 3;
```

冗余 `asset_id` 之后，直接 `WHERE asset_id = 3`，走 `idx_eam_maintain_order_asset` 索引，一次索引扫描搞定。工单表的量级是"每台设备每年十几张"，十年也就几十万行，这个索引很关键。

**第三，计划的归属可能变。** 如果设备科把一条计划从 EQ-CNC-001 改到 EQ-CNC-002（比如计划建错了设备），历史工单不应该跟着"穿越"到新设备上。工单冗余 `asset_id`，就把"当时是哪台设备"钉死了，这是审计正确性。

代价是一致性风险：插入工单时，`asset_id` 必须从计划里带过来，不能前端传。引擎里就是一行 `order.setAssetId(plan.getAssetId())`，再加上 `order.setPlanId(plan.getId())`，两个字段都从计划取值。这是"冗余字段的唯一可信来源"——只要所有写入口都这么写，一致性就不会出问题。

同样的逻辑也适用于 `order_no` 里嵌的 `planId`：`MO-20261110-1` 里的 `1` 是计划 ID。这是第二处冗余，好处是运维一眼能看出工单来自哪条计划，坏处是计划 ID 变了工单号就对不上——但计划 ID 是自增主键，不会变，所以这个风险可以接受。

## 六、7 个枚举：为什么用 Integer code，不用 EnumTypeHandler

系统里有 7 个业务枚举：

| 枚举 | 取值 | 落在哪张表 |
|------|------|-----------|
| `EamAssetStatus` | 1 运行 / 2 停机 / 3 维修中 / 4 报废 | `eam_asset.status` |
| `EamCycleType` | 1 按天 / 2 按周 / 3 按月 | `eam_maintain_plan.cycle_type` |
| `EamMaintainOrderStatus` | 1 待执行 / 2 执行中 / 3 已完成 / 4 已取消 | `eam_maintain_order.status` |
| `EamPlanStatus` | 0 停用 / 1 启用 | `eam_maintain_plan.status` |
| `EamRepairPriority` | 1 低 / 2 中 / 3 高 / 4 紧急 | `eam_repair_order.priority` |
| `EamRepairStatus` | 1 待派工 / 2 已派工 / 3 维修中 / 4 待验收 / 5 已完成 / 6 已取消 | `eam_repair_order.status` |
| `EamSpareRecordType` | 1 入库 / 2 出库 / 3 退库 | `eam_spare_record.type` |

每一个都是这个形状：

```java
// enums/EamCycleType.java
@Getter
@AllArgsConstructor
public enum EamCycleType {
    DAYS(1, "按天数"),
    WEEKS(2, "按周数"),
    MONTHS(3, "按月数");

    private final Integer code;
    private final String name;
}
```

为什么不用 MyBatis-Plus 自带的 `EnumTypeHandler`，直接把 DO 字段声明成枚举类型？因为 `EnumTypeHandler` 默认落库的是**枚举名**（`PENDING_DISPATCH`）或**ordinal**（0、1、2），两个都有硬伤。

**落枚举名的问题：改名即数据迁移。** 今天叫 `PENDING_DISPATCH`，明天产品说"待派工"改成"待分配"，开发顺手把枚举常量改成 `PENDING_ASSIGN`——数据库里所有历史数据立刻对不上，查询全空。而且枚举名是英文、下划线，DBA 和报表工具看不懂，前端字典还要再做一层映射。

**落 ordinal 的问题：调序即错乱。** ordinal 是枚举常量的声明顺序，今天 `PENDING_DISPATCH` 是 0，明天有人在前面插了一个 `NEW`，所有值整体后移。数据库里的 0 突然变成了 `NEW`，历史数据全部错位。这是最危险的一种，因为编译能过、启动能过，只有数据悄悄错了。

显式 `Integer code` 把"落库值"和"Java 常量名"解耦：数据库里永远是 1、2、3，枚举常量随便改名、随便调序，只要 `code` 不变，数据就不会坏。而且这套 code 可以直接对齐芋道的字典表（`system_dict_data`），前端用同一套字典渲染下拉框，不需要额外映射。

代价也要认：

**其一，DO 里是 `Integer`，不是枚举。** 所以 Service 里到处是 `EamRepairStatus.DONE.getCode()` 这样的比较，而不是 `status == DONE`。代码稍微啰嗦，但换来的是"落库值显式可见"。

**其二，脏 code 要兜底。** 如果有人手工往库里插了 `status = 99`，枚举转换会失败。所以引擎里有一个防御性的 `cycleTypeOf(Integer code)`：遍历 `EamCycleType.values()` 匹配 `code`，找不到返回 null，由调用方按脏数据跳过。注意这里的取舍：找不到不是抛异常，是返回 null，让调用方 `continue`。因为保养扫描是批处理，一条脏数据不应该让整批 200 台设备的扫描全部失败。**批处理的第一原则是"坏一条，跳过一条，别搞挂一批"。**

**其三，前端要维护字典。** 每个枚举都要在字典表里配一份，否则下拉框是空的。这是运维成本，但也是好处——字典可以热更新，加一个状态不用发版。

## 七、约束与索引：让数据库帮你守规矩

六张表的 DDL 里，有一批容易被忽略但很重要的东西：唯一键、外键、普通索引。它们不是"性能优化"，是"数据正确性的最后一道防线"。

| 类型 | 位置 | 作用 |
|------|------|------|
| `UNIQUE (tenant_id, asset_no)` | `eam_asset` | 同一租户内设备编号不重复 |
| `UNIQUE (tenant_id, plan_no)` | `eam_maintain_plan` | 计划编号不重复 |
| `UNIQUE (tenant_id, order_no)` | `eam_maintain_order` | 保养工单号不重复，防重复出单 |
| `UNIQUE (tenant_id, order_no)` | `eam_repair_order` | 维修工单号不重复 |
| `UNIQUE (tenant_id, part_no)` | `eam_spare_part` | 备件编号不重复 |
| `REFERENCES eam_asset(id)` | plan / maintain_order / repair_order | 工单不能挂到不存在的设备上 |
| `REFERENCES eam_maintain_plan(id)` | maintain_order | 保养工单的计划必须存在（可空） |
| `REFERENCES eam_spare_part(id)` | spare_record | 流水必须挂到存在的备件 |
| `idx_eam_asset_status` | `eam_asset` | 按状态筛设备（"所有维修中的设备"） |
| `idx_eam_maintain_plan_status` | `eam_maintain_plan` | 扫描时只取启用的计划 |
| `idx_eam_maintain_order_asset` | `eam_maintain_order` | 按设备查工单 |
| `idx_eam_repair_order_asset` | `eam_repair_order` | 按设备查维修历史 |
| `idx_eam_spare_record_biz` | `eam_spare_record` | 按工单号反查领料记录 |

两个点值得展开。

**唯一键是幂等的最后保险。** 保养引擎的工单号是 `MO-yyyyMMdd-planId`，理论上同一天同一计划只会出一张。但万一并发两次扫描、或者有人手工造单，`UNIQUE (tenant_id, order_no)` 会让第二次插入直接失败，而不是悄悄插进去两条。**唯一键不是"应该加"，是"必须加"**——它是应用层逻辑出错时，数据库替你踩刹车。

**外键在演示库开启，商用要评估。** 外键能保证引用完整性，但高并发写入时会有额外的锁开销，而且分库分表后外键基本不可用。所以很多互联网团队禁用外键。我的看法是：中小工厂的 EAM，写入量是"每天几十到几百条"，外键的开销可以忽略，收益（防止脏关联）远大于成本。等哪天要分库了再拆。**架构决策要匹配当前规模，不要提前为"千万级并发"买单。**

还有一个字段必须提：`deleted`。六张表都有 `deleted BOOLEAN NOT NULL DEFAULT FALSE`，这是逻辑删除。芋道框架的 `BaseMapperX` 会自动在查询里加 `deleted = false`，删除时改成 `true`。好处是历史可恢复，坏处是所有唯一键都要考虑"已删除的重复"——比如一台设备删了，再建同编号的设备，`UNIQUE (tenant_id, asset_no)` 会冲突。商用版本要么把 `deleted` 加进唯一键，要么删除时改编号。演示版本没处理，这是个已知缺口。

`eam-init.sql` 的末尾是种子数据，一共五组。它们不是随便写的，每一条都对应后面某一章的验证场景。

**3 台设备：**

| id | asset_no | 名称 | 型号 | 分类 | 位置 | 状态 | 备注 |

- 备件 2 的 `asset_ids = [3]`，正好对应设备 3（注塑机），而维修工单也是设备 3，流水也挂在工单上——"这台设备用这个备件、这张工单领了这个件"整条链路是通的。

我写种子数据的原则是：**宁可少，不要假**。五组数据，每组都能在后面的章节里被真实调用，不写"测试设备 1、测试设备 2"这种占位数据。因为文章里的每个数字，读者都可能拿去复现，编的数据一跑就露馅。

## 九、商用化检查清单（模型版）

- `attributes` 的 JSONB schema 有没有校验？当前是自由 Map，键名和类型都可能写错。
- 备件 `asset_ids` 有没有 GIN 索引？反向查询"这台设备用什么备件"会不会全表扫？
- 设备删除/报废后，`asset_ids` 里的残留 ID 谁来清理？
- 逻辑删除 `deleted` 和唯一键冲突怎么处理？删了再建同编号设备会报唯一键冲突。
- 外键在生产库是否保留？分库分表或高并发写入场景要重新评估。
- `priority` 字段有了，但"紧急工单插队"的调度逻辑没实现，商用要不要补 SLA？
- 保修期 `warranty_until` 是否在报修时提示？当前只是存着，没有联动。
- 工单号规则 `MO-yyyyMMdd-planId` 在跨天补跑时会不会重号？唯一键能兜住，但报表按日期统计会偏。
- 7 个枚举的 code 是否和前端字典一一对齐？字典漏配会导致下拉框空白。
- `tenant_id` 是否由芋道多租户插件自动注入？手写 SQL 必须自己带，否则跨租户串数据。

## 十、下一章预告：保养计划引擎，从 cron 到滑动窗口

模型建好了，接下来是第一个引擎：保养计划怎么算出"今天该不该出单"。

这一章会讲一个我真实踩过的坑：一开始我用 Spring 的 `@Scheduled(cron = "0 0 8 1 * ?")`，每月 1 号早上 8 点扫描全厂计划。结果第一个月就出事了——200 台设备里有 60 多台同时到期，维修班一天收到 60 张工单，根本干不完；更要命的是，有些设备上个月 28 号刚保养过，1 号又被排了一次，因为 cron 只知道"今天是 1 号"，不知道"这台设备上次是什么时候做的"。

cron 是日历定点，保养周期是相对上次完成时间的滑动窗口。这两个语义的差别，决定了整个引擎的设计。下一章我会把 `NextDateCalculator` 和 `MaintainPlanEngine.scanAndGenerate` 的每一行拆开讲：三种周期怎么算、提前窗口怎么判、脏数据怎么跳过、工单号怎么生成、重复扫描为什么不会重复出单，以及一个"空压机 500 小时保养"的手算例子——顺便讲清楚，"按运行小时保养"这个真实需求，当前的数据模型为什么接不住。
