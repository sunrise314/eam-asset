# 用 MTBF 和 MTTR 算清设备可靠性

## 一、场景：预算会上，三个数字打了三种口径

第四年冬天，王主任把我叫去开一个我本来没资格参加的会——年度设备更新预算评审。桌上坐的是厂长、财务、设备科和维修班，议题只有一个：二车间那台海天 HTF160 注塑机，用了五年，今年到底换不换。新机报价 86 万，大修报价 12 万，不换继续修的话，今年已经花掉的维修费是 4.8 万。

厂长先问了一句："这台机，是不是我们厂最不靠谱的那台？"

会议室里出现了三个数字，而且互相打架。李师傅是维修班班长，他掰着手指头说："**今年修了五次**，光伺服电机那次就等了快三个月件。"财务翻着台账说："**维修费 4.8 万**，比去年涨了 40%。"设备科的小赵打开 Excel 说："**这台机状态是运行**，上个月还满产。"

三个数字，三套口径，谁也说服不了谁。厂长最后看向我："你那个系统里不是有维修记录吗？能不能给我一个数，让我知道这台机到底是'偶尔坏但修得快'，还是'一坏就趴一个月'？"

这个问题问得很专业。它其实是在问两个不同的东西：**故障的频率**和**修复的能力**。前者叫 MTBF（Mean Time Between Failures，平均故障间隔），后者叫 MTTR（Mean Time To Repair，平均修复时间）。而厂长脱口而出的那句"最不靠谱"，恰恰是这两个指标合起来才能回答的——一台设备可能坏得不频繁，但每次修一个月；也可能坏得频繁，但每次两小时就恢复。这两种"不靠谱"，处置方式完全不同。

我答应他两周内给一张表。这张表后来成了这套 EAM 里被翻得最烂的一个页面，而它背后的代码只有一个五十行不到的纯函数类：`MtbfCalculator`。这一章就讲清楚：这两个指标的口径怎么钉死、代码逐段为什么这么写、真实数据算出来是什么样、以及为什么同一个公式能被不同部门算出三个数。

## 二、定义先把口径钉死，公式是最后一步

MTBF 和 MTTR 是可靠性工程里的标准概念，任何一本设备管理教材上都有公式。但我在项目里反复强调一句话：**公式是常识，口径是工程**。同一个公式，换三种口径能算出三个数，而且三个数都"没错"。所以先把口径钉死，再谈计算。

我们这个系统采用的口径，写在 `MtbfCalculator` 的类注释里，一共三行：

| 指标 | 公式 | 业务含义 | 单位 |
|------|------|---------|------|
| MTBF 平均故障间隔 | （统计窗口总时长 − 总维修时长）÷ 故障次数 | 平均"好好跑多久才坏一次"，越大越好 | 小时 |
| MTTR 平均修复时间 | 总维修时长 ÷ 故障次数 | 平均"坏一次要修多久"，越小越好 | 小时 |
| 可用率 | MTBF ÷ (MTBF + MTTR) | 设备在统计窗口内真正可用的时间占比 | 百分比 |

三个口径决定必须一条条讲清楚，因为它们直接决定数字的含义。

**第一，MTBF 的分子为什么要减掉维修时长。** 设备躺在维修台上的那几个小时（或者那几十天），既不是"正常运行"，也不是"随时可能故障"——它已经故障了，正在被修。如果分子直接用窗口总时长，一台"修一次瘫一个月"的设备会显得 MTBF 极高，这是假的好。分子只保留"设备本可以正常跑的时间"，才对得起"故障**间隔**"这四个字。行业里确实有人图省事直接用窗口时长除以次数，短期看差别不大，但维修时长占比越高，误差越离谱：一台一年修了 2760 小时的设备，两种口径能差出 30% 以上。

**第二，故障次数怎么数。** 我们的定义是：**统计窗口内已完成的维修工单数**。三个限定词缺一不可——"已完成"（status=DONE）、"窗口内"（finishTime 落在窗口里）、"维修工单"（报修后又取消的误报不算）。为什么只数已完成的？因为进行中的工单维修时长还没定，把它算进分母会同时污染 MTBF 和 MTTR：次数加了、时长没加，MTBF 和 MTTR 一起失真。这个选择有代价——一张修了两个月还没验收的单，等于从统计里消失了，会让指标"看起来变好"。这个坑我在第十章的复盘里专门讲。

**第三，维修时长算不算"停机等待件"的时间。** 这是三个口径里争议最大的一个。李师傅说的"伺服电机等了快三个月件"，那 87 天算不算维修时长？我们的实现里，维修时长取的是工单的 `startTime` 到 `finishTime`，而 `startTime` 是"开始维修"的时间，不是"设备停机"的时间。所以严格来说，**等件的时间不算维修时长**——它既不在 MTBF 的分子里，也不在 MTTR 的分子里，等于从统计窗口里凭空蒸发了。这是个已知的缺口，代价是 MTBF 被高估、MTTR 被低估。我在第八节会讲商用版怎么补：要么把 `startTime` 改成"停机时间"，要么单独加一张停机记录表。演示仓库先按"维修工时"口径实现，因为这是维修班唯一能保证填准的时间。

**第四，窗口由调用方传，指标不落库。** 月报传自然月、季报传季度、年度评审传一整年。为什么不建一张"设备指标表"算一次存一次？因为一落库，口径就被锁死了：客户想把月报改成滚动 30 天，历史数据全部作废，得重刷。随查随算的纯函数，窗口想怎么切就怎么切。代价是每次都要扫一遍工单，但中小工厂的量级（几百台设备、一年几百张工单）下，这根本不是性能问题。**规模决定架构**，等工单涨到几十万张再谈预聚合。

## 三、MtbfCalculator：五十行代码，五处讲究

整个计算器就是一个 `static` 方法加一个 `@UtilityClass` 注解，没有依赖、没有状态、没有 Spring。完整代码如下：

```java
// framework/eam/metrics/MtbfCalculator.java
@UtilityClass
public class MtbfCalculator {

    public static MetricsResult calc(Long assetId, List<EamRepairOrderDO> doneOrders,
                                     LocalDateTime windowStart, LocalDateTime windowEnd) {
        int faultCount = doneOrders != null ? doneOrders.size() : 0;
        if (faultCount == 0) {
            // 除零无意义：MTBF 是"平均多久坏一次"，0 次故障时它趋近无穷大而不是 0。
            // 返回 null 让前端显示 "—"，避免误导成"这台设备每 0 小时就坏一次"。
            return new MetricsResult(assetId, 0, null, null);
        }
        // 总维修时长：只累加起止时间齐全的工单；缺时间的脏数据跳过，不污染整体口径
        double repairHours = 0.0;
        for (EamRepairOrderDO order : doneOrders) {
            if (order.getStartTime() == null || order.getFinishTime() == null) {
                continue;
            }
            repairHours += Duration.between(order.getStartTime(), order.getFinishTime()).toMinutes() / 60.0;
        }
        double windowHours = Duration.between(windowStart, windowEnd).toMinutes() / 60.0;
        // 窗口总时长 - 维修时长 = 无故障运行时长；防御负数（脏数据维修时长超过窗口）
        double mtbf = Math.max(windowHours - repairHours, 0.0) / faultCount;
        double mttr = repairHours / faultCount;
        return new MetricsResult(assetId, faultCount, mtbf, mttr);
    }
}
```

五十行里有五处讲究，每一处都是被真实数据逼出来的。

**第一处：入参的空判断。** `doneOrders != null ? doneOrders.size() : 0`。有人会问，Mapper 查出来的 List 怎么会是 null？正常情况当然不会是 null，但这是一个 `@UtilityClass` 的公开静态方法，任何地方都能调，包括单测里手工传 `null`。纯函数的第一条纪律是**不信任调用方**，把 null 当"零次故障"处理，方法永远不抛空指针。

**第二处：零故障返回 null，而不是 0。** 这是全方法最重要的一段。MTBF 的分母是故障次数，0 次故障时除零没有意义；而在语义上，"这个月一次没坏"的 MTBF 应该趋近无穷大，不是 0。如果把 0 当成兜底值返回，前端会显示"这台设备每 0 小时就坏一次"，把全厂状态最好的设备排到排行榜最差的位置——**指标系统的第一原则是别骗看板前的人**。返回 null，前端渲染成 "—"，含义是"这个月没坏过，算不出来"，这是诚实的表达。

这里有个工程细节值得说：null 要一路穿过 Service、Controller、JSON 序列化，中间任何一层都不许"兜底"成 0。我在 Code Review 里见过太多次这种"顺手兜底"——Controller 里一个 `result.getMtbfHours() == null ? 0 : ...`，把整个设计意图废掉。所以 `MetricsResult` 的字段类型是 `Double` 而不是 `double`，用包装类型把 null 显式地保留下来，这是一次有意的类型选择，不是随手写的。

**第三处：脏数据跳过，但仍计入故障次数。** 累加维修时长时，起止时间不全的工单直接 `continue`。真实系统里一定有这种数据：补录的历史工单只填了日期没填时分、流程异常中断的单、从旧 Excel 迁移过来时丢字段的记录。两种处理思路——抛异常让整个计算失败，或者跳过。我们选跳过：一张脏单不该搞挂整个看板。

但注意一个细节：`faultCount` 在循环**之前**就定了，被跳过的工单仍然算一次故障。这会让 MTTR 轻微偏低（分母照算、分子没加），属于"宁可偏低、不可虚高"的保守口径。这个选择在当时看是合理的——维修班报喜不报忧是常态，指标宁可保守一点。但它在上线后真咬了我一口：客户迁移进来的 200 条历史记录里有 70 条缺时分，MTTR 被压到 1.2 小时，维修班长当场拆穿"我修一次哪回不是小半天"。这件事的完整复盘在第十章。

**第四处：`Math.max` 防负数。** 理论上窗口时长一定大于维修时长，但脏数据没有"理论"：有人把一张修了 100 小时的单塞进 24 小时的窗口，不减负就得到负的 MTBF。`Math.max(windowHours - repairHours, 0.0)` 把下限钳死在 0。这不是防御式编程的风格问题，是刚需——看板上的数字没人替你复核，一个负数的 MTBF 挂在车间大屏上，整套系统的可信度当场归零。

**第五处：单位统一为小时。** `Duration.between(...).toMinutes() / 60.0`，先转分钟再除 60，保留小数。为什么不直接 `toHours()`？因为 `toHours()` 会把 90 分钟截断成 1 小时，一次两小时的维修和一次五十九分钟的维修在指标上没区别。分钟级精度对维修场景足够（一次维修从几小时到几天），用 double 返回，显示几位小数交给前端决定。单位统一还有一层意义：MTBF、MTTR、窗口时长三者在同一量纲上，前端画图、后端比对、客户手算，全都对得上。

## 四、MetricsResult：一个 record 就是一份出参契约

返回值没有用 VO，也没有用 Map，而是一个 Java record：

```java
// framework/eam/metrics/MetricsResult.java
public record MetricsResult(
        Long assetId,
        Integer faultCount,
        Double mtbfHours,
        Double mttrHours
) {
}
```

四个字段，四个都是必要的，其中一个容易被当成"副产品"删掉——`faultCount`。

`faultCount` 不是副产品，是**样本量提示**。MTBF 相近的两台设备，故障 8 次的那台远比故障 1 次的那台"稳定地差"。举个极端的例子：A 设备一年坏 1 次、修了 200 小时，MTBF 8560 小时；B 设备一年坏 5 次、每次修 40 小时，MTBF 1712 小时。只看 MTBF，A 好得多；但 A 那一次是 catastrophic failure，B 是五次可预期的小毛病。没有 faultCount 放在旁边，单看 MTBF 一定会被小样本骗到。所以这个字段在前端看板上是**必须和 MTBF 并排显示**的，不是藏在详情页里的附加信息。

用 record 而不是 Lombok 的 `@Data` 类，有三个实在的好处。**一是不可变**——指标算出来就是算出来了，从 Service 传到 Controller 再到 JSON，任何一层都改不了它，杜绝"顺手乘个系数"。**二是自解释**——四个字段的语义写在构造签名上，不需要点进类里看 getter。**三是序列化友好**——Jackson 从 2.12 起原生支持 record，出参就是 `{"assetId":3,"faultCount":1,"mtbfHours":716.0,"mttrHours":4.0}`，和前端约定的字段名一一对应，不用维护一套 VO 转换代码。

字段注释里还有一句关键的话："0 次故障时为 null，前端显示 '—'"。这句话不只是给前端看的，它是**前后端之间的契约**：后端承诺不用 0 兜底，前端承诺不用 0 渲染。契约写在代码注释里，比写在接口文档里更难被忽略——改代码的人一定会看到它。

## 五、数据从哪来：三个查询条件就是半个口径

计算器的入参 `doneOrders` 由 Mapper 查出来。查询条件本身就是口径的一部分，写错一个条件，后面的计算再精确也没用：

```java
// dal/mysql/EamRepairOrderMapper.java
/** 查询设备在统计窗口内已完成的维修工单（供 MtbfCalculator 计算 MTBF/MTTR） */
default List<EamRepairOrderDO> selectDoneList(Long assetId, LocalDateTime windowStart, LocalDateTime windowEnd) {
    return selectList(new LambdaQueryWrapperX<EamRepairOrderDO>()
            .eq(EamRepairOrderDO::getAssetId, assetId)
            .eq(EamRepairOrderDO::getStatus, EamRepairStatus.DONE.getCode())
            .between(EamRepairOrderDO::getFinishTime, windowStart, windowEnd)
            .eq(EamRepairOrderDO::getDeleted, false)
            .orderByAsc(EamRepairOrderDO::getFinishTime));
}
```

四个条件各有职责。`assetId` 限定设备；`status = DONE` 落实"只统计闭环工单"；`finishTime between` 用**完工时间**定位窗口；`deleted = false` 是软删除的标准过滤——被取消后逻辑删除的工单不进统计。

其中最有争议的是第三个：为什么用完工时间，不用报修时间？一张 10 月 31 日报修、11 月 2 日修完的单，算 11 月的故障还是 10 月的？我们的选择是"以修好为准"，算 11 月。理由是**指标的用途是评估"这个周期内设备的可靠性表现"**，而"修好"才是一次故障事件的闭环点。用报修时间定位，会出现"10 月报修、11 月才修完"的单被算进 10 月，导致 10 月的维修时长虚高、11 月虚低——统计上一年的 12 个自然月，数字会在月份之间跳来跳去。

这个选择有固有代价：一张修了三周的单，完工落在哪个窗口就全算进哪个窗口，导致那个窗口 MTTR 暴涨、上个窗口 MTBF 虚高。这是按 finishTime 定位的必然结果，换成 startTime 只是把问题搬家。我的态度是接受它、标注它，**不要试图"均摊"**——把维修时长按天摊到两个窗口，算出来的平滑曲线反而掩盖了真实的维修压力。

Service 层只有一行实质调用，没有任何加工：

```java
// service/repairorder/EamRepairOrderServiceImpl.java
@Override
public MetricsResult calcMetrics(Long assetId, LocalDateTime windowStart, LocalDateTime windowEnd) {
    // 只取窗口内已完成的工单：进行中的工单维修时长未定，纳入会虚增维修时长
    List<EamRepairOrderDO> doneOrders = repairOrderMapper.selectDoneList(assetId, windowStart, windowEnd);
    return MtbfCalculator.calc(assetId, doneOrders, windowStart, windowEnd);
}
```

**口径全部集中在 SQL 和计算器两处，没有第三处能偷偷改数字**——这是指标类代码的纪律。我见过太多项目在 Controller 里"顺手"四舍五入、在 VO 里"顺手"乘个系数，最后看板、报表、导出三个数对不上，查半天才发现口径散在三层。指标代码的正确性不取决于算法多聪明，取决于**口径有没有第二个出口**。

对外接口挂在维修工单 Controller 上，因为指标是"维修工单数据的派生视图"，不值得单开一个 Controller：

```java
// controller/admin/repairorder/EamRepairOrderController.java
@GetMapping("/metrics")
@Operation(summary = "设备可靠性指标（MTBF/MTTR，单位小时；0 故障返回 null）")
public CommonResult<MetricsResult> metrics(
        @RequestParam("assetId") Long assetId,
        @RequestParam("windowStart") @DateTimeFormat(iso = DateTimeFormat.ISO.DATE_TIME) LocalDateTime windowStart,
        @RequestParam("windowEnd") @DateTimeFormat(iso = DateTimeFormat.ISO.DATE_TIME) LocalDateTime windowEnd) {
    return success(repairOrderService.calcMetrics(assetId, windowStart, windowEnd));
}
```

参数用 `LocalDateTime` 加 ISO 格式，前端传 `2026-01-01T00:00:00`，不带时区。这个选择在本地开发时毫无问题，在 UTC 服务器上会出大问题——时区这件事我在第九章专门讲，它让保养扫描提前一天出了单，也让指标窗口整体偏了 8 小时。

## 六、把三台设备算一遍：数据自己会说话

做完接口，我做的第一件事不是接前端，而是把王主任厂里三台主力设备的一年数据跑了一遍。窗口取 2026-01-01 00:00 到 2027-01-01 00:00，共 8760 小时。数据来自维修班的纸质记录补录，我按"两次保养之间"的口径核对过一遍工单。

| 设备 | 故障次数 | 维修总时长（h） | MTBF（h） | MTTR（h） | 可用率 |
|------|---------|---------------|----------|----------|--------|
| EQ-CNC-001 数控车床 | 2 | 16 | 4372 | 8 | 99.82% |
| EQ-CNC-002 加工中心 | 3 | 36 | 2908 | 12 | 99.59% |
| EQ-INJ-001 注塑机 | 5 | 2760 | 1200 | 552 | 68.49% |

注塑机这 2760 小时维修时长是怎么来的？五次故障里，四次是液压/加热圈/机械手之类的小毛病，每次 8 到 16 小时；**一次是伺服电机烧了，等进口件等了 2616 小时（109 天），换上只用了 4 小时**。2760 = 2616 + 144。

算一遍：MTBF = (8760 − 2760) ÷ 5 = 1200 小时；MTTR = 2760 ÷ 5 = 552 小时；可用率 = 1200 ÷ (1200 + 552) = 68.49%。这三个数放在一起，画面就非常清楚了——**这台机一年里有 31.5% 的时间是不可用的，而它的设计 MTBF 是 8000 小时，实际只有设计值的 15%**。

但真正有价值的不是"它很差"这个结论，而是**差在哪**。如果只看 MTTR = 552 小时，会得出"维修能力太差"的错误判断；拆开看，四次小修平均 36 小时，是正常水平，问题全在那一次 109 天的等件。所以根因不是"修得慢"，是**关键备件没有库存、进口件采购周期失控**。

这张表直接改变了预算会的结论。原本要批的是 86 万换整机，最后批的是 8 万——换伺服电机 + 建关键备件安全库存（电机、驱动器各备一套）。厂长说的原话是："**原来不是机器不行，是我们让它趴在那儿等件。**"这就是指标的价值：它不直接给答案，它把"我觉得这台机老坏"翻译成"这台机 31.5% 的时间不可用，其中 95% 的不可用来自一次等件"——后面这个句子，才能支撑一个具体的、金额正确的决策。

顺带说一句另外两台设备。数控车床 MTBF 4372 小时、可用率 99.82%，是全厂最好的；加工中心 MTBF 2908 小时，也不算差，但它的三次故障里有两次是刀库定位不准，属于同一个根因反复发作。这类"同一根因反复"的设备，MTBF 看着还行，实际上是最该做根因分析（RCA）的——**指标负责排序，根因分析负责开药**，两件事不能互相替代。

## 七、MTBF 的陷阱：为什么各部门能算出三个数

指标上线一个月，我就发现一个比算法更难解决的问题：**同一个公式，各部门算出来的数不一样，而且每个人都认为自己是对的**。这一节把常见的四种陷阱列清楚，它们比代码 bug 更常见，也更难修。

**陷阱一：统计窗口不一致。** 生产部看"最近 30 天"，财务看自然月，设备科看季度。同一台注塑机，最近 30 天一次没坏，MTBF 是 null（显示"—"）；自然月里坏了一次，MTBF 是 700 多小时；季度里坏了三次，MTBF 掉到 900 小时。三个数都"对"，但放在同一张会上就是吵架。解法只有一个：**全系统只允许一种窗口口径，并在页面标题上写明**。我们最后定的是"自然月 + 年度累计"两档，前端切换，接口不提供任意窗口给业务人员用——任意窗口留给运维排查，不给业务看。

**陷阱二：维修记录不完整，MTBF 虚高。** 这是最隐蔽的一种。维修班有个习惯：小毛病顺手修了，不报修、不开单。漏报一次故障，分母少 1，分子里的"维修时长"也少几小时，MTBF 直接往上跳。一台真实 MTBF 1200 小时的设备，如果一半的小故障没开单，算出来能到 2400 小时——**看板上它从"该换"变成了"还行"**。这不是算法能解决的问题，只能靠流程：要么把"报修开单"变成领备件的前置条件（第十章讲的第三次翻车就是这个思路），要么定期用备件出库流水反查"有领料无工单"的记录。

**陷阱三：未闭环工单被漏掉。** 一张修了两个月还没验收的单，既不进故障次数，也不进维修时长，等于从统计里消失。设备科看到的是"今年只坏了两次"，实际是"两次修完了，还有一次挂着"。这会同时虚增 MTBF、压低 MTTR，制造出一台"看起来很好"的设备。商用版必须在指标旁边加一个"超期未闭环工单数"，逼流程闭环——**指标的可信度，取决于流程的闭环率**。

**陷阱四：把指标当考核大棒。** 这条不是技术问题，是管理问题，但影响最大。MTBF/MTTR 一旦和维修班绩效硬挂钩，维修班会立刻找到"优化"办法：轻症不报修、完工压着不验收、把一次维修拆成两张单。指标是给你"找问题设备"的，不是给你"考核人"的。我的建议一直是：**先跑半年数据、把流程跑顺，再谈考核**，顺序反了，数据就废了。

还有一个纯统计的坑要提一句：**小样本的 MTBF 方差极大**。一台设备窗口内只坏了 1 次，MTBF 就是"窗口时长减维修时长"，这个数几乎等于窗口长度，没有任何统计意义。所以 `MetricsResult` 里那个 `faultCount` 必须跟着一起展示——故障次数小于 3 的设备，MTBF 只能当参考，不能拿来排序做决策。这也是我在第六节那张表里坚持把"故障次数"放在第二列的原因：**先看样本量，再看指标值**。

## 八、从单台到类别，从 MTBF 到 OEE：这套指标的延长线

单台设备的 MTBF 解决的是"这台该不该修/换"，但厂长真正关心的是"我们厂的设备整体靠不靠谱"。所以这套指标天然有两条延长线。

**第一条：从单台聚合到设备类别。** 注塑车间 12 台注塑机，单看每台的 MTBF 排序意义不大（有的设备新、有的老），要看的是"注塑这一类设备的平均 MTBF"。这里有个必须避开的坑：**不能对 MTBF 求算术平均**。正确做法是把分子分母分别加总再相除：

```sql
-- 类别级 MTBF：先加总无故障时长与故障次数，再相除（不是 AVG(mtbf)）
SELECT a.category,
       SUM(EXTRACT(EPOCH FROM (r.finish_time - r.start_time)) / 3600.0) AS repair_hours,
       COUNT(*)                                                     AS fault_count
FROM eam_repair_order r
JOIN eam_asset a ON a.id = r.asset_id
WHERE r.status = 5 AND r.deleted = FALSE
  AND r.finish_time >= :windowStart AND r.finish_time < :windowEnd
GROUP BY a.category;
```

拿这条 SQL 的结果再套一次 `MtbfCalculator` 的公式（窗口时长换成"设备台数 × 窗口时长"），得到的才是类别级 MTBF。直接 `AVG(单台 MTBF)` 会让一台零故障设备的 null 或超大值把整类拉飞——**平均的平均，是统计里最常见的错误**。

**第二条：从 MTBF 到 OEE。** MTBF 只回答"可靠性"，不回答"效率"。设备没坏，但开开停停、速度上不去、做出来是废品，一样不产出。设备综合效率 OEE 是三个因子的乘积：

| 因子 | 含义 | 数据来源 | 和 EAM 的关系 |
|------|------|---------|--------------|
| 可用率 Availability | 计划时间里有多少时间真在跑 | EAM 维修工单 + 停机记录 | 就是 MTBF/(MTBF+MTTR) 的另一种算法 |
| 性能 Performance | 实际节拍 ÷ 理论节拍 | SCADA / MES 报工 | EAM 不采集，只做关联 |
| 合格率 Quality | 合格数 ÷ 总产出 | QMS / MES | EAM 不判定，只做关联 |

注意第二、三行的"不采集"——这是边界。EAM 能提供的是可用率这一块，性能和质量分别在 SCADA/MES 和 QMS 里，硬塞进 EAM 会让它变成一个什么都管、什么都管不准的怪物。我在第十章会再讲一次这个边界。商用版里我做的是一个"OEE 拼装接口"：EAM 出可用率，从 MES 拉性能和合格率，拼成一张 OEE 看板，数据不落地——**拼装是集成层的事，不是内核的事**。

**第三条延长线：从人工统计到 IoT 自动采集。** 现在 MTBF 依赖维修工单，工单依赖人填。如果设备接了 SCADA，停机时长可以从 PLC 的运行信号里自动算出来，不依赖任何人报修：

```text
MTBF 自动口径 = Σ(两次停机之间的运行时长) ÷ 停机次数
停机判定 = 运行信号为 0 且持续 > 10 分钟（避免正常换模/待料误判）
```

这条路的诱惑很大，但有个前提必须先做：**停机的分类**。SCADA 只知道"停了"，不知道是故障停、待料停、换模停还是计划停机。不分类直接算 MTBF，会把所有计划停机都算成故障，指标立刻失真。所以我在给客户的方案里，永远是先上 EAM 的工单闭环、把"故障停机"这个语义沉淀下来，再考虑接 SCADA 做自动采集——**先有语义，再有自动化**，顺序反了就是花钱买一堆噪声。

## 九、商用化检查清单（可靠性指标版）

- 0 故障设备返回 null 还是 0？前端是否显示 "—" 而不是 0？中间层有没有"顺手兜底"？
- `faultCount` 是否和 MTBF/MTTR 并排展示？故障次数小于 3 的设备是否标注"样本不足"？
- 统计窗口口径（自然月 / 年度累计 / 滚动 30 天）全系统统一了吗？页面标题写明了吗？
- 维修时长取的是 `startTime → finishTime`，等件时间被排除了——这个口径向客户解释过吗？要不要加停机记录表补全？
- 只统计 status=DONE 的口径，客户认吗？"超期未闭环工单数"有没有单独展示？
- 缺 start/finish 时间的脏工单占比查过吗？跳过口径会不会让 MTTR 系统性偏低？
- 类别级 MTBF 是加总后再除，还是错误地 `AVG(单台 MTBF)`？
- 指标有没有被拿去直接做班组考核？造假的路径（漏报、压单、拆单）堵了吗？
- 如果接 SCADA 自动算停机，停机分类（故障/待料/换模/计划）定义了吗？

## 十、下一章预告：账上有 230 台，车间只有 187 台

指标算得再准，也得有"设备"这个主体。这一章所有数字的前提是：每台设备在系统里有一条唯一的、状态正确的台账记录。而现实是——王主任厂里年中盘点，账上 230 台，车间实际只有 187 台对得上，另外 12 台在车间里干活但系统里根本没有，还有 43 台是"幽灵"：报废没销账、重复录入、借出去没还。

下一章讲设备状态流转与台账治理：为什么"停机"和"维修中"必须分成两个状态（它直接影响这一章 MTBF 的口径）、报废为什么不能删记录只能改状态、`attributes` 这个 JSONB 字段到底存什么、以及我用扫码枪和三条 SQL 把账实相符率从 81% 拉到 100% 的全过程。
