# 商用上线与复盘：客户现场的三次翻车

## 一、场景：一个 200 台设备的汽配厂，上线三个月

这家客户是做汽车内饰件的，两条注塑线、一条喷涂线、一条装配线，设备台账 200 台出头。老板拍板上 EAM 的理由很实在：去年一年非计划停机损失了一百多万，他要知道钱花在哪、下次该先修哪台。

项目上线三个月，系统跑起来了，数据也进来了，但中间翻了三次车。三次都不是"代码写错了"，而是**我以为业务会这样用，业务偏偏那样用**。这一章不复述功能，只复盘这三次翻车：现象、根因、修法，以及修完之后客户拿到的三个真实数字。

先把三次翻车摆出来，让后面的复盘有个坐标：

| 次序 | 现象 | 根因一句话 | 修复方向 |
|------|------|-----------|---------|
| 第一次（上线第 9 天） | 一天生成 47 张保养工单 | 47 条计划的 `nextMaintainTime` 停在三个月前，"到期就出单"把欠账全补了 | 扫描只出当期一张，欠账走"逾期清单" |
| 第二次（上线第 5 周） | 200 张维修工单堆着没人派 | 派工全靠调度员手动点，没人点就躺着 | 超 4 小时未派工自动升级提醒 |
| 第三次（上线第 2 个月） | 备件账实不符，差 49 个 | 师傅领料口头说一声就走，没有单据 | 出库必须扫工单号，无单不给料 |

三次翻车有个共同点：**系统本身没坏，是"规则只写在 SOP 里、没写进代码"**。这一章最后会把这条总结成三条经验，但先一个一个讲。

## 二、翻车一：保养工单一天生成了 47 张

上线第 9 天早上，维修班长老魏给我打电话，语气不太好："你们这个系统，一晚上给我下了 47 张保养单，我全班 6 个人，一天做 8 张就到顶了。这是要干嘛？"

我打开后台一看，47 张单，工单号从 `MO-20260812-101` 排到 `MO-20260812-147`，全是当天生成、全是"待执行"状态，计划日期清一色是 **2026-07-15**。

### 2.1 现场到底发生了什么

追下去，原因很朴素：客户上线时用 Excel 批量导入了 187 条保养计划。导入模板里"下次保养时间"那一列，我留了一个示例值 `2026-07-15`，客户填表的人**只填了自己要填的列，示例值没删**。于是 47 条计划的 `nextMaintainTime` 全部停在 7 月 15 日，而系统上线是 8 月 3 日——等到 8 月 12 日第一次扫描，这 47 条全都是"逾期三个月"。

再看引擎怎么处理这种逾期。`MaintainPlanEngine` 的判定只有三步：

```java
// framework/eam/maintain/MaintainPlanEngine.java（节选）
// 2. 判定：nextMaintainTime - advanceDays 是否已进入今天（提前窗口）
int advanceDays = plan.getAdvanceDays() != null ? plan.getAdvanceDays() : 0;
LocalDate triggerDate = plan.getNextMaintainTime().toLocalDate().minusDays(advanceDays);
if (triggerDate.isAfter(today)) {
    continue; // 还没到出工单的时机
}
// 3. 生成工单：工单号 "MO-yyyyMMdd-planId"，同一天同一计划只会出一张
EamMaintainOrderDO order = new EamMaintainOrderDO();
order.setOrderNo("MO-" + today.format(ORDER_NO_DATE) + "-" + plan.getId());
order.setPlanDate(plan.getNextMaintainTime().toLocalDate());
order.setStatus(EamMaintainOrderStatus.PENDING.getCode());
// 4. 推进计划：last=原 next，next=按周期滑到下一窗口
LocalDateTime base = plan.getNextMaintainTime();
plan.setLastMaintainTime(base);
plan.setNextMaintainTime(NextDateCalculator.next(cycleType, plan.getCycleValue(), base));
```

引擎的语义是"**到期就出单，出完推进一个周期**"。这个语义在"每天扫描、每天只落后一个周期"的理想状态下是对的。但它没有回答一个问题：**如果一条计划落后了 3 个周期呢？**

单看一台设备、一条计划，仓库版引擎的行为是：8 月 12 日出 1 张，`next` 从 7-15 推到 8-15；8 月 13 日扫描，`triggerDate = 8-15 - 提前天数`，可能还在未来，于是停；等到 9 月上旬再出第 2 张。**它不会一次出 47 张，但它会在接下来两个月里，持续不断地给这台设备补"历史欠账"的工单**——一台设备欠 3 个月，就是 3 张单，分散在 3 个时间点，每张单的计划日期都是过去的。

而客户现场的 47 张，是"47 条计划各欠 3 个月"——每条计划出 1 张，加起来 47 张。**这不是"补了三个月的账"，是 47 条脏计划在同一晚集体触发。** 我在复盘会上把这句话说清楚的时候，客户设备科长老赵愣了一下："所以不是系统算错了，是我们导进去的日期错了？"我说："日期是你们填错的，但系统不该在发现 47 条计划同时逾期三个月时，一声不吭地全出单。"

### 2.2 为什么"到期就出单"在商用场景下不够

这一条值得单独讲，因为它是这一章最重要的一课。

我的引擎设计里有一个隐含假设：**扫描会稳定地每天跑，计划最多落后一个周期**。这个假设在我的开发机上永远成立——我每天手动点一次，看到的是"每天推进一步"的优雅节奏。但在客户现场，这个假设有三个破口：

**破口一：系统会停。** 客户机房断电、升级、搬迁，扫描停了 10 天，10 天里到期的计划全部欠账。恢复后第一天，全部触发。

**破口二：数据会脏。** 批量导入、历史迁移、手工补录，都可能写进一个"很久以前"的 `nextMaintainTime`。引擎不知道这个日期是"真的欠了三个月"还是"填错了"，它只会照章办事。

**破口三：业务会改。** 客户把某台设备停用改造了两个月，计划的 `status` 忘了停用（或者停了又恢复），`nextMaintainTime` 就冻在两个月前。等设备重新投产，这笔账就浮出来了。

三个破口指向同一个设计缺陷：**"到期"和"欠账"被当成了同一件事**。到期是该出单，欠账是该有人看一眼再决定——把两者混在一起，系统就会在异常数据上表现得"特别勤奋"。

### 2.3 修法：扫描只出当期一张，欠账走逾期清单

修复的核心是把"当期"和"历史"分开。判定条件从"`triggerDate <= today`"改成"**`triggerDate` 落在当期窗口内**"：

```java
// 商用补法（示意，仓库当前版本未内置逾期判定）
LocalDate planDate = plan.getNextMaintainTime().toLocalDate();
LocalDate triggerDate = planDate.minusDays(advanceDays);
if (triggerDate.isAfter(today)) {
    continue;                       // 未到窗口，不出单
}
// 逾期判定：计划日期已经落后超过一个周期，属于"历史欠账"，不补单，进逾期清单
LocalDate nextPlanDate = NextDateCalculator.next(cycleType, plan.getCycleValue(),
        plan.getNextMaintainTime()).toLocalDate();
if (planDate.isBefore(today) && !nextPlanDate.isAfter(today)) {
    overdueList.add(plan);          // 只登记，不出单；由人确认后"手工补一张"或"直接跳过"
    continue;
}
// 当期：出且只出一张，然后把 next 一次性对齐到"今天之后"，不做逐周期追赶
EamMaintainOrderDO order = buildOrder(plan, planDate, today);
plan.setLastMaintainTime(plan.getNextMaintainTime());
LocalDateTime next = plan.getNextMaintainTime();
do {
    next = NextDateCalculator.next(cycleType, plan.getCycleValue(), next);
} while (!next.toLocalDate().isAfter(today));
plan.setNextMaintainTime(next);
```

三段逻辑，三个决定。

**第一段：逾期不补单。** 判定条件是"计划日期在过去，且下一个周期也已经在今天之前"——意思是它已经欠了不止一期。这种计划不进工单流，进逾期清单。为什么？因为**工单是给维修班派活的，不是给系统记账的**。一张计划日期是三个月前的工单，派下去也没人知道该按哪天的标准做，做完了 `lastMaintainTime` 该写哪天也说不清。**历史欠账的正确处理是"承认它欠了、记在账上、由人决定补不补"，不是"假装它今天到期"。**

**第二段：当期只出一张。** 对正常到期的计划，出单后把 `next` 一次性对齐到"今天之后"，而不是只推一个周期。这一步很关键：如果只推一个周期（从 7-15 推到 8-15），8-15 依然在过去，第二天扫描又会命中——**连续 30 天每天出一张**，正是我在第 2.1 节说的"分散在两个月里的慢性灾难"。`do-while` 一次推到位，把追赶变成对齐。

**第三段：逾期清单是给人看的。** 清单长这样：

```sql
-- 逾期清单：计划已落后超过一期，且当前没有未完成的工单
SELECT p.plan_no, a.asset_no, a.name, p.next_maintain_time,
       CURRENT_DATE - p.next_maintain_time::date AS overdue_days,
       (SELECT COUNT(*) FROM eam_maintain_order o
         WHERE o.plan_id = p.id AND o.status IN (1, 2) AND o.deleted = FALSE) AS open_orders
FROM eam_maintain_plan p
JOIN eam_asset a ON a.id = p.asset_id
WHERE p.status = 1 AND p.deleted = FALSE
  AND p.next_maintain_time < CURRENT_DATE - INTERVAL '1 day'
ORDER BY overdue_days DESC;
```

清单页面上每行有两个按钮："补一张（今天做）"和"跳过这期（对齐到今天）"。两个动作都会留下操作人和时间——**欠账是业务事实，系统不能替你决定补不补，但必须把"谁决定的、什么时候决定的"记下来**。

另外加了一道熔断：单次扫描生成的工单数超过阈值（比如 20 张）就**只出前 20 张，其余进逾期清单，并发一条告警**。理由很直白：一次扫描出 47 张单，不管是数据脏还是业务真的到期，都说明有异常，先停下来让人看一眼，比"勤勤恳恳地错"强。**批处理系统要有"刹车"，不能只有油门。**

这次修完，47 张单被作废了 46 张（保留一张当"当期"），47 条计划的日期重新对齐。老魏后来的评价是："早这么干，我那 6 个人就不用白跑两天。"

## 三、翻车二：200 张维修工单堆着没人派

第二次翻车没那么响，但更伤。上线第 5 周，老赵拿着一份清单来找我："系统里 200 张维修单挂着'待派工'，最老的一张是 11 天前的。设备坏了不修，这个系统上了有什么用？"

### 3.1 派工这件事，系统没有推着人走

看数据就明白了：200 张待派工单，分布在 47 个报修人身上，最老的 11 天。而调度员只有一个，姓孙，那段时间他请了 5 天假，回来之后又赶上月底盘库，工单就那么堆着。

系统的设计是"**报修 → 调度员派工 → 维修 → 验收**"，中间那个"派工"是纯人工动作：调度员打开列表，一张一张点，选维修工，提交。系统不提醒、不催办、不上报，**它只是安静地把 200 张单排在那儿**。

这是我在做需求时的一个默认假设：**"有人会一直盯着列表"**。这个假设在 demo 里成立（我在演示时天天打开），在现场不成立（调度员会请假、会忙别的、会以为"别人会看"）。而维修工单的时效性很强——设备停一天就是一天的产能损失，堆 11 天，等于这台设备半个月没产出。

更糟的是"没人知道自己该管"。报修的人以为调度会派，调度以为班组长会催，班组长以为设备科在盯。**工单在系统里是"有主的"，在组织里是"无主的"。**

### 3.2 修法：把"超时"变成一个会叫的事件

修复思路是把"盯着列表"这个人的职责，换成"系统定时检查 + 自动升级"。规则定得很简单：**创建后 4 小时未派工，提醒班组长；8 小时未派工，提醒设备科长。**

先写查询。三个条件：状态是待派工、创建时间超过阈值、没有未关闭的提醒记录（防重复轰炸）：

```sql
-- 超时未派工：status=1 且创建超过 4 小时
SELECT r.id, r.order_no, a.asset_no, a.name AS asset_name,
       r.priority, r.create_time,
       EXTRACT(EPOCH FROM (NOW() - r.create_time)) / 3600 AS waiting_hours
FROM eam_repair_order r
JOIN eam_asset a ON a.id = r.asset_id
WHERE r.status = 1              -- 待派工
  AND r.deleted = FALSE
  AND r.create_time < NOW() - INTERVAL '4 hours'
ORDER BY r.priority DESC, r.create_time ASC;
```

然后是定时任务。这里刻意用"扫描 + 判断"而不是"报修时延时消息"，因为**延时消息在服务重启、消息丢投时会失效，而扫描是可重入的**——这一点和第八章讲的"生成类任务用唯一索引兜底"是同一个思路：**状态放在数据库里，比放在消息队列的延迟队列里可靠**。

```java
// 商用补法：job/EamRepairOrderEscalateJob.java（示意）
@Component("eamRepairOrderEscalateJob")
@RequiredArgsConstructor
public class EamRepairOrderEscalateJob implements JobHandler {

    private final EamRepairOrderMapper repairOrderMapper;
    private final NotifyClient notifyClient;

    @Override
    public String execute(String param) {
        List<EamRepairOrderDO> pending = repairOrderMapper.selectTimeoutPending(4);
        if (pending.isEmpty()) {
            return "无超时未派工工单";
        }
        // 按优先级排序，把"高优先级 + 等得最久"放在消息最前面
        String content = buildDigest(pending);
        notifyClient.sendWebhook(NotifyChannel.WECOM_GROUP, content);
        // 8 小时以上，升级到设备科长（单独一个群）
        List<EamRepairOrderDO> escalated = pending.stream()
                .filter(o -> Duration.between(o.getCreateTime(), LocalDateTime.now()).toHours() >= 8)
                .toList();
        if (!escalated.isEmpty()) {
            notifyClient.sendWebhook(NotifyChannel.WECOM_MANAGER, buildDigest(escalated));
        }
        return "超时未派工 " + pending.size() + " 张，升级 " + escalated.size() + " 张";
    }
}
```

消息长这样（企微机器人 markdown）：

```text
【EAM 超时未派工提醒】共 5 张工单超过 4 小时未派工
> RO-20260915-031 注塑机-合模异响 优先级:高 已等 9.5 小时
> RO-20260915-044 空压机-压力不足 优先级:中 已等 7.2 小时
> ……
请调度员在今日 17:00 前完成派工，超 8 小时将上报设备科。
```

三个设计细节值得说，它们决定了这条提醒是"有用"还是"招人烦"。

**一是阈值要按优先级分层。** 高优先级 2 小时、中优先级 4 小时、低优先级 8 小时。一刀切 4 小时，会让"低优先级的照明灯坏了"和"高优先级的主机停机"一起轰炸，人很快就会把群消息免打扰——**告警一旦被无视，就等于没有**。

**二是要合并推送，不要一张单一条消息。** 5 张单合并成一条摘要，一天最多推 3 次。逐条推送的结果是刷屏，刷屏的结果是静音。

**三是要有"认领"闭环。** 提醒发出去不算完，得让人能一键点进工单详情去派工。如果消息里只有一个工单号，人还得打开电脑、登录、搜单号，中间每一步都在流失。**通知的价值 = 信息完整度 ÷ 操作步数**，这个比值低到一定程度，通知就是噪声。

### 3.3 修完之后，多了一个指标

这个改动上线后，我顺手加了一个指标：**平均派工时长**（`dispatch_time - create_time`）。它不在最初的 PRD 里，但它比"工单总数"有用得多——工单多说明设备忙，派工慢说明管理卡住了。

| 指标 | 上线前 | 修完 1 个月 | 说明 |
|------|-------|-----------|------|
| 待派工工单峰值 | 200 张 | 11 张 | 超时提醒 + 认领入口 |
| 平均派工时长 | 31 小时 | 2.4 小时 | 从"想起来才派"到"当天派" |
| 超 8 小时未派工 | 78 张/月 | 3 张/月 | 升级机制起效 |

老孙（调度员）后来跟我说了一句挺实在的话："以前我怕漏单，天天上班第一件事就是翻列表；现在系统会叫我，我反而能把精力放在和维修工排班上。"这句话说明一件事：**系统不该替代人做判断，但该替人记住"该做判断了"**。

## 四、翻车三：备件账实不符，差了 49 个

第三次翻车发生在第二个月月底，库管张姐盘完库，拿着单子来找老赵："系统里轴承 6205 有 320 个，我数了三遍，货架上 271 个。差的 49 个，我也不知道去哪了。"

### 4.1 "口头领料"是怎么把账做烂的

我去车间待了半天，看了三次领料，流程都是这样的：师傅走到库房窗口，说"张姐，6205 给我两个"，张姐从货架上拿两个递过去，在本子上记一笔，师傅走了。**全程没有单据，系统里更没有记录。**

为什么会这样？因为系统的出库流程要求"选备件 → 填数量 → 填关联工单号 → 提交"，四个动作。而现场的真实动作是"喊一声、拿件、走人"，一个动作。**系统要求的操作成本，比现场习惯高 4 倍，人就绕过去了。**

更要命的是，绕过去之后没人发现。因为库存是"账"，账少了不影响干活，只有盘点那天才会暴露。而盘点一年两次——意味着**账可以烂半年不被发现**。

### 4.2 `bizOrderNo` 这个字段，本来就是为这个场景设计的

翻代码的时候我挺惭愧的：出库方法的签名里，第三个参数就是 `bizOrderNo`，注释也写了它的用途。

```java
// service/sparepart/EamSparePartServiceImpl.java
/**
 * 出库。库存不足直接抛 1_003_301，不允许扣成负数。
 *
 * 并发取舍：演示仓库先读后写；商用高并发应改原子 SQL
 * UPDATE eam_spare_part SET stock = stock - #{quantity} WHERE id = #{id} AND stock >= #{quantity}，
 * 影响行数为 0 即库存不足，避免两个并发出库都读到旧库存导致超卖。
 */
@Override
@Transactional(rollbackFor = Exception.class)
public EamSparePartDO outbound(Long partId, Integer quantity, String bizOrderNo, String operator) {
    EamSparePartDO part = getSparePart(partId);
    int stock = part.getStock() != null ? part.getStock() : 0;
    if (stock < quantity) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_STOCK_NOT_ENOUGH, stock, quantity);
    }
    part.setStock(stock - quantity);
    sparePartMapper.updateById(part);
    writeRecord(partId, EamSpareRecordType.OUT.getCode(), quantity, bizOrderNo, operator);
    return part;
}
```

`bizOrderNo` 是"业务单号"，出库时必须带上"这次领料是为哪张维修工单/保养工单领的"。这个字段有三个作用，缺一个都不值得设：

**第一，追溯。** 一台设备这个月换了三次轴承，工单号都在流水里，翻开就能看到——这是判断"这台设备是不是有根因问题"的直接证据，也是第六章 MTBF 根因分析的数据来源。

**第二，成本归集。** 维修成本 = 工时 + 备件。没有 `bizOrderNo`，备件成本只能摊到"全厂",有了它，才能算"这台设备一年花了多少钱修"——**这是设备更新决策的关键输入**。

**第三，防漏。** 一张工单能领多少件、领了什么，工单详情页一拉就清楚。没有这个字段，领料和工单是两条平行线，永远对不上。

那么问题来了：字段有了，为什么没起作用？因为**它是可空的，而且没有任何校验**。前端表单不填也能提交，接口传 null 也不报错。一个"设计上很重要、实现上可选"的字段，在现场等于不存在。

### 4.3 修法：出库必须扫工单号，无单不给料

修复分三步，从"技术上可选"变成"业务上不可能绕过"。

**第一步：`bizOrderNo` 必填，且必须是一张真实存在的、未关闭的工单。**

```java
// 商用补法（示意，仓库当前版本未校验 bizOrderNo）
private void validateBizOrderNo(String bizOrderNo) {
    if (StrUtil.isBlank(bizOrderNo)) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_SPARE_ORDER_NO_REQUIRED);   // 1_003_302
    }
    EamRepairOrderDO repair = repairOrderMapper.selectByOrderNo(bizOrderNo);
    EamMaintainOrderDO maintain = repair == null ? maintainOrderMapper.selectByOrderNo(bizOrderNo) : null;
    if (repair == null && maintain == null) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_SPARE_ORDER_NOT_EXISTS, bizOrderNo);
    }
    // 只允许给"已派工/维修中/执行中"的工单领料；待派工的还没人干，领料没有依据
    Integer status = repair != null ? repair.getStatus() : maintain.getStatus();
    if (!ALLOW_OUTBOUND_STATUS.contains(status)) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_SPARE_ORDER_STATUS_INVALID, bizOrderNo);
    }
}
```

然后在 `outbound` 的第一行调用它。注意状态白名单：待派工的工单不允许领料——因为还没派工，谁去修、修什么都不知道，这时候领料大概率是"先备着"，而"先备着"就是呆滞库存的源头。

**第二步：把"填单号"变成"扫单号"。** 这是让现场愿意用的关键。要求师傅打开手机扫工单二维码，`bizOrderNo` 自动带入；PC 端也一样，扫码枪扫一下就行。**从"四个动作"降到"一个动作"，人才不会绕过去。** 这一条比第一条更重要——第一条是"不许绕"，第二条是"不用绕"。

**第三步：把"账实相符率"做成月度指标。** 每月抽盘 20% 的备件，算 `相符条目数 / 抽盘条目数`，和上个月对比。这个指标一上墙，库管张姐自己就会去追那些"领了没扫"的记录——**指标的作用不是考核，是让问题有一个固定的暴露窗口**。

### 4.4 修完的账

| 项目 | 修前 | 修后 3 个月 | 说明 |
|------|------|-----------|------|
| 系统库存 vs 实盘 | 320 / 271（差 49） | 相符率 98.4% | 剩 4 条历史差异挂"待核销" |
| 出库单据完整率 | 约 62% | 100% | 无单号无法提交 |
| 备件呆滞金额占比 | 23% | 18.9% | 有单可查后，重复采购减少 |
| 单台设备维修成本 | 不可算 | 可算 | 工时 + 备件归集到 `bizOrderNo` |

那张"320 vs 271"的差异，最后查出来 41 个是"口头领料没记录"、8 个是"入库时数量录错"。41 个里有一部分是正常的维修消耗，只是没记；另一部分是领了没用、放在工具箱里——**这部分就是典型的"影子库存"，账上没有、车间里到处是，采购还在继续买**。这也解释了为什么备件呆滞库存能降下来：不是买得少了，是"买了不知道在哪、又买一遍"的情况少了。

## 五、客户算出来的三个数字

三个月验收，老赵在验收会上给了三个数，我完整记了下来：

| 指标 | 上线前 | 上线 3 个月 | 变化 | 口径 |
|------|-------|-----------|------|------|
| 保养计划执行率 | 40% | 92% | +52pp | 按期完成的保养工单 ÷ 应完成工单（含提前量窗口） |
| 非计划停机时长 | 基线 100% | 65% | −35% | 维修工单 `startTime→finishTime` 累加 + 停机记录 |
| 备件呆滞库存 | 100% | 82% | −18% | 12 个月无出库的备件金额 ÷ 备件总金额 |

这三个数字我特意核过口径，因为它们最容易被"算得好看"。

**保养执行率 40% → 92%** 的分母是"应完成工单"，不是"已生成工单"。如果按后者算，系统自己生成的单自己闭环，执行率当然高，那是自欺欺人。真正的分母来自计划：这个月到期多少条计划，就该有多少张工单，完成了多少张。上线前没有系统，这个数靠人工统计，40% 是维修班自己估的，可能还偏乐观——因为纸质记录里"做了但没记"和"记了但没做"都分不清。

**非计划停机时长 −35%** 的口径是维修工单的 `startTime→finishTime` 加上停机记录。这个口径有水分（等件时间不在里面，第六章讲过），但**同一个口径前后对比是有意义的**：变化来自两件事，一是保养按计划做了，小故障少了；二是派工从 31 小时压到 2.4 小时，同样的故障，趴着的时间短了。第二件事的贡献其实比第一件大，这也是我后来在所有项目里都强调"派工时效"的原因。

**备件呆滞库存 −18%** 这个数最实在，因为它直接对应现金。张姐的原话是："以前买轴承都是一箱一箱买，反正不知道还剩多少；现在一查就知道还有 87 个，够用两个月，不买了。"

## 六、三条经验

三次翻车，三条经验，每一条都是被现场打出来的。

**第一条：业务规则要写进代码，不要写在 SOP 里。**

我们交付时给客户的《设备管理制度》里写着"领料必须登记工单号"、"工单必须在 4 小时内派工"、"逾期三个月的计划要重新评估"。这三条都写在纸上，贴在墙上，一条都没执行。为什么？因为**SOP 没有执行力，代码有**。

写进代码的意思是：不填单号，提交按钮点不动；超过 4 小时，消息自己会发出去；逾期超过一期，扫描不会替你出单。规则一旦变成"系统不让你这么干"，执行率就是 100%，不需要任何人盯。反过来，规则只写在制度里，执行率取决于"这个月谁在管"，而人是最不可靠的一环。

这一条还有个推论：**能被绕过的校验，等于没有校验**。`bizOrderNo` 可空、`status` 可以随便改、报废设备可以改回运行——这些都是"写在代码里的 SOP"，看着有，实际没有。

**第二条：数据口径先对齐，再开发。**

第六章讲的 MTBF 口径之争，第七章的"账实相符率怎么算"，这一章的"执行率分母是什么"，三次争论都发生在**开发之后**，而且每次都要返工。

正确的顺序是：先拿一张纸，把指标的定义、分子、分母、时间窗口、数据来源写清楚，让业务方签字，再写代码。口径没对齐就开发，等于用精确的代码算一个没人认可的数——**算得再准，也是白算**。

我现在的做法是每个项目启动时先做一张"指标口径表"，一页纸，五行：指标名、公式、分子、分母、数据来源。这张纸比任何 PRD 都重要，因为它是后面所有争议的裁判。

**第三条：先跑通一条完整的设备生命周期，比铺满功能重要。**

上线前我的功能清单有 14 项：台账、保养计划、保养工单、维修工单、备件出入库、备件预警、MTBF、MTTR、看板、导入导出、移动端、扫码、审批流、报表。三个月下来，真正被用起来的只有 6 项。

而客户真正感知到价值的，是**一条完整的链路**：设备在台账里 → 计划到期出保养单 → 保养发现异常转维修单 → 维修领备件（带工单号）→ 验收完成 → 工时和备件归集到设备 → MTBF 和成本能算出来。这条链路走通了，客户就会用；链路断在任何一环（比如领料不带单号），后面的指标全是假的。

所以如果重来一次，我会先只做这条链路，把每一环的数据都做实，再谈看板和报表。**功能的宽度不产生价值，链路的完整度才产生价值。** 铺满 14 个功能、每个都半截，不如 6 个功能串成一条能跑通的线。

## 七、全系列回顾：三个引擎、两张表、一个决策

十篇文章写下来，这套 EAM 的内核其实很小。把它压缩成一张表：

| 内核 | 类 / 机制 | 解决的问题 | 关键设计 | 相关章节 |
|------|----------|-----------|---------|---------|
| 计划引擎 | `MaintainPlanEngine` + `NextDateCalculator` | 计划到期自动出单、周期推进 | 纯函数、不落库、注入 `today` 可测 | 第 3、4、10 章 |
| 状态机 | `RepairOrderStateMachine` | 工单只能按合法路径流转 | 迁移表 + `assertTransit`，非法即抛 | 第 5、8 章 |
| 指标引擎 | `MtbfCalculator` + `MetricsResult` | 把维修记录变成可靠性指标 | 无状态、0 故障返回 null、窗口由调用方定 | 第 6 章 |
| 台账 | `EamAssetStatus` + `attributes` JSONB | 四个状态、异构参数 | 状态有语义、报废不删记录、JSONB 免扩展表 | 第 7 章 |
| 并发 | `@Version` + 唯一索引 + 单号幂等 | 重复派工、重复出单 | 乐观锁兜版本、唯一索引兜重复 | 第 8 章 |

五条里，三条是"引擎"（计划、状态机、指标），两条是"约束"（台账语义、并发控制）。引擎负责"把业务规则算出来"，约束负责"让错误的数据进不来"。**这两类东西缺一类，系统都会在半年后变成一堆没人信的数据。**

再说"两张核心表"。整套系统的数据其实就围绕两张表：

- **`eam_asset`**：设备是谁、在哪、什么状态、有什么参数。它是所有业务的主语。
- **`eam_repair_order`**：设备坏过几次、谁修的、修了多久、花了什么件。它是所有指标的事实来源。

`eam_maintain_plan`、`eam_maintain_order`、`eam_spare_part`、`eam_spare_record` 都是围绕这两张表长出来的：计划是"预防维修"，维修单是"故障维修"，备件流水是"维修的成本明细"。**主数据 + 事实表，是所有工业软件的共同骨架**——SCADA 是"点位 + 时序值"，QMS 是"检验项 + 检验记录"，APS 是"工序 + 排产结果"。想清楚哪两张表是骨架，剩下的都是枝叶。

最后是"一个复用决策"。这套 EAM 的脚手架直接复用了芋道（ruoyi-vue-pro）：权限、菜单、字典、多租户、代码生成、MyBatis-Plus 插件链、定时任务，全是现成的。我真正写的只有 61 个文件：DO、Mapper、Service、Controller、三个引擎、一份 DDL。**复用不是偷懒，是把时间花在只有这个业务才需要的地方。**

但复用有一个前提：**算法自己写**。保养周期推进、状态机、MTBF，这三个东西一行第三方库都没引，全用 `java.time` 和 `Map` 手写。理由不是"炫技"，是它们承载的是业务规则——业务规则必须能被读懂、能被改、能被单测覆盖。引入一个"通用规则引擎"，最后所有人都在学那个引擎，没人知道业务规则长什么样了。

## 八、后面还能做什么

这套系统在客户那里跑稳之后，老赵问过我"下一步能加什么"。我说了三个方向，按投入产出排序。

**第一，扫码报修（小程序）。** 现在报修要打开电脑、登录、选设备、填现象。车间里的人更愿意"扫一下设备上的码，拍张照，说一句'这机有异响'"。技术上不难：设备二维码里放 `asset_no`，扫码进小程序，自动带出设备信息、最近三次维修记录、当前是否已有未闭环工单，提交后走同一条 `createRepairOrder` 接口。**它解决的是"报修门槛"，而报修率直接决定 MTBF 的准确性**——第六章讲过，漏报会让 MTBF 虚高，而漏报的根源就是"报修太麻烦"。

**第二，设备 IoT 接入（对接 SCADA 做预测性维护）。** 客户的注塑机已经接了 SCADA，能采到合模压力、油温、电机电流。做法是先做"阈值告警 + 自动建单"（油温连续 10 分钟超 75℃ → 自动生成维修工单，`bizOrderNo` 直接带上），再往"趋势预测"走（同一台设备的油温基线在缓慢抬升 → 提前 2 周提示检修）。**这条路的前提是停机分类**——SCADA 只知道"停了"，不知道是故障停还是待料停，不分类就接进来，MTBF 会被计划停机污染（第六章第八节讲过）。

**第三，备件供应链协同。** 现在的安全库存是"拍脑袋 + 经验"，可以往前走一步：用历史出库 + 采购提前期算"再订货点"，出库流水带 `bizOrderNo` 之后，备件消耗和设备、工单、故障类型都能关联，于是能回答"这类故障平均每月消耗几个轴承"。再往后，把供应商的交期回填进系统，MTTR 里"等件时间"就能被单独拆出来——**而等件时间恰恰是客户那台注塑机 552 小时 MTTR 的主因**。这条路的终点是"备件不再拖累 MTBF"。

三个方向有一个共同点：**都建立在"这条链路的数据已经做实"之上**。扫码报修做实的是"故障发生"这一端，IoT 做实的是"停机真相"这一端，供应链协同做实的是"修复速度"这一端。数据没做实就上这些，等于在沙子上盖楼。

## 九、写在最后

这十篇写完，我最想留下的不是某段代码，而是一个判断标准：**当你面对一台设备、一张工单、一个指标时，先问一句"这个数是怎么来的、谁在维护它"。**

王主任厂里那台注塑机，MTBF 只有 1200 小时，看着像"该换"，拆开看是"等件 109 天"；汽配厂 47 张保养单，看着像"系统疯了"，拆开看是"导入模板的示例日期没删"；200 张工单没人派，看着像"调度员失职"，拆开看是"系统没有催办机制"。**所有看起来像"人的问题"的现场事故，往下挖两层，几乎都能挖到一个"没写进代码的规则"。**

工业软件的难，不在于技术栈有多新，而在于它必须同时懂三件事：设备的物理逻辑（一台机器为什么会坏）、车间的组织逻辑（一张单该谁签字）、软件的工程逻辑（并发、时区、数据一致性）。三件事缺一件，系统就会在现场翻车。而翻车不可怕，可怕的是翻完车只改了数据、没改规则——那下一次，它会以另一种形式再翻一次。

如果你的厂里也有"哪台设备最不靠谱"这种说不清的问题，不妨从最小的那一步开始：把维修记录如实录进系统，跑一个月的 MTBF。数字不一定好看，但它会告诉你，钱该花在哪。
