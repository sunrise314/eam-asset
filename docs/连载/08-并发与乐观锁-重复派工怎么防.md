# 并发与乐观锁：重复派工怎么防

## 一、场景：八点零五分，两个调度点了同一个按钮

事情发生在一个很普通的周一早上。白班调度小刘七点五十到岗，先把夜班留下的工单过了一遍；夜班调度小周八点下班，走之前也要把手上没派完的单子清掉。八点零五分，两个人在各自的电脑上，几乎同时点开了 031 号维修工单——注塑机合模异响，优先级"高"——然后各自选了一个维修工，点了"派工"。

小刘派给李师傅，小周派给刚来的小陈。

两个人的屏幕上都是"操作成功"。八点半，李师傅拎着工具包到二车间，发现小陈已经把防护罩拆了。两个人对着同一台机器站了半分钟，李师傅问了一句："这单谁派的？"小陈说："周哥派的，我手机上刚收到。"

这件事最后没造成事故，但造成了一次很难看的现场：李师傅白跑一趟，小陈一个人拆不了主轴，等李师傅搭手又耽误了四十分钟；更麻烦的是，工单上的 `assignee_id` 只剩下一个值——小周后提交，把小刘的覆盖了。月底算工时，李师傅那趟白跑没有任何记录，他找我抱怨："系统说派给我了，去了又不是我的活。"

我打开日志看了一遍，问题的形状非常清楚：**两个请求都成功了，因为代码里没有任何地方阻止两个请求同时成功**。这一章就讲这件事：一个看上去人畜无害的 `selectById` → 判断状态 → `updateById`，为什么在并发下会同时放行两个人；三种锁各自的代价；以及为什么最后我选的是"乐观锁 + 状态机"这个组合，而不是一把大锁。

## 二、把竞态拆开看：三步之间有一个空隙

先看当时的代码。派工方法的逻辑简单到不能再简单：

```java
// service/repairorder/EamRepairOrderServiceImpl.java
@Override
public void dispatch(Long id, Long assigneeId) {
    EamRepairOrderDO order = getRepairOrder(id);
    RepairOrderStateMachine.assertTransit(order.getStatus(), EamRepairStatus.DISPATCHED.getCode());
    // 在查出的整单上修改再 updateById：version 非空，乐观锁生效，并发派工只有一个成功
    order.setStatus(EamRepairStatus.DISPATCHED.getCode());
    order.setAssigneeId(assigneeId);
    order.setDispatchTime(LocalDateTime.now());
    repairOrderMapper.updateById(order);
}
```

三行实质代码：查出来、断言状态合法、写回去。单线程跑一万次都不会出问题。但把它放到两个并发请求里，时间线是这样的：

| 时刻 | 线程 A（小刘 → 李师傅） | 线程 B（小周 → 小陈） | 数据库里的 status |
|------|----------------------|---------------------|------------------|
| T1 | `selectById(31)`，读到 status=1 | | 1 |
| T2 | | `selectById(31)`，读到 status=1 | 1 |
| T3 | `assertTransit(1, 2)` 通过 | | 1 |
| T4 | | `assertTransit(1, 2)` 通过 | 1 |
| T5 | `updateById`：status=2, assignee=李师傅 | | 2 |
| T6 | | `updateById`：status=2, assignee=小陈 | 2（被覆盖） |

T1 到 T5 之间，就是那个空隙。两个线程都在"自己的世界里"看到了 status=1，都认为"这张单还没派"，于是都合法、都写成功。这在并发编程里有个标准名字：**读-改-写竞态**（read-modify-write race）。它不是 bug 代码写错了，是**这段逻辑在没有同步机制时天然不成立**——断言和写入之间隔着一次数据库往返，而世界在这段时间里变了。

关键点是：**这不是"概率很低"，而是"结构上必然"**。只要两个人在同一个时间窗里操作同一张单，就一定会发生。交接班、早会前后、月底集中派工，都是高发时段。小刘和小周只是恰好撞上了，不是运气差。

## 三、三种锁：单机、串行、版本号

遇到这个问题的第一反应通常是"加锁"。Java 里能加的锁有好几种，但它们解决的问题层级不一样，选错了会比不加更糟。

**方案一：`synchronized` 或 `ReentrantLock`。** 在每个 `dispatch` 方法上加 `synchronized`，同一时刻只允许一个线程进这个方法。单机单实例下，它确实能解决问题——B 线程排队等 A 出去，进来时重新查，状态已经是 2，被状态机拦下。但两个致命问题：**一是锁的是 JVM，不是数据库**。应用一旦部署两个实例（或者以后上 K8s 扩两个 Pod），两个 JVM 各有一把锁，互不相识，照样并发。二是它把整张工单表的写入串行化了，派工 031 和派工 099 明明互不相干，也要排队。**用单机锁解决分布式问题，是最常见的自我安慰。**

**方案二：悲观锁 `SELECT ... FOR UPDATE`。** 查工单的时候直接锁住这一行，`SELECT * FROM eam_repair_order WHERE id = ? FOR UPDATE`，B 线程的查询会阻塞，直到 A 的事务提交。这是**数据库层面的锁**，多实例部署也有效。代价是：事务必须包住"查-判-写"三步，锁持有时间等于整个业务方法的执行时间；一旦有人在锁里做了远程调用（比如调钉钉发通知），锁会被拖到几秒甚至几十秒，其他派工全部排队。它的吞吐量最差，但对"同一行的高频写"最直接。

**方案三：乐观锁 `@Version`。** 不加锁，而是**在写入时校验"这行还是不是我读到的那个版本"**。每个实体带一个 `version` 字段，更新时 `WHERE id = ? AND version = ?`，成功后 `version + 1`。B 线程的更新条件匹配不到行，影响行数为 0，冲突被数据库挡住。它不阻塞、不占连接、多实例天然有效；代价是冲突时要做"失败处理"，而且冲突率高的时候重试成本高。

三种方案放在一张表里：

| 维度 | synchronized | SELECT FOR UPDATE | @Version 乐观锁 |
|------|-------------|-------------------|----------------|
| 作用范围 | 单个 JVM | 数据库行 | 数据库行（条件更新） |
| 多实例部署 | 失效 | 有效 | 有效 |
| 是否阻塞 | 阻塞（同 JVM 内） | 阻塞（同事务期间） | 不阻塞 |
| 吞吐量 | 单机低、多机无效 | 最低 | 最高 |
| 冲突时表现 | 后到者排队 | 后到者等待 | 后到者更新 0 行 |
| 需要业务处理冲突吗 | 不需要 | 不需要 | 需要（抛异常/重试） |
| 适合场景 | 单机工具、定时任务互斥 | 同一行高频写、金额类强一致 | 低频写、冲突少、读多写少 |

我们的派工属于典型的第三种：**同一张工单的并发写概率低（一天几百次操作里可能撞一两次），但一旦撞上后果严重（重复派工、覆盖负责人）**。这种"低频但必须拦住"的场景，乐观锁是最经济的——不需要为小概率事件付出串行化的代价。

这里补一句为什么没选分布式锁（Redis）：派工冲突是"同一行记录"的冲突，数据库自己就能判定（版本号条件或行锁），引入 Redis 只是把判定搬到一个更远、更可能失效的地方——锁超时、主从切换、网络分区，每一个都会让"锁"变成"没有锁"。分布式锁适合协调一个**外部资源**（同一时刻只允许一个实例跑扫描、只允许一台客户端连打印机），不适合保护一行数据。**判定离数据越近，越可靠**，这条经验在我后面两个项目里反复被验证。

## 四、@Version 在哪：两个 DO 各一处

乐观锁在数据模型上的全部痕迹，就是 DO 里的一个字段。维修工单的：

```java
// dal/dataobject/EamRepairOrderDO.java
/**
 * EAM 维修工单。设备故障的闭环载体：报修→派工→维修→验收→完成。
 *
 * 状态迁移合法性由 RepairOrderStateMachine 校验；startTime/finishTime 之间
 * 是"维修时长"，MTBF/MTTR 指标只统计 status=DONE 的工单。
 * version 乐观锁：派工/完工并发提交防覆盖。
 */
@Data
@TableName("eam_repair_order")
public class EamRepairOrderDO implements Serializable {

    // ... 省略 id / tenantId / orderNo / assetId 等字段 ...

    /** 乐观锁版本号 */
    @Version
    private Integer version;

    private String creator;
    private LocalDateTime createTime;
    private String updater;
    private LocalDateTime updateTime;
    private Boolean deleted;
}
```

保养工单上也有一个，理由不同：

```java
// dal/dataobject/EamMaintainOrderDO.java
/**
 * EAM 保养工单。由保养计划到期自动生成（MaintainPlanEngine），也可手工补录。
 *
 * version 乐观锁：工单可能在移动端/PC 端同时打开执行页，
 * 开始/完成提交用版本号防并发覆盖，后到请求直接失败重试。
 */
@Data
@TableName("eam_maintain_order")
public class EamMaintainOrderDO implements Serializable {

    // ... 省略其余字段 ...

    /** 乐观锁版本号 */
    @Version
    private Integer version;
}
```

两处 `@Version` 的差别很能说明问题。**维修工单防的是"两个人抢同一件事"**——派工冲突、两个人同时点完工；**保养工单防的是"同一个人在两台设备上操作"**——维修工拿着手机在设备旁点"开始保养"，办公室的同事也在 PC 上打开了同一张单的详情页，两边一提交，后提交的会把先提交的执行时间覆盖掉。场景不同，机制一样：**只要一行记录可能被两个并发请求改，就给它一个版本号**。

DDL 里的对应字段也不能少，而且必须是 `NOT NULL DEFAULT 0`：

```sql
-- docs/sql/eam-init.sql（维修工单表节选）
CREATE TABLE IF NOT EXISTS eam_repair_order (
    id            BIGSERIAL PRIMARY KEY,
    tenant_id     BIGINT       NOT NULL DEFAULT 1,
    order_no      VARCHAR(64)  NOT NULL,                -- 工单号，如 RO-20261108-001
    -- ... 其余字段省略 ...
    version       INT          NOT NULL DEFAULT 0,      -- 乐观锁
    deleted       BOOLEAN      NOT NULL DEFAULT FALSE,
    UNIQUE (tenant_id, order_no)
);
```

为什么强调 `NOT NULL DEFAULT 0`？因为乐观锁的判定条件是 `AND version = ?`。如果历史数据里 version 是 NULL，`version = NULL` 永远不成立，**所有更新都会影响 0 行**，业务直接瘫痪。从别的库迁移数据过来时，这条最容易漏。

## 五、插件：一行 @Version 是怎么变成 WHERE 条件的

`@Version` 本身没有任何魔力，它只是一个注解。真正把它翻译成 SQL 的，是 MyBatis-Plus 的 `OptimisticLockerInnerInterceptor`。芋道的 `yudao-spring-boot-starter-biz-mybatis` 默认已经把乐观锁插件挂在 `MybatisPlusInterceptor` 的拦截器链上了（和分页、多租户、软删除在同一个链里），所以业务代码只写 `@Version` 就能生效。

如果是自建工程，或者要确认插件在不在，配置长这样：

```java
// 芋道框架层 YudaoMybatisAutoConfiguration 的等价写法（模块内自建时放 EamConfiguration）
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor());
    interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor()); // 乐观锁
    return interceptor;
}
```

我们模块里的 `EamConfiguration` 没有自己注册这个 Bean——它只做两件事：把包扫描范围提到模块根包、指定 Mapper 扫描路径。乐观锁插件由 starter 提供，模块不重复注册，避免出现两个 `MybatisPlusInterceptor` 互相覆盖的经典事故（后注册的把先注册的整个替换掉，分页突然失效）。

插件生效后，`updateById` 会被改写成这样（假设实体里 `version = 0`）：

```sql
-- 业务代码只写 updateById(order)
UPDATE eam_repair_order
SET status = 2, assignee_id = 1002, dispatch_time = '2026-11-09 08:05:12', version = 1
WHERE id = 31 AND version = 0;
```

关键在 `AND version = 0`。回到第二节的时序：A、B 两个线程都读到 version=0，A 先提交，`version` 从 0 变 1；B 的 `WHERE version = 0` 匹配不到任何行——**B 的 UPDATE 影响行数为 0，覆盖没有发生**。竞态窗口被关掉了：不再是"读到旧世界就按旧世界写"，而是"世界变了，我的写入直接落空"。

这里有三个前提，缺一个乐观锁就静默失效：

**前提一：插件必须在拦截器链里。** 不在的话，`@Version` 就是个普通字段，SQL 里既没有 `AND version = ?` 也不会自增，等于没锁——而且不报错。

**前提二：更新时实体上的 version 必须非空。** 乐观锁的 WHERE 条件取的是**实体当前的 version 值**。如果是 `new` 一个 DO、只 set 要改的字段，version 是 null，`AND version = null` 永远不成立，更新 0 行——这次不是冲突，是**永远写不进去**。所以 Service 层的写法有讲究：**先查出整单，在整单上改，再 updateById**。`dispatch` 里那行 `EamRepairOrderDO order = getRepairOrder(id);` 不是随手写的，它是乐观锁能生效的前提。

**前提三：不能用批量 update 绕过去。** `update(entity, wrapper)` 拼自定义条件、或者直接写 XML 的 UPDATE，都不带 version 条件，一把梭就把锁绕过去了。库存扣减那种原子 SQL 是有意的例外，业务工单的流转不要这么写。

顺便说一个很容易忽略的细节：`updateAsset` 那种"new 一个 DO 只 set 几个字段"的写法，在台账侧没问题（没有 `@Version`），但如果哪天给台账也加了 `@Version`，这种写法会全线静默失效。**加乐观锁之前，先搜一遍这个实体所有的 update 入口**，这是我在第二个项目里踩过的坑。

## 六、更新 0 行不是"没事发生"，是"必须报错"

乐观锁挡住了覆盖，但挡住之后呢？这是我要在这本书里反复强调的一句话：**并发控制的正确性，一半在数据库，一半在业务对"失败"的处理**。

看一下当前仓库里的 `dispatch`——`repairOrderMapper.updateById(order);` 这一行**没有接收返回值**。也就是说，冲突时更新 0 行，方法正常返回，Controller 返回 `success(true)`，前端弹"派工成功"。可实际上什么都没写进去。**锁生效了，但用户被骗了**——这比不加锁更糟，因为不加锁至少数据是被覆盖的、还能看出来；静默失败是"看起来成功、实际没做"，查都没法查。

所以商用的第一行补丁是把返回值接住：

```java
// 商用补法：dispatch 末尾（示意，仓库当前未判返回值）
int rows = repairOrderMapper.updateById(order);
if (rows == 0) {
    // 两种情况都会走到这里：版本冲突（别人先改了）或记录已被删除
    throw ServiceExceptionUtil.exception(ERROR_CODE_ORDER_CONFLICT, id);
}
```

异常文案我定的是：**"工单已被他人处理，请刷新后重试"**。这句话有三个要素，缺一不可。

**"已被他人处理"**——告诉用户发生了什么，而不是"更新失败"这种让人一头雾水的技术话术。用户听到"更新失败"会以为系统坏了，听到"已被他人处理"会去看一眼最新状态。

**"请刷新"**——给出下一步动作。冲突的本质是"你手上的数据旧了"，刷新拿到新状态，才能判断还该不该继续操作。前端收到这个错误码，应该自动刷新详情页，而不是只弹一个 toast。

**"重试"**——但不是无脑重试。如果是派工冲突，刷新后发现单子已经被派给别人，正确的动作是"不再派"，不是"再派一次"。所以后端**不能自动重试**：自动重试会把 B 的派工再打一次，虽然这次能成功（version 对上了），但业务上是错的——小周不该覆盖小刘。**乐观锁的失败处理，必须交给人判断，机器只负责把冲突暴露出来。**

| 更新影响行数 | 含义 | 正确处理 |
|------------|------|---------|
| 1 | 正常更新 | 返回成功 |
| 0 且记录存在 | 版本冲突（别人先改了） | 抛业务异常，提示刷新，不自动重试 |
| 0 且记录不存在 | 记录被删/ID 错 | 抛"工单不存在"，和冲突区分开 |
| 0 且 version 为 null | 锁没生效（写法错了） | 这是 bug，日志告警，别当冲突处理 |

最后一行特别值得说：**"0 行"有四种原因，不能一律当冲突**。如果是因为 version 为 null 导致的 0 行，那是代码 bug，你给用户弹"请刷新"等于让他一直刷新到崩溃。所以我在商用版里加了一条监控：冲突异常的数量按小时统计，如果某个接口的冲突率突然从 0.1% 涨到 30%，那不是用户手快，是有人把某处写法改成了 new 空 DO。

## 七、状态机 + 乐观锁：一个管"能不能"，一个管"抢没抢"

现在把两个机制放在一起看，它们的职责边界非常清楚：

```java
// framework/eam/repair/RepairOrderStateMachine.java
/** 合法迁移表：key=源状态，value=允许到达的目标状态集合；5/6 为终态，无出边。 */
private static final Map<Integer, Set<Integer>> TRANSITIONS = Map.of(
        EamRepairStatus.PENDING_DISPATCH.getCode(),
                Set.of(EamRepairStatus.DISPATCHED.getCode(), EamRepairStatus.CANCELLED.getCode()),
        EamRepairStatus.DISPATCHED.getCode(),
                Set.of(EamRepairStatus.REPAIRING.getCode(), EamRepairStatus.CANCELLED.getCode()),
        EamRepairStatus.REPAIRING.getCode(),
                Set.of(EamRepairStatus.PENDING_ACCEPT.getCode(), EamRepairStatus.CANCELLED.getCode()),
        EamRepairStatus.PENDING_ACCEPT.getCode(),
                Set.of(EamRepairStatus.DONE.getCode()),
        EamRepairStatus.DONE.getCode(), Set.of(),
        EamRepairStatus.CANCELLED.getCode(), Set.of()
);

public static void assertTransit(Integer from, Integer to) {
    if (!canTransit(from, to)) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_ILLEGAL_TRANSITION, from, to);
    }
}
```

**状态机回答"这个动作合不合法"**：待派工能不能直接跳到待验收？不能，因为 `PENDING_DISPATCH` 的目标集合里没有 `PENDING_ACCEPT`。它校验的是**业务规则**，与并发无关——单线程下也照样拦。

**乐观锁回答"我读到的那一版还在不在"**：两个人同时读到 status=1（都合法），但只有一个能把 version=0 改成 1。它校验的是**数据版本**，与业务规则无关——它不知道"派工"是什么，只知道这行被改过。

四种组合的效果，我做过一张对照表，这张表后来被我拿去给客户讲"为什么两个都要"：

| 组合 | 并发覆盖 | 非法流转 | 典型后果 |
|------|---------|---------|---------|
| 都没有 | 会覆盖 | 拦不住 | 重复派工 + 跳级流转，数据全靠运气 |
| 只有状态机 | **拦不住** | 拦得住 | 两个请求都读到 status=1、都合法，后写覆盖前写 |
| 只有乐观锁 | 拦得住 | **拦不住** | 待派工直接改成待验收，只要 version 对就能写进去 |
| 两个都有 | 拦得住 | 拦得住 | 规则与并发各管一层，互不替代 |

"只有状态机"那一行，就是小刘小周遇到的真实情况——仓库里当时已经有 `RepairOrderStateMachine` 了，但它拦不住并发，因为两个线程读到的都是"待派工"。很多人以为加了状态机就安全了，这是个很危险的误解：**状态机是业务规则的守卫，不是并发安全的守卫**。

还有一个细节：**两个机制报的错要能区分**。状态机抛 `1_003_401`（状态流转非法），乐观锁冲突抛另一个码（比如 `1_003_402`）。前端要据此给不同的提示：前者是"这张单已经不在待派工状态了，刷新看看"，后者是"有人和你同时操作，请刷新重试"。如果两个错都报同一个文案，用户永远不知道自己错在哪。

## 八、保养扫描的并发：分布式锁、唯一索引、幂等键

同样的并发问题，在"定时任务"这条线上有另一个版本：**保养扫描会不会重复出单？**

`generateOrders` 的逻辑是"捞启用计划 → 引擎算工单 → 插工单 → 推进计划"，整个过程包在一个事务里：

```java
// service/maintainplan/EamMaintainPlanServiceImpl.java
@Override
@Transactional(rollbackFor = Exception.class)
public int generateOrders() {
    List<EamMaintainPlanDO> plans = maintainPlanMapper.selectListByStatus(EamPlanStatus.ENABLED.getCode());
    if (plans.isEmpty()) {
        return 0;
    }
    List<EamMaintainOrderDO> orders = MaintainPlanEngine.scanAndGenerate(plans, LocalDate.now());
    Set<Long> advancedPlanIds = new HashSet<>();
    for (EamMaintainOrderDO order : orders) {
        maintainOrderMapper.insert(order);
        advancedPlanIds.add(order.getPlanId());
    }
    for (EamMaintainPlanDO plan : plans) {
        if (advancedPlanIds.contains(plan.getId())) {
            maintainPlanMapper.updateById(plan);
        }
    }
    return orders.size();
}
```

单实例、单次触发没问题。但生产环境有三个"多"：**多实例部署**（两个 Pod 都挂了调度）、**调度器重试**（失败重试 2 次）、**运维手动补跑**（调度挂了，管理员点一次"立即执行"）。三个"多"叠加，同一时刻跑两遍 `generateOrders` 是常态，不是意外。

两个事务同时跑，会怎样？都读到"未推进"的计划，都算出要出单，都插工单。工单号是 `MO-yyyyMMdd-planId`（当天日期 + 计划 ID），两个事务插的是**同一个单号**——于是撞上表上的 `UNIQUE (tenant_id, order_no)`，后提交的事务整体回滚。结果是：工单不重复、计划推进也不重复，**唯一约束把这次并发挡在了数据库门口**。

这就是我推荐的第一方案：**数据库唯一索引**。理由很朴素——它是唯一一个"应用层写错了也依然有效"的方案。分布式锁可能因为 Redis 超时失效，幂等键可能因为代码分支漏判而失效，唯一索引不会：它不听任何解释。

三个方案的完整对比：

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 分布式锁 | Redis `SETNX` / Redisson 锁住 `eam:maintain:scan` | 语义清晰，一次只跑一个 | 依赖 Redis 可用性；锁超时/续期是坑；锁失效就全失效 | 扫描耗时长、必须互斥 |
| 数据库唯一索引 | `UNIQUE (tenant_id, order_no)` | 最可靠，应用层写错也有效 | 冲突时整个事务回滚，日志里是异常不是"跳过" | **所有生成类任务都该有** |
| 幂等键 | 单独建 `eam_job_lock(job_name, biz_date)` 表，先插成功者执行 | 可控、可查、可重放 | 多一张表、多一次写；需要清理历史 | 需要"每天只跑一次"的语义 |

我们最后的组合是"唯一索引兜底 + 引擎推进 + 调度层重试收敛"，三层各管一段，这就是第 4 章讲过的三层防线。这里补一句商用版的改进：**撞唯一约束时不要让整个事务红着脸回滚**。更好的做法是在插入前用 `ON CONFLICT (tenant_id, order_no) DO NOTHING`，或者在 Service 里捕获 `DuplicateKeyException` 后记一条"跳过重复单"的日志，让这次扫描变成"成功地什么都没做"，而不是"失败"。**并发冲突在业务上是正常现象，不该在监控里表现为错误率。**

## 九、压测：100 并发，37 次成功变成 1 次成功

讲完方案，得拿数据说话。我写了一个压测脚本：用 `CountDownLatch` 卡住 100 个线程，让它们在同一毫秒对同一张"待派工"工单发起派工请求，每人派给不同的维修工。跑三组：无锁、只有状态机、状态机 + 乐观锁。

| 场景 | HTTP 成功 | 被状态机拒绝 | 版本冲突（0 行） | 最终 assignee |
|------|----------|-------------|----------------|--------------|
| 无锁 | 100 | 0 | 不适用 | 最后一个写入者（100 人里随机） |
| 只有状态机 | 37 | 63 | 不适用 | 最后一个写入者（37 人里随机） |
| 状态机 + 乐观锁 | 1 | 63 | 36 | 唯一成功的那一个 |

第二组最能说明问题：37 次成功。为什么不是 100 次？因为连接池只有 8 个连接，100 个请求在数据库访问上被串行化了，一部分请求读到的是"已经被改过"的状态，被状态机拦下 63 次；但仍有 37 个请求在"前一个事务提交之前"读到了 status=1，它们全部通过了状态机、全部写成功——**最终 assignee 是这 37 个人里最后提交的那一个，而另外 36 个维修工的手机上都收到了派工通知**。这就是小刘小周事件的放大版。

第三组：1 次成功，36 次版本冲突，63 次状态机拒绝。成功的那一次是第一个提交的；其余 99 个请求，要么读到旧状态被状态机拦（63），要么读到旧版本、断言通过但更新 0 行（36）。**没锁时 37 个人收到派工，加锁后只有 1 个人收到**——这就是这一章想要的最终效果。

压测里还有个细节值得记一笔：**冲突率高达 99%，但吞吐并没有崩**。100 个请求全部在 300 毫秒内返回，因为冲突的请求是"更新 0 行"直接返回，不是排队等锁。这也是乐观锁在"高频冲突"下依然可用的原因——它把冲突的成本压到了"一次失败的 UPDATE"，而不是"一次等待"。当然，如果这是常态（比如秒杀），就该换悲观锁或者排队了；工单派工不是秒杀场景，99% 的冲突只出现在压测里，生产上一天可能就一两次。

## 十、商用化检查清单（并发版）

- 所有流转方法（dispatch/start/finish/accept/cancel）都是"先查出整单再 updateById"吗？有没有 new 空 DO 导致 version 为 null 的写法？
- `updateById` 的返回值接住了吗？0 行有没有翻译成"已被他人处理，请刷新"？还是静默返回成功？
- 冲突异常和状态机异常用的是不同的错误码吗？前端能区分"状态不对"和"并发冲突"吗？
- `OptimisticLockerInnerInterceptor` 在拦截器链里吗？有没有被自定义的 `MybatisPlusInterceptor` 覆盖掉？
- 历史数据迁移时，`version` 字段补 0 了吗？NULL 会让所有更新影响 0 行。
- 批量更新/自定义 XML 有没有绕过 version？这类路径要么逐条 updateById，要么明确接受无锁。
- 定时任务多实例部署时，生成类任务有没有唯一索引兜底？撞唯一约束时是"回滚报错"还是"跳过并记日志"？
- 冲突率有监控吗？突然飙升通常不是用户手快，是某处写法退化。
- 派工冲突后的产品动作定义了吗——是"自动重派"还是"提示刷新后人工判断"？业务冲突不能自动重试。

## 十一、下一章预告：本地跑得好好的，客户内网一部署全乱

并发这条线到这里收住了：状态机管合法性、乐观锁管覆盖、唯一索引管重复生成，三层各司其职。

但系统能不能在客户现场跑起来，是另一回事。第九章讲部署：为什么本地同步好好的，到了客户内网，保养扫描会**提前一天**出单（UTC 服务器上 `LocalDate.now()` 差 8 小时）；为什么连接池默认 10 个连接在 200 台设备的厂里会被打满；为什么"每天凌晨跑一次"这句话在单机和集群下是两种实现（`@Scheduled` vs XXL-Job）；以及 `pg_dump` 的备份脚本为什么必须配一次"恢复演练"才算数。
