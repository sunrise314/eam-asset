# 设备状态流转与台账治理

## 一、场景：盘点那天，账上有 230 台，车间只有 187 台

每年六月是王主任厂里的年中盘点。财务要盘固定资产，设备科要盘设备台账，两个部门拿着一份从 Excel 导出来的清单，一人一个车间地走。走到第二天下午，小赵（设备科的台账管理员，刚毕业两年）拿着清单来找王主任，脸是白的。

清单上 230 台设备，车间里对着编号能找到、并且确实在用的，只有 187 台。剩下 43 台去哪了？三个人花了一下午对出来三类：**31 台是早就报废拆走的**，但台账上的状态还写着"运行"；**8 台是重复录入**——两台不同年代的贴片机都叫"贴片机-1"，当年买第二台的时候直接复制了一行改了型号；**4 台是借给隔壁厂的**，借出去两年，台账上还挂在二车间。

更麻烦的是反过来的方向：车间里有 **12 台设备在干活，系统里根本没有**。有 3 台是老板朋友厂子倒闭时折价拉过来的，没走采购流程就没入账；有 5 台是技改时自己做的非标设备；还有 4 台是租来的。

王主任把这份对账结果拍在桌上，说了一句很刺人的话："**我们连自己有多少台设备都说不清，还谈什么保养、维修、可靠性？**"

这话是对的。前一章讲 MTBF，所有的计算都建立在一个前提上：每台设备在系统里有一条唯一的、状态正确的台账记录。台账错了，MTBF 就是拿一堆错数据算出来的精确错误。这一章讲两件事：**设备的状态到底有几种、怎么流转**，以及**台账从"死档案"变成"活账本"要做的三个动作**。

## 二、台账为什么会烂：四条没有落点的路径

我先没急着改数据，而是问小赵："这 43 台幽灵设备，是怎么产生的？"对完一遍，原因很集中——设备在生命周期里有四条"状态变化"的路径，而 Excel 台账上没有任何一条有落点。

**第一条：新增。** 采购入库、调拨转入、租入、自制、接受捐赠。只有"采购入库"这一条会触发财务走流程、顺便通知设备科登记；其余四条全靠人记得。那 12 台没入账的设备，全是从这四条缝里漏进来的。

**第二条：报废。** 设备报废要走固定资产清理，财务那边销账了，但设备科的 Excel 没人改——**因为财务销账和设备台账销账是两件事、两个人、两套表**。31 台报废未销账，全是这么来的。

**第三条：位置/归属变化。** 设备在车间之间调拨、借出、租出、封存。Excel 里"安装位置"那一列是纯文本，改不改全靠自觉。借给隔壁厂那 4 台，就是这么在账上"留在二车间"两年的。

**第四条：状态变化。** 运行、停机、维修中、报废。这一列在 Excel 里常年是"1"，因为它是**唯一一个需要人主动去改、且改了没有任何即时反馈的字段**。设备坏了，维修班关心的是"什么时候修好"，没人会想起来去改台账；修好了，更没人改回来。一年下来，状态列的准确率我自己估过，不到 30%。

四条路径归拢成一句话：**台账不是"记错了"，是"没人负责记、也没有机制逼人记"**。所以治理台账不能靠"下次盘点认真点"，得靠三样东西：状态语义要清楚（这一章前半部分）、唯一性要有数据库兜底（后半部分的动作一）、盘库动作要能被系统接住（动作二和三）。

## 三、四个状态：为什么不是三个，也不是六个

系统里的设备状态只有四个，定义在 `EamAssetStatus` 里：

```java
// enums/EamAssetStatus.java
@Getter
@AllArgsConstructor
public enum EamAssetStatus {

    RUNNING(1, "运行"),
    DOWN(2, "停机"),
    REPAIRING(3, "维修中"),
    SCRAPPED(4, "报废");

    private final Integer code;
    private final String name;
}
```

四个状态，对应设备在厂里的四种"存在方式"。注意这里没有"待机""封存""调拨中""报废审批中"——不是我没想到，是**中小工厂的台账不需要那么细**。每多一个状态，就多一批"这个状态该谁维护、能迁到哪"的规则，而规则越多，现场越不愿意维护。四个状态是我在三个项目里试出来的甜点：够表达业务，又不至于让人记不住。

合法迁移应该长这样（这是业务规则，不是代码里现成的表——仓库里的台账侧**没有状态机**，这一点我在下一节会坦白说清）：

| 当前状态 | 允许迁往 | 触发动作 | 谁操作 |
|---------|---------|---------|--------|
| 运行 RUNNING | 停机 DOWN | 排产结束、待料、计划闲置 | 设备科 / 班组长 |
| 运行 RUNNING | 维修中 REPAIRING | 报修并派工 | 调度员 |
| 运行 RUNNING | 报废 SCRAPPED | 报废审批通过 | 设备科 + 财务 |
| 停机 DOWN | 运行 RUNNING | 复产 | 设备科 |
| 停机 DOWN | 维修中 REPAIRING | 停机设备报修 | 调度员 |
| 停机 DOWN | 报废 SCRAPPED | 报废审批通过 | 设备科 + 财务 |
| 维修中 REPAIRING | 运行 RUNNING | 维修验收通过 | 验收人 |
| 维修中 REPAIRING | 停机 DOWN | 修不了、转待件封存 | 设备科 |
| 报废 SCRAPPED | —— | 无出边，终态 | —— |

这张表里有三条边是经过争论的。

**第一条：维修中 → 停机。** 一开始我把它禁掉了，理由是"修完就该回运行"。上线两周就发现不对：一台设备拆开发现主轴要换，备件要等三周，这三周它既不在维修（没人干活），也不该算运行。没有这条边，现场只能把它挂在"维修中"三周，MTBF 的维修时长被虚增三周。加上这条边之后，"维修中"的语义被收窄成"此刻真的有人在修"，指标才准。

**第二条：停机 → 报废 和 运行 → 报废。** 报废可以从任何非报废状态发起，因为设备可能在停机时被判定无维修价值，也可能在运行中被技改替换掉。但**报废不能从"维修中"直接发起**——活干到一半说报废，工时和备件流水都还没结，财务对不上。所以维修中的设备要先回到停机或运行，再走报废。

**第三条：报废是终态，没有出边。** 这一点我在第六节单独讲，因为它牵涉到"删不删记录"这个更根本的问题。

## 四、代码的现状：枚举有了，状态机还没有

讲到这里必须坦白一件事：**仓库里的台账侧只有一个枚举，没有状态机**。这和维修工单那套 `RepairOrderStateMachine` 不一样——维修工单有 6 个状态、5 条迁移边，我抽了状态机；台账只有 4 个状态，且迁移大多由人工在后台点，演示仓库就没有再抽一层。当前的写入路径是这样的：

```java
// service/asset/EamAssetServiceImpl.java
@Override
public Long createAsset(EamAssetSaveReqVO createReqVO) {
    EamAssetDO asset = new EamAssetDO();
    asset.setAssetNo(createReqVO.assetNo());
    asset.setName(createReqVO.name());
    asset.setModel(createReqVO.model());
    asset.setCategory(createReqVO.category());
    asset.setLocation(createReqVO.location());
    asset.setStatus(createReqVO.status() != null ? createReqVO.status() : EamAssetStatus.RUNNING.getCode());
    asset.setPurchaseDate(createReqVO.purchaseDate());
    asset.setWarrantyUntil(createReqVO.warrantyUntil());
    asset.setResponsibleUserId(createReqVO.responsibleUserId());
    asset.setAttributes(createReqVO.attributes());
    asset.setRemark(createReqVO.remark());
    assetMapper.insert(asset);
    return asset.getId();
}

@Override
public void updateAsset(EamAssetSaveReqVO updateReqVO) {
    validateAssetExists(updateReqVO.id());
    EamAssetDO updateObj = new EamAssetDO();
    updateObj.setId(updateReqVO.id());
    // ... 其余字段省略 ...
    updateObj.setStatus(updateReqVO.status());
    // ... 其余字段省略 ...
    assetMapper.updateById(updateObj);
}
```

两个细节值得说。

**第一，`createAsset` 给状态兜了个默认值。** 前端没传状态时，默认 `RUNNING`。这是个有意的选择：新入册的设备绝大多数是在用的，让录入的人少点一次下拉框，比让他面对一个 null 强。代价是——如果录的是"买回来先封存"的设备，默认运行就错了。所以商用版我在录入表单上把状态做成了必填，默认值只留给接口调用方。

**第二，`updateAsset` 是"直改"状态。** 没有 `assertTransit`、没有审批、没有留痕，前端传什么就写什么。这意味着**任何人都能把一台报废设备一键改回运行**。演示仓库可以这么干，商用不行。我在第二个客户那里补的写法是这样的（这是商用补法，仓库里没有这个类）：

```java
// 商用版建议新增：framework/eam/asset/AssetStatusMachine.java（示意，仓库未落地）
private static final Map<Integer, Set<Integer>> TRANSITIONS = Map.of(
        EamAssetStatus.RUNNING.getCode(),
        Set.of(EamAssetStatus.DOWN.getCode(), EamAssetStatus.REPAIRING.getCode(), EamAssetStatus.SCRAPPED.getCode()),
        EamAssetStatus.DOWN.getCode(),
        Set.of(EamAssetStatus.RUNNING.getCode(), EamAssetStatus.REPAIRING.getCode(), EamAssetStatus.SCRAPPED.getCode()),
        EamAssetStatus.REPAIRING.getCode(),
        Set.of(EamAssetStatus.RUNNING.getCode(), EamAssetStatus.DOWN.getCode()),
        EamAssetStatus.SCRAPPED.getCode(), Set.of()   // 报废是终态
);

public static void assertTransit(Integer from, Integer to) {
    if (from == null || to == null || !TRANSITIONS.getOrDefault(from, Set.of()).contains(to)) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_ASSET_ILLEGAL_TRANSITION, from, to);
    }
}
```

然后在 `updateAsset` 里加一行 `AssetStatusMachine.assertTransit(asset.getStatus(), updateReqVO.status())`。写法和 `RepairOrderStateMachine` 完全同构——**同一个工程里，同类问题用同一种解法**，这比"状态机要不要抽"本身更重要。维修工单抽了、台账没抽，是规模差异（5 条边 vs 9 条边、自动流转 vs 人工点击），不是原则差异；等台账也要支持扫码报修自动置"维修中"，这层状态机就必须补上。

顺便说一个查询入口。盘库时扫码枪扫出来的是一串设备编号，系统要能用编号直接定位设备：

```java
// service/asset/EamAssetServiceImpl.java
@Override
public EamAssetDO getByAssetNo(String assetNo) {
    EamAssetDO asset = assetMapper.selectByAssetNo(assetNo);
    if (asset == null) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_ASSET_NO_NOT_EXISTS, assetNo);
    }
    return asset;
}
```

异常码 `1_003_002`，文案"设备编号不存在: {}"。盘库现场扫到一个编号系统里没有，这一声报错就是"未入账设备"的发现点——**扫码盘库的价值不在于快，而在于它把"账上没有"这件事变成了一个当场可见的异常**。

## 五、为什么"停机"和"维修中"必须分开

四个状态里，最容易被合并的是"停机"和"维修中"——反正都是没在生产，合并成一个"不可用"不就行了？我在第一个项目里就这么干过，三个月后乖乖拆开了。三个理由。

**第一，人力投入不一样。** 停机（待料、没排产、计划闲置）是**零人力投入**；维修中是**有人正在干活**。这两个状态在管理上的含义完全不同：停机要问"为什么没排产"，维修中要问"谁在修、修到哪一步、缺不缺件"。合并之后，设备科长打开列表看到一片"不可用"，既不知道该去催计划，也不知道该去催维修。

**第二，对 MTBF 口径的影响是致命的。** 上一章讲过，MTBF 的分子是"设备本可以正常跑的时间"。如果一台设备因为没订单停了三个月，却挂着"维修中"，这三个月会被算进维修时长，MTBF 被凭空压低——设备明明是好的，指标却显示它很烂。反过来，一台真在维修的设备如果挂着"停机"，维修时长不进统计，MTBF 虚高。**状态错了，指标就错了，而且错得没有任何报错。**

**第三，它决定了"维修工单"从哪开始。** 我们的维修工单里，`startTime` 是维修开始时间，设备状态的 `REPAIRING` 应该和它同步：派工开工置 REPAIRING，验收通过回 RUNNING。如果停机也算维修中，那"设备什么时候进入维修"就没有明确的信号，工单的 `startTime` 只能靠人填，填错就污染 MTTR。

| 维度 | 停机 DOWN | 维修中 REPAIRING |
|------|----------|-----------------|
| 语义 | 没在生产，但设备本身没坏 | 设备故障，正在修复 |
| 人力投入 | 无 | 有（维修工 + 可能的外协） |
| 典型原因 | 待料、无订单、计划闲置、封存 | 故障、预防性检修、技改 |
| 是否计入 MTBF 维修时长 | 否 | 是（从 startTime 到 finishTime） |
| 该谁关注 | 生产计划 / 设备科 | 维修班 / 调度 |
| 对应业务单据 | 无（或停机记录） | 维修工单 / 保养工单 |

这张表我在客户现场打印出来贴在设备科墙上。因为每次一讨论"这台机到底算停机还是维修中"，就会有人想和稀泥说"差不多"——把这张表摆出来，争论就结束了。

## 六、报废不是删除：一条记录要活过设备的物理生命

小赵最开始提的方案很直接："31 台报废的，我直接在系统里删掉，账不就对上了？"我拦住了。理由不是"删除危险"这种正确但空泛的话，而是三条具体的账。

**第一，历史工单还引用它。** `eam_repair_order.asset_id`、`eam_maintain_order.asset_id`、`eam_maintain_plan.asset_id` 都有外键指向 `eam_asset(id)`。物理删掉设备，这些工单要么删（历史没了）、要么外键悬空（数据坏了）。而设备一生的维修履历，恰恰是这台设备"值不值得再买同款"的唯一依据——**报废的是设备，不是经验**。

**第二，备件流水还引用它。** `eam_spare_part.asset_ids` 里存着"这个备件适用于哪些设备"的 JSONB 数组。设备删了，数组里留着一个不存在的 ID，下次查"这个轴承能装哪台机"就会查出鬼。备件适用关系是维修班最常查的东西之一。

**第三，财务口径对不上。** 设备台账不只是设备科的表，它和固定资产台账是同一批实物。财务那边报废了一个资产编号，设备科这边删了一行记录，两边的"设备总数"永远差 31 台，每次审计都要重新解释一遍。

所以报废的正确做法是**改状态，不删记录**：

```sql
-- 报废：状态置 4，记录保留；不是 DELETE
UPDATE eam_asset
SET status = 4, update_time = NOW(), updater = :operator
WHERE id = :assetId AND status <> 4;
```

这里要和 MyBatis-Plus 的**软删除**（`deleted` 字段）区分清楚，两者语义完全不同：

| 动作 | 字段变化 | 语义 | 还能查到吗 | 用于什么场景 |
|------|---------|------|-----------|-------------|
| 报废 | `status = 4` | 资产退出服役，履历仍在 | 能（默认列表可按状态过滤） | 设备拆解、卖掉、报废 |
| 软删除 | `deleted = true` | 录入错误，这行不该存在 | 不能（全局过滤） | 录错型号、重复录入的 8 条 |

重复录入的那 8 条走软删除，报废的 31 条走状态置 4——**同样是"从账面上消失"，一个是"这台设备不存在过"，一个是"这台设备存在过、现在退役了"**。分不清这两个，台账迟早还会烂：把报废设备软删掉，第二年想查"上一台同型号用了几年、修了多少次"，就查不到了。

还有一条边界要交代：报废设备的**保养计划必须同步停用**，否则第二天凌晨扫描还会给它出保养工单。这个联动演示仓库没做（`eam_maintain_plan` 里没有触发器，也没有领域事件），商用版要么在报废审批里显式停用计划，要么在 `MaintainPlanEngine` 扫描时 join 一次设备状态过滤。我倾向后者——**把"不该出单"的判断放在引擎里，比指望每个入口都记得停计划可靠**。

## 七、attributes 这个 JSONB：不同设备记不同的账

台账最麻烦的字段不是名称、不是位置，是"这台设备的关键参数是什么"。数控车床要记最大加工直径、主轴转速范围；空压机要记排气量、工作压力；注塑机要记锁模力、射胶量。三类设备、三套字段，而且客户随时会加第四类。

三种建模方式我都试过：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 宽表加字段 | `eam_asset` 上加 `max_diameter`、`air_flow`、`clamping_force`… | 查询快、类型强 | 每来一类设备就 ALTER TABLE，几十个字段大部分是 NULL |
| EAV 三表 | 属性定义表 + 属性值表 + 关联 | 无限扩展、可做元数据 | 查一台设备要 JOIN 三次，类型全是字符串，代码里到处转型 |
| JSONB 一列 | `attributes JSONB` | 加字段零成本、一个接口存任意结构、可建 GIN 索引 | 类型弱、跨设备聚合慢、需要应用层约定 |

这个厂 200 台设备、七八个类别，我选了 JSONB。代码就是一个字段加两个注解：

```java
// dal/dataobject/EamAssetDO.java
@Data
@TableName(value = "eam_asset", autoResultMap = true)   // autoResultMap 必须开
public class EamAssetDO implements Serializable {

    // ... 省略 id / tenantId / assetNo / name 等基础字段 ...

    /** 1=运行 2=停机 3=维修中 4=报废 */
    private Integer status;

    /** 设备扩展属性（JSONB），如 {"power":"15kW","vendor":"沈阳机床","serialNo":"SY20240315"} */
    @TableField(typeHandler = JacksonTypeHandler.class)
    private Map<String, Object> attributes;
}
```

两个注解缺一不可。`@TableField(typeHandler = JacksonTypeHandler.class)` 让 MyBatis-Plus 在写库时把 Map 序列化成 JSON、读库时反序列化回 Map；而 `@TableName(autoResultMap = true)` 是让它**在查询结果映射时也走 typeHandler**——少了这一个，插入正常、查询回来的 `attributes` 永远是 null，而且不报错。这个坑我在两个项目里各踩过一次，现在看到 `attributes` 是 null，第一反应就是去翻 `autoResultMap`。

真实存进去的数据长这样：

```json
// 数控车床 EQ-CNC-001
{"maxDiameter":"φ500mm","spindleSpeed":"45-4500rpm","power":"15kW","vendor":"沈阳机床","serialNo":"SY20240315"}

// 空压机 EQ-AIR-002
{"displacement":"3.6m³/min","workingPressure":"0.8MPa","tankVolume":"120L","vendor":"阿特拉斯"}

// 注塑机 EQ-INJ-001
{"clampingForce":"160T","shotWeight":"320g","power":"37kW","dryer":"料斗干燥机 50kg"}
```

JSONB 在这个场景里有个普通 JSON 没有的好处：**它能建索引、能按路径查询**。比如"找出所有工作压力大于 0.8MPa 的空压机"：

```sql
SELECT asset_no, name, attributes->>'workingPressure' AS pressure
FROM eam_asset
WHERE category = '动力'
  AND (attributes->>'workingPressure')::numeric > 0.8;
```

代价也要说清楚：**JSONB 里的字段没有类型约束**。有人把 `workingPressure` 写成 `"0.8"`，有人写成 `"0.8MPa"`，强转 numeric 直接报错。所以商用版我加了三道防线：录入表单按类别给固定的字段模板（前端约束）；应用层用一个 `AssetAttributeSchema` 做校验（后端兜底）；关键数值字段（功率、压力）如果要参与统计，就从 JSONB 提升成独立列——**JSONB 适合"存"，不适合"算"**，这个边界要提前想清楚。

## 八、台账治理的三个动作：从 81% 到 100%

数据模型讲完，回到盘点那天的烂摊子。我用了两周，做了三个动作，把账实相符率从 81.3% 拉到 100%。这三个动作都不难，难的是**按顺序做**。

**动作一：给设备编号加数据库唯一约束。** 这是所有治理的地基。8 台重复录入的根源，是 Excel 里没有任何东西阻止两行写同一个编号。DDL 里已经有这条：

```sql
-- docs/sql/eam-init.sql
CREATE TABLE IF NOT EXISTS eam_asset (
    id                  BIGSERIAL PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL DEFAULT 1,
    asset_no            VARCHAR(64)  NOT NULL,                -- 设备编号，租户内唯一，如 EQ-CNC-001
    -- ... 其余字段省略 ...
    deleted             BOOLEAN      NOT NULL DEFAULT FALSE,
    UNIQUE (tenant_id, asset_no)
);
```

`UNIQUE (tenant_id, asset_no)` 是租户内唯一——这是多租户系统的标准写法，A 厂和 B 厂可以有同一个编号，同一个厂内不行。但这条约束有个**和软删除的冲突**：一台设备录错了软删除（`deleted = true`），它的 `asset_no` 还占着，再录一个同编号的会撞唯一约束，而业务上这条记录已经"不存在"了。正确做法是改成部分唯一索引：

```sql
-- 商用版：只对未删除的记录做唯一约束
DROP CONSTRAINT IF EXISTS eam_asset_tenant_id_asset_no_key;
CREATE UNIQUE INDEX IF NOT EXISTS uk_eam_asset_no
    ON eam_asset (tenant_id, asset_no)
    WHERE deleted = FALSE;
```

同理，`eam_maintain_order` 和 `eam_repair_order` 上的 `UNIQUE (tenant_id, order_no)` 也要改成 `WHERE deleted = FALSE`，否则一张被软删除的工单会永久占住它的单号——而单号是按日期生成的，占住就意味着那一天的号段永远缺一个。

**动作二：给每台设备贴码，用扫码枪盘库。** 编号规则定成 `EQ-{类别缩写}-{三位序号}`，比如 `EQ-CNC-001`、`EQ-INJ-001`、`EQ-AIR-002`。二维码里**只放 assetNo 一个字段**，不放 URL、不放 JSON——扫码枪扫出来就是一串字符，直接调 `getByAssetNo`，不依赖网络解析、不依赖系统地址变更。现场盘点变成四个动作：

| 扫到的结果 | 现场判断 | 处理 |
|-----------|---------|------|
| 系统有、实物在 | 账实相符 | 打勾，不改 |
| 系统有、实物找不到 | 疑似幽灵 | 标记待核，当天查报废/借出/调拨记录 |
| 系统无、实物在 | 未入账 | 现场拍照 + 补录台账，编号当场生成贴上 |
| 系统有、实物在但状态不对 | 状态失真 | 现场改状态（报废置 4、维修中置 3） |

这套动作的价值不在"扫得快"，在于**它把盘点从"人对纸"变成了"系统对实物"**。以前盘点是小赵念编号、财务打勾，念错一个数字就错一行；现在扫一下，系统直接告诉你这台设备在不在账上、状态是什么，人对的只是"要不要改"。

**动作三：用保养计划反查"长期没人管"的设备。** 幽灵设备里最危险的不是报废的，是**还在账上、还在跑、但从来没进过保养计划**的那些——它们不出现在任何工单里，等于游离在管理之外。三条 SQL 就能把它们捞出来：

```sql
-- 1) 有台账但没有任何启用中保养计划的设备（管理盲区）
SELECT a.asset_no, a.name, a.status
FROM eam_asset a
LEFT JOIN eam_maintain_plan p
       ON p.asset_id = a.id AND p.status = 1 AND p.deleted = FALSE
WHERE a.deleted = FALSE AND a.status <> 4 AND p.id IS NULL;

-- 2) 计划存在但已逾期 30 天以上没出过工单的设备（引擎漏扫/计划停用）
SELECT a.asset_no, a.name, p.plan_no, p.next_maintain_time
FROM eam_maintain_plan p
JOIN eam_asset a ON a.id = p.asset_id
WHERE p.status = 1 AND p.deleted = FALSE
  AND p.next_maintain_time < NOW() - INTERVAL '30 days';

-- 3) 台账状态与未闭环维修工单矛盾的设备（状态失真）
SELECT a.asset_no, a.status, r.order_no, r.status AS repair_status
FROM eam_asset a
JOIN eam_repair_order r ON r.asset_id = a.id AND r.deleted = FALSE
WHERE a.status <> 3
  AND r.status IN (2, 3);   -- 已派工 / 维修中
```

第一条查出 27 台"孤儿设备"——有台账、没计划，其中 11 台是那 12 台未入账设备补录后还没来得及配计划的。第二条查出 6 条逾期计划，全是计划停用后忘了恢复。第三条最有意思：查出 9 台设备的台账状态是"运行"，但系统里挂着"已派工/维修中"的维修工单——**设备在修，台账却说在跑**，这就是状态没人维护的直接证据。

## 九、治理前后：一张表看完两周的活

治理的最终数字，我整理成了这张表，它后来成了王主任每次向老板汇报设备管理工作的固定第一页：

| 项目 | 治理前 | 治理后 | 说明 |
|------|-------|-------|------|
| 账面设备数 | 230 | 199 | 销账 43 台、补录 12 台 |
| 车间实际在用 | 199 | 199 | 含原账上 187 台 + 未入账 12 台 |
| 幽灵设备 | 43 | 0 | 报废未销账 31、重复录入 8、借出未还 4 |
| 账实相符率 | 81.3%（187/230） | 100%（199/199） | 分子从"账上真在用的"变成"账实一致" |
| 有保养计划的设备 | 121 台 | 187 台 | 孤儿设备 27 台已补计划（含新入账 12 台） |
| 状态失真设备 | 9 台 | 0 | 台账状态与维修工单矛盾 |
| 唯一编号约束 | 无（8 组重复） | 部分唯一索引 | `WHERE deleted = FALSE` |

81.3% 这个数，就是把 187 除以 230——账面 230 台里，真正对得上实物的只有 187 台。治理后不是"230 台都对上了"，而是"账面从 230 修正到 199，199 台全对上"。**账实相符率的提升，一半靠改数据，一半靠改账面**，这一点必须跟老板讲清楚，否则他会以为你把 43 台设备变出来了。

王主任在汇报会上说了一句我记到现在的话："以前我以为台账是个记录本，现在知道它是个**约束**——编号唯一、状态有语义、盘库有系统接着，这三条立住，人才会认真记。"这句话其实就是这一章的全部意思。

## 十、商用化检查清单（台账与状态版）

- 台账侧有没有状态迁移校验？报废能不能被一键改回运行？有没有留痕（谁改的、什么时候、从什么状态到什么状态）？
- `停机` 和 `维修中` 是否分开？有没有"维修中→停机"这条边处理长期待件？
- 报废是改 `status=4` 还是物理删除/软删除？历史工单、备件适用关系、财务报表还对得上吗？
- 设备报废后，保养计划是否同步停用？引擎扫描时有没有过滤报废设备？
- `UNIQUE (tenant_id, asset_no)` 是否处理了软删除冲突？是否改成了 `WHERE deleted = FALSE` 的部分唯一索引？
- 工单表的 `UNIQUE (tenant_id, order_no)` 有没有同样的软删除问题？
- `@TableName(autoResultMap = true)` 开了吗？不加它 `attributes` 查询回来是 null，且不报错。
- `attributes` 的字段模板有没有约束？关键数值字段要参与统计的，是否该提升为独立列？
- 盘库是否用扫码枪 + 系统实时校验？"系统无、实物在"和"系统有、实物无"有没有明确的处理动作？
- 有没有定期跑三条治理 SQL：孤儿设备、逾期计划、状态与工单矛盾？
- 设备编号编码规则定死了吗？跨系统（SCADA/MES/QMS）用的是同一个 `asset_no` 吗？

## 十一、下一章预告：两个调度员同时点了"派工"

台账把"设备"这个主体立住了，状态也有了语义。但状态是会被并发修改的——尤其当它和"人"抢同一条记录的时候。

第八章讲一件真实发生过的事：白班调度和夜班交接的调度，在早上八点零五分同时点了同一张维修工单的"派工"，一个派给李师傅，一个派给小陈。两个人都收到了"成功"，李师傅八点半到现场，发现小陈已经在拆机了。这是典型的"读-改-写"竞态：`selectById` 查状态、判断合法、`updateById` 写回，三步之间没有任何锁。那一章讲三种锁方案的取舍（synchronized / 悲观锁 / 乐观锁）、`@Version` 在 MyBatis-Plus 里怎么生效、`updateById` 返回 0 行为什么必须翻译成"工单已被他人处理"，以及 100 并发压测下 37 次成功是怎么变成 1 次成功 99 次冲突的。
