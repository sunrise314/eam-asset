# 维修工单状态机：六状态与合法迁移

## 一、场景：一张被改回"待派工"的工单

2026 年 11 月 8 日下午 2 点，李师傅把 EQ-INJ-001 的液压泵密封件换完了，试机压力回到 14 MPa。他在后台点了"完工"，填了维修记录，工单状态变成"待验收"。

第二天上午，设备科验收通过，工单状态变成"已完成"，`finish_time` 是 11 月 8 日 14:00，`start_time` 是 11 月 8 日 10:00。一切正常。

问题出在一周后。另一个调度员在整理工单列表时，看到这张单"已完成"，觉得流程不对——"我记得这张单还没验收啊"，于是打开编辑页，把状态下拉框从"已完成"改成了"待派工"，又派给了另一个维修工。系统没有拦，因为那会儿的更新接口是个通用接口，前端传什么状态就写什么状态。

结果这张单变成了：`status = 1`（待派工），`start_time = 11-08 10:00`，`finish_time = 11-08 14:00`，`dispatch_time = 11-08 09:30`。新维修工重新派工、开工，`start_time` 被覆盖成 11-15 09:00，`finish_time` 还是 11-08 14:00。

月底我算 MTTR，这张单的"维修时长"是 `finish_time - start_time = -7 天 5 小时`。负七天。MTBF 也被带偏：本来这台设备 11 月只坏了一次，因为工单被"复活"又完成了一次，统计成了两次。

王主任拿着报表问我："这台机器上个月到底是修了一次还是两次？"我答不上来。不是数据丢了，是数据被"合法地"改乱了。

那次之后我做了两件事。第一，把通用更新接口里的 `status` 字段拿掉——状态不能由前端随便传，只能通过专门的动作接口改。第二，写一个 `RepairOrderStateMachine`，把所有合法迁移收在一张表里，Service 每个流转方法的第一行都过一遍校验。

这一章讲的就是这个状态机：六个状态、五条迁移边、为什么不用 Spring StateMachine、以及并发和乱序怎么防。

## 二、六个状态与五条迁移边

维修工单的状态枚举 `EamRepairStatus` 有六个值：

| code | 枚举常量 | 名称 | 含义 | 允许去向 |
|------|---------|------|------|---------|
| 1 | `PENDING_DISPATCH` | 待派工 | 报修已登记，还没指定维修人 | 2 已派工、6 已取消 |
| 2 | `DISPATCHED` | 已派工 | 已指定维修人，还没开工 | 3 维修中、6 已取消 |
| 3 | `REPAIRING` | 维修中 | 维修人已开工，正在处理 | 4 待验收、6 已取消 |
| 4 | `PENDING_ACCEPT` | 待验收 | 维修人已完工，等设备科验收 | 5 已完成 |
| 5 | `DONE` | 已完成 | 验收通过，工单闭环 | 无（终态） |
| 6 | `CANCELLED` | 已取消 | 误报、备件不到位等原因取消 | 无（终态） |

画成文字就是一条主干加三个分支：

```
待派工(1) ──→ 已派工(2) ──→ 维修中(3) ──→ 待验收(4) ──→ 已完成(5)
   │            │            │
   └────────────┴────────────┴──→ 已取消(6)
```

五个迁移"边"其实是四条主干边加一条取消边，但因为取消边有三个起点（1、2、3），迁移表里要写三条。所以严格说，这张表有 7 组合法迁移：

1 → 2、1 → 6、2 → 3、2 → 6、3 → 4、3 → 6、4 → 5。

有两个设计决定需要解释。

**为什么"待验收"不允许取消？** 因为活已经干完了。如果验收不通过，正确的动作是"驳回重修"，而不是"取消工单"。取消意味着这件事没发生，但维修工时、备件消耗都已经发生了，取消会让成本统计失真。演示仓库没有实现"驳回"这条边（4 → 3），只在注释里注明"有争议应走验收驳回而不是抹掉工单"。这是个已知缺口：真实车间里验收不通过是常态，商用版本必须补上 4 → 3，并记录驳回原因。

**为什么已完成、已取消没有出边？** 终态就是终态。一张已完成的工单如果要返修，应该新建一张工单，而不是把老单改回"维修中"。这样历史清晰：第一张单记录"第一次怎么修的"，第二张单记录"返修怎么修的"，MTBF 也能正确统计成两次故障。**允许终态回退，等于允许历史被改写。**

## 三、RepairOrderStateMachine：一张不可变 Map 就是全部规则

完整代码如下：

```java
package cn.iocoder.yudao.module.eam.framework.eam.repair;

import cn.iocoder.yudao.framework.common.exception.ErrorCode;
import cn.iocoder.yudao.framework.common.exception.util.ServiceExceptionUtil;
import cn.iocoder.yudao.module.eam.enums.EamRepairStatus;
import lombok.experimental.UtilityClass;

import java.util.Map;
import java.util.Set;

/**
 * 维修工单状态机：定义"待派工→已派工→维修中→待验收→已完成 / 已取消"的合法迁移。
 *
 * 为什么不用 Spring StateMachine：Spring StateMachine 面向"事件-动作-守卫"的复杂场景，
 * 配置/持久化/监听器一套下来要引入数个大件；维修工单一共 6 个状态、5 条迁移边，
 * 一张不可变 Map 就足以表达，且 canTransit 是纯查表——单测无需启动状态机容器。
 * 杀鸡不用牛刀：10 个状态以内 Map 驱动足够，状态再膨胀（加驳回/挂起/升级）时再评估升级。
 *
 * 迁移语义说明：
 * - 待派工/已派工/维修中 三个阶段允许取消（客户误报、备件不到位）
 * - 待验收不允许取消：活已经干完，有争议应走验收驳回而不是抹掉工单（演示仓库未展开驳回边）
 * - 已完成/已取消是终态，无任何出边
 */
@UtilityClass
public class RepairOrderStateMachine {

    /** 非法状态流转错误码（对外暴露，Service 层与全局异常处理统一文案） */
    public static final ErrorCode ERROR_CODE_ILLEGAL_TRANSITION =
            new ErrorCode(1_003_401, "维修工单状态流转非法: {} -> {}");

    /** 合法迁移表：key=源状态，value=允许到达的目标状态集合；5/6 为终态，无出边。 */
    private static final Map<Integer, Set<Integer>> TRANSITIONS = Map.of(
            EamRepairStatus.PENDING_DISPATCH.getCode(),
                    Set.of(EamRepairStatus.DISPATCHED.getCode(), EamRepairStatus.CANCELLED.getCode()),
            EamRepairStatus.DISPATCHED.getCode(),
                    Set.of(EamRepairStatus.REPAIRING.getCode(), EamRepairStatus.CANCELLED.getCode()),
            EamRepairStatus.REPAIRING.getCode(),
                    Set.of(EamRepairStatus.PENDING_ACCEPT.getCode(), EamRepairStatus.CANCELLED.getCode()),
            EamRepairStatus.PENDING_ACCEPT.getCode(),
                    Set.of(EamRepairStatus.DONE.getCode()),
            EamRepairStatus.DONE.getCode(), Set.of(),
            EamRepairStatus.CANCELLED.getCode(), Set.of()
    );

    /**
     * 判断是否允许从 from 流转到 to。
     *
     * @param from 源状态（当前工单状态）
     * @param to   目标状态
     * @return true=合法迁移
     */
    public static boolean canTransit(Integer from, Integer to) {
        if (from == null || to == null) {
            return false;
        }
        return TRANSITIONS.getOrDefault(from, Set.of()).contains(to);
    }

    /**
     * 断言 from -> to 是合法迁移，非法直接抛业务异常（ErrorCode 1_003_401）。
     * Service 层每个流转方法的第一行都应调用它。
     */
    public static void assertTransit(Integer from, Integer to) {
        if (!canTransit(from, to)) {
            throw ServiceExceptionUtil.exception(ERROR_CODE_ILLEGAL_TRANSITION, from, to);
        }
    }
}
```

这段代码有三个值得讲的地方。

### 3.1 为什么 `Map.of` 而不是 `HashMap`

`Map.of` 返回的是不可变 Map，`Set.of` 返回不可变 Set。这意味着迁移表在类加载后**不可能被任何代码修改**。状态机的规则必须是常量，如果它能在运行时被改，那"状态机"就变成了"状态建议"，谁都可以往里面加一条边，规则就失去意义了。

不可变还有两个附带好处：线程安全（多线程读没有可见性问题）、序列化安全（不怕被反序列化成可变对象）。这是"用最少的代码表达最强的约束"。

### 3.2 为什么终态要显式写 `Set.of()` 而不是省略

`TRANSITIONS.getOrDefault(from, Set.of())` 已经能处理"from 不在表里"的情况，返回空集合，`contains` 永远 false。那为什么还要显式写 `DONE -> Set.of()` 和 `CANCELLED -> Set.of()`？

因为**可读性和意图表达**。显式写出来，读代码的人一眼就知道"这两个是终态，故意没有出边"；如果省略，读者会怀疑"是不是漏了"。代码首先是写给人看的，其次才是给编译器看的。多两行，换一个"意图明确"，值得。

### 3.3 为什么 `canTransit` 要判空

因为 `from` 可能来自数据库的脏数据（比如手工插了 `status = null`），`to` 可能来自前端没传。判空返回 false，让 `assertTransit` 抛 1_003_401，比抛 `NullPointerException` 好——NPE 在日志里是一堆堆栈，业务异常是一句"状态流转非法: null -> 2"，运维一眼能看懂。

`assertTransit` 里还有一个细节：异常消息带两个占位符 `{} -> {}`，对应 `ErrorCode` 里的 `"维修工单状态流转非法: {} -> {}"`，`ServiceExceptionUtil.exception(code, from, to)` 会把两个状态填进去。这样前端拿到的错误信息是"维修工单状态流转非法: 5 -> 1"，而不是一句干巴巴的"系统错误"。**错误信息要能定位问题，不能只告诉用户"失败了"。**

## 四、为什么不用 Spring StateMachine

每次讲这个设计，都有人问："状态机不用 Spring StateMachine，是不是重复造轮子？"

我的回答是：轮子的大小要和车匹配。维修工单是 6 个状态、7 组迁移，用 Spring StateMachine 大概是这样一幅景象：

| 维度 | Spring StateMachine | 本项目的 Map |
|------|--------------------|-------------|
| 依赖 | `spring-statemachine-core` + 可能的 `spring-statemachine-data-jpa` | 零新增依赖，JDK 自带 `Map`/`Set` |
| 配置 | 一个 `@Configuration` 类、`StateMachineFactory`、`StateMachineConfigurerAdapter`、状态/事件枚举、迁移定义 | 一个 `Map.of(...)` |
| 持久化 | 需要配 `StateMachinePersister`，或者手工在业务表里存状态再恢复 | 状态本来就在业务表的 `status` 字段里 |
| 守卫/动作 | 支持 `Guard`、`Action`、`Listener`，功能强 | 需要自己写 if；本项目只有"校验 + 改字段" |
| 测试 | 启动状态机上下文，或用 `StateMachineTestPlan` | 直接调 `canTransit(1, 2)`，毫秒级 |
| 学习成本 | 新人要理解 state/event/transition/guard/action/persister 六个概念 | 新人看一张表就懂 |
| 适合场景 | 状态 > 10、有复杂守卫、需要分层状态、需要持久化恢复 | 状态 ≤ 10、迁移规则稳定、动作简单 |

Spring StateMachine 是好东西，但它解决的问题比我们复杂一个数量级。它面向的是"订单履约"那种场景：十几个状态、几十个事件、每个迁移带守卫条件（"库存够不够""支付有没有到账"）、需要把状态机实例持久化到 Redis 或数据库、需要分层状态（"维修中"下面再分"等件""等工"）。维修工单没有这些需求。

更现实的一点：**引入框架会增加排障成本。** 生产上出一张单流转不了，用 Map 的话，日志里一行"5 -> 1 非法"就定位了；用 Spring StateMachine 的话，要先确认事件有没有发出去、状态机有没有正确恢复、守卫是不是返回了 false、监听器有没有吞异常。多一层抽象，就多一层可能出错的地方。

我的判断标准是：**状态少于 10 个、迁移规则能用一张表写完、不需要持久化状态机实例，就用 Map。** 等到要加"驳回、挂起、升级、会签、超时自动关闭"这些边，状态膨胀到十几个，再评估引入框架。到那时迁移表会变得很难维护，框架的价值才显现出来。

## 五、Service 层：每个流转方法的第一行都是状态机

状态机只是规则，真正改数据的是 Service。五个流转方法，形状高度一致：

```java
// service/repairorder/EamRepairOrderServiceImpl.java（节选）
@Override
public void dispatch(Long id, Long assigneeId) {
    EamRepairOrderDO order = getRepairOrder(id);
    RepairOrderStateMachine.assertTransit(order.getStatus(), EamRepairStatus.DISPATCHED.getCode());
    // 在查出的整单上修改再 updateById：version 非空，乐观锁生效，并发派工只有一个成功
    order.setStatus(EamRepairStatus.DISPATCHED.getCode());
    order.setAssigneeId(assigneeId);
    order.setDispatchTime(LocalDateTime.now());
    repairOrderMapper.updateById(order);
}

@Override
public void start(Long id) {
    EamRepairOrderDO order = getRepairOrder(id);
    RepairOrderStateMachine.assertTransit(order.getStatus(), EamRepairStatus.REPAIRING.getCode());
    order.setStatus(EamRepairStatus.REPAIRING.getCode());
    order.setStartTime(LocalDateTime.now());
    repairOrderMapper.updateById(order);
}

@Override
public void finish(Long id, String repairNote) {
    EamRepairOrderDO order = getRepairOrder(id);
    RepairOrderStateMachine.assertTransit(order.getStatus(), EamRepairStatus.PENDING_ACCEPT.getCode());
    order.setStatus(EamRepairStatus.PENDING_ACCEPT.getCode());
    order.setFinishTime(LocalDateTime.now());
    order.setRepairNote(repairNote);
    repairOrderMapper.updateById(order);
}

@Override
public void accept(Long id, String acceptNote) {
    EamRepairOrderDO order = getRepairOrder(id);
    RepairOrderStateMachine.assertTransit(order.getStatus(), EamRepairStatus.DONE.getCode());
    order.setStatus(EamRepairStatus.DONE.getCode());
    order.setAcceptNote(acceptNote);
    repairOrderMapper.updateById(order);
}

@Override
public void cancel(Long id) {
    EamRepairOrderDO order = getRepairOrder(id);
    // 能否取消由状态机决定：1/2/3 → 6 合法，待验收与终态抛 1_003_401
    RepairOrderStateMachine.assertTransit(order.getStatus(), EamRepairStatus.CANCELLED.getCode());
    order.setStatus(EamRepairStatus.CANCELLED.getCode());
    repairOrderMapper.updateById(order);
}
```

五个方法的骨架完全一样：**取单 → 断言迁移 → 改状态 → 写时间/备注 → 更新**。逐点说。

**第一行永远是 `getRepairOrder(id)`。** 它不是简单查一下，而是查不到就抛 1_003_400（"维修工单不存在"）。这样后面的 `order.getStatus()` 不可能 NPE，也不需要每个方法都写一遍判空。

**第二行永远是 `assertTransit`。** 这是整个设计的核心：Service **不自己判断**"当前状态允不允许"。如果每个方法里写 `if (status == 2 || status == 3)`，规则就会散落在五个方法里，改一条边要改五处，早晚漂移。把规则收到状态机一处，Service 只负责"按规则执行"。

**改状态和写字段是绑定的。** `dispatch` 一定写 `assigneeId` 和 `dispatchTime`，`start` 一定写 `startTime`，`finish` 一定写 `finishTime` 和 `repairNote`，`accept` 一定写 `acceptNote`。这些字段就是"状态变化的证据"。如果只改状态不写时间，MTBF/MTTR 就没法算——第 6 章会讲，指标计算的前提是"每个状态变化都有时间戳"。

**`accept` 不写 `finishTime`。** 因为完工时间在 `finish` 时已经写了，验收只是确认。如果有人把验收时间也塞进 `finishTime`，MTTR 就会被拉长成"维修时长 + 等待验收时长"，指标失真。验收如果需要记时间，应该单独加 `accept_time` 字段——当前表没有，`accept_note` 只记了文字，这是个已知的小缺口。

**`cancel` 不改任何时间字段。** 取消的工单，`start_time` 可能已经有值（修到一半取消），保留它，因为"修了多久才放弃"是有价值的信息。`cancel` 也不写取消原因——表里没有 `cancel_reason` 字段。这是另一个已知缺口，商用版本应该补上。

Controller 层只是把这些方法暴露成 HTTP 接口，不做任何状态判断：

```java
// controller/admin/repairorder/EamRepairOrderController.java（节选）
@PutMapping("/dispatch")
@Operation(summary = "派工（待派工 → 已派工）")
public CommonResult<Boolean> dispatch(@RequestParam("id") Long id,
                                      @RequestParam("assigneeId") Long assigneeId) {
    repairOrderService.dispatch(id, assigneeId);
    return success(true);
}

@PutMapping("/start")
@Operation(summary = "开始维修（已派工 → 维修中）")
public CommonResult<Boolean> start(@RequestParam("id") Long id) {
    repairOrderService.start(id);
    return success(true);
}
```

接口名就是动作名：`/dispatch`、`/start`、`/finish`、`/accept`、`/cancel`。**不要做一个 `/update-status` 的万能接口**，那等于把状态机又打开了。前端只能调"派工""开工"这些动作，不能直接说"我要把状态改成 5"。这是"用 API 设计强制约束"——比文档里写"请不要随便改状态"有用一万倍。

## 六、设备状态联动：为什么用领域事件，而不是跨 Service 调用

维修工单和设备的 `status` 是有联动的：设备报修，设备状态应该变成"维修中"（3）；维修验收完成，设备状态应该回到"运行"（1）。这个联动看起来天经地义，但实现起来有个坑。

最直接的写法是：在 `EamRepairOrderServiceImpl` 里注入 `EamAssetService`，`accept` 方法里调 `assetService.updateStatus(assetId, RUNNING)`。问题是，设备侧也需要反向调用维修侧——设备报修时，`EamAssetServiceImpl` 要调 `repairOrderService.createRepairOrder(...)`。于是两个 Service 互相注入：

- `EamRepairOrderServiceImpl` 依赖 `EamAssetService`
- `EamAssetServiceImpl` 依赖 `EamRepairOrderService`

Spring 用构造器注入时，这会直接导致启动失败（Spring Boot 2.6 以后默认禁止循环依赖）。就算用 `@Lazy` 或字段注入绕过去，也是个定时炸弹：两个 Service 的生命周期绑死，单测要互相 mock，调用链一深就出现"谁先初始化"的问题。

所以当前代码**故意不注入** `EamAssetService`。`accept` 方法上方的注释写得很清楚：

```java
/**
 * 验收通过。
 *
 * 联动取舍：验收后设备理应从 REPAIRING 回 RUNNING，但此处故意不注入 EamAssetService——
 * repair→asset 调用会变成双向依赖（asset 报修时又想置 REPAIRING），演示仓库保持单向；
 * 商用建议完工/验收后发领域事件，由 asset 侧订阅改状态，两个 Service 彻底解耦。
 */
```

这段话是这一节的核心。当前实现的状态是：**联动规则写在了注释里，代码没做。** 这不是"忘了"，是"知道该怎么做，但演示版本选择了更简单的边界"。我要诚实地说明这一点，而不是假装系统已经联动。

商用版本的正确做法是领域事件。示意如下（非本仓库代码，只是扩展方向）：

```java
// 商用扩展示意：不是本仓库现有代码
// repair 侧：验收通过后发事件，不关心谁消费
eventPublisher.publishEvent(new RepairOrderAcceptedEvent(order.getId(), order.getAssetId()));

// asset 侧：事务提交后再改设备状态，避免工单回滚但设备已置 RUNNING
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onRepairOrderAccepted(RepairOrderAcceptedEvent event) {
    assetMapper.updateStatus(event.assetId(), EamAssetStatus.RUNNING.getCode());
}
```

三个关键点：

**第一，发事件方不依赖接收方。** `repair` 只知道"我验收完了"，不知道"谁会来处理"。这样 `repair → asset` 的编译期依赖就断了，循环依赖自然消失。以后要加"验收后通知采购""验收后触发备件补货"，只需新增监听器，不用改 `repair` 的代码。

**第二，用 `@TransactionalEventListener` 而不是 `@EventListener`。** 前者默认在事务提交后执行（`AFTER_COMMIT`），后者在事件发布时同步执行。如果用普通的 `@EventListener`，工单事务还没提交，设备状态已经改成 RUNNING 了；万一工单事务回滚，设备状态就变成了"运行中但工单不存在"的脏状态。用 `AFTER_COMMIT`，只有工单真的落库了，才改设备状态。

**第三，事件要带最小必要信息。** `assetId` 和 `orderId` 就够了，不要把整个 DO 塞进去。事件是"发生了什么"的声明，不是"数据快照"。接收方如果需要更多字段，自己按 id 查，这样事件不会因为 DO 加字段而变得臃肿。

什么时候该用事件，什么时候该直接调用？我的判断标准是：**调用方不需要返回值、且被调用方可能失败但不应该回滚调用方，就用事件。** 设备状态联动符合这两条：验收不需要知道设备状态改没改成功；设备状态改失败也不应该让验收回滚（否则工单永远验收不了）。反过来，"扣库存"就不能用事件，因为库存不足必须让出库失败——那是强一致，必须同步调用、同一事务。

## 七、乱序、重复、并发：三道闸门

状态机是规则，但规则要被"执行"才有用。执行层面有三类问题：乱序、重复、并发。

### 7.1 乱序：跳步和回退

跳步是指"待派工"直接到"待验收"，回退是指"已完成"回到"待派工"。这两种在当前实现里都会被 `assertTransit` 拦住：

- `accept(id)` 在 `status = 1` 时调用：`assertTransit(1, 5)` → `TRANSITIONS.get(1) = {2, 6}`，不包含 5 → 抛 1_003_401。
- `dispatch(id)` 在 `status = 5` 时调用：`assertTransit(5, 2)` → `TRANSITIONS.get(5) = {}` → 抛 1_003_401。

前端拿到的错误是"维修工单状态流转非法: 1 -> 5"，用户一看就知道"哦，还没派工，不能直接验收"。

### 7.2 重复：同一状态再流转一次

重复派工：工单已经是 `status = 2`（已派工），再调一次 `dispatch`。`assertTransit(2, 2)` → `TRANSITIONS.get(2) = {3, 6}`，不包含 2 → 抛 1_003_401。

注意这一点：**状态机连"自己到自己"都不允许。** 有些人会把 `2 -> 2` 加进去，觉得"重复派工是幂等，应该允许"。我不这么看：重复派工意味着"换人"，换人应该是一个独立的"改派"动作（带改派原因、通知原维修人），而不是悄悄把 `assigneeId` 覆盖掉。允许 `2 -> 2` 会让"谁在修"变得不可追溯。所以宁可报错，让用户走"取消 + 重新派工"或者未来的"改派"接口。

### 7.3 并发：两个调度员同时派工

这是最隐蔽的一类。两个调度员同时打开同一张"待派工"的工单，一个派给李师傅，一个派给张师傅，同时点"确定"。

时间线是这样的：

| 时刻 | 线程 A（派李师傅） | 线程 B（派张师傅） |
|------|------------------|------------------|
| T1 | 读工单，status=1，version=0 | |
| T2 | `assertTransit(1, 2)` 通过 | 读工单，status=1，version=0 |
| T3 | 改 status=2、assignee=李，update 成功，version=1 | `assertTransit(1, 2)` 通过 |
| T4 | | 改 status=2、assignee=张，update 时 version 还是 0 |

线程 B 的 `updateById` 带的是 `WHERE id = ? AND version = 0`，而此时库里 version 已经是 1，所以更新影响 0 行。乐观锁生效，张师傅的派工没有覆盖李师傅的。

这就是 `EamRepairOrderDO` 上 `@Version` 的作用：

```java
/** 乐观锁版本号 */
@Version
private Integer version;
```

配合 MyBatis-Plus 的 `OptimisticLockerInnerInterceptor`，`updateById` 会自动把 `version` 加进 WHERE 条件，并在成功后 `version + 1`。不需要手写 SQL，也不需要加锁。但有个前提：拦截器必须在 MyBatis 配置里注册，否则 `@Version` 只是一个普通字段，SQL 里根本不会带版本条件。本模块的 `EamConfiguration` 只做了 Mapper 扫描，拦截器由父工程的 MyBatis 配置统一提供；如果把模块单独拎出来跑，记得自己注册。

但这里有个**必须说清楚的坑**：`updateById` 返回的是"影响行数"，当前 Service 代码把返回值丢掉了：

```java
repairOrderMapper.updateById(order);   // 返回 int，被忽略
```

这意味着并发冲突时，线程 B 的请求会"静默成功"——Controller 返回 `true`，用户以为派工成功了，其实什么都没改。正确做法是检查返回值：

```java
// 商用改造：乐观锁冲突时明确报错，而不是静默成功
int rows = repairOrderMapper.updateById(order);
if (rows == 0) {
    throw ServiceExceptionUtil.exception(ERROR_CODE_CONCURRENT_CONFLICT, id);
}
```

这是演示仓库的一个真实缺陷，第 8 章会展开讲乐观锁的完整用法。这里先记住结论：**状态机防的是"逻辑上不该发生"的流转，乐观锁防的是"并发下同时发生"的流转。两道闸门缺一不可，而且第二道闸门必须检查返回值，否则等于没关。**

顺带说一句为什么不用悲观锁（`SELECT ... FOR UPDATE`）。维修工单的并发冲突概率很低（一天几十张单，两个调度员同时点同一张单是极小概率），悲观锁会让每次派工都占一行锁，收益不值得。乐观锁无锁读、冲突时失败，更适合这种"低冲突、可重试"的场景。如果是备件扣减那种"高冲突、必须成功"的场景，反而应该用悲观锁或原子 SQL——第 5 章会讲。

## 八、一张工单的完整生命周期流水

把种子数据里的 `RO-20261108-001` 展开，如果这张单从头走一遍，完整流水如下（version 每次 update 递增 1）。注意种子数据是直接导入的快照，`version` 记为 2，不必和推演值一致：

| 时间 | 动作 | 操作人 | 状态变化 | 写入字段 | version |
|------|------|--------|---------|---------|---------|
| 11-08 07:40 | 报修 | 张三 | — → 1 待派工 | orderNo、assetId=3、faultDesc、priority=3、reporter | 0 |
| 11-08 09:30 | 派工 | 王主任 | 1 → 2 已派工 | assigneeId=1002、dispatchTime | 1 |
| 11-08 10:00 | 开工 | 李师傅 | 2 → 3 维修中 | startTime | 2 |
| 11-08 14:00 | 完工 | 李师傅 | 3 → 4 待验收 | finishTime、repairNote | 3 |
| 11-09 09:00 | 验收 | 王主任 | 4 → 5 已完成 | acceptNote | 4 |

对应的接口调用：

```text
POST /api/admin/eam/repair-order/create
PUT  /api/admin/eam/repair-order/dispatch?id=1&assigneeId=1002
PUT  /api/admin/eam/repair-order/start?id=1
PUT  /api/admin/eam/repair-order/finish?id=1&repairNote=更换液压泵密封件，压力恢复正常
PUT  /api/admin/eam/repair-order/accept?id=1&acceptNote=试机2小时无异常，验收通过
```

这条流水里有三个时间戳，它们定义了三个区间：

- `dispatchTime → startTime`：等待开工，30 分钟。反映调度效率。
- `startTime → finishTime`：维修时长，4 小时。这是 MTTR 的分子。
- `finishTime → 验收`：等待验收，19 小时。反映验收流程的效率，不计入 MTTR。

如果状态机被绕过，比如"待派工"直接"已完成"，那么 `startTime` 和 `finishTime` 都是 null，MTTR 就没有分子；如果工单被改回"待派工"再走一遍，`startTime` 被覆盖成第二次的时间，`finishTime` 还是第一次的，就会出现负数时长。**状态机的价值，最终体现在这张流水表的每一行都不可跳过、不可回退、不可覆盖。**

再看一个"被拒绝"的流水，验证错误码：

| 时间 | 动作 | 当前状态 | 目标状态 | 结果 |
|------|------|---------|---------|------|
| 11-08 09:00 | 验收 | 1 待派工 | 5 已完成 | 拒绝，1_003_401：状态流转非法: 1 -> 5 |
| 11-08 09:05 | 重复派工 | 2 已派工 | 2 已派工 | 拒绝，1_003_401：状态流转非法: 2 -> 2 |
| 11-10 10:00 | 回退 | 5 已完成 | 1 待派工 | 拒绝，1_003_401：状态流转非法: 5 -> 1 |
| 11-10 10:05 | 取消待验收 | 4 待验收 | 6 已取消 | 拒绝，1_003_401：状态流转非法: 4 -> 6 |

这四条拒绝，就是"数据不会再被改乱"的证明。

## 九、状态机与指标：为什么它决定了 MTBF 能不能算

第 6 章会讲 MTBF/MTTR 的计算，但这里要先埋一个伏笔：**指标的可信度，取决于状态机的严格程度。**

MTTR 的公式是"总维修时长 ÷ 故障次数"，维修时长取 `finishTime - startTime`。这个公式成立的前提是：

1. 每张完成的工单都有 `startTime` 和 `finishTime`；
2. `finishTime` 一定晚于 `startTime`；
3. 一张工单只对应一次故障，不会被"复活"成两次。

状态机恰好保证了这三点：4 → 5 之前必须经过 3（维修中），而进入 3 一定写 `startTime`，进入 4 一定写 `finishTime`；终态不能回退，所以一张单不会变成两次故障。

反过来，如果没有状态机，用通用 update 随便改状态，这三点全部失守：可以没有 `startTime` 就"完成"；可以把 `finishTime` 改到 `startTime` 之前；可以把已完成的单改回待派工再完成一次。这时候算出来的 MTBF/MTTR 不是"设备可靠性指标"，是"数据质量指标"。

所以我常说：**状态机不是为了流程图好看，是为了让指标可算。** 很多工厂上 EAM，看板做得很漂亮，MTBF 曲线一路向好，但一问"工单状态有没有约束"，答案是"随便改"。那这条曲线就是假的，越好看越危险。

还有一个小细节：`calcMetrics` 只取 `status = DONE` 的工单。

```java
// 只取窗口内已完成的工单：进行中的工单维修时长未定，纳入会虚增维修时长
List<EamRepairOrderDO> doneOrders = repairOrderMapper.selectDoneList(assetId, windowStart, windowEnd);
return MtbfCalculator.calc(assetId, doneOrders, windowStart, windowEnd);
```

为什么排除"已取消"？因为取消的工单可能根本没修（误报），把它算进故障次数会虚增故障率。为什么排除"维修中"和"待验收"？因为它们的 `finishTime` 还没有值，纳入会得到一个偏小的 MTTR（分母有、分子没有）。**统计口径必须和状态定义严格对齐，否则指标就是自欺欺人。**

## 十、商用化检查清单（状态机版）

- 通用 `update` 接口是否还允许改 `status`？必须拿掉，状态只能通过动作接口改。
- 五个流转方法的 `updateById` 返回值是否检查了？不检查等于乐观锁白配。
- 验收不通过（4 → 3 驳回）的边要不要补？真实车间里验收驳回是常态。
- 取消原因 `cancelReason` 字段要不要加？当前只改状态，不记录为什么取消。
- 验收时间 `acceptTime` 字段要不要加？当前只有 `acceptNote`。
- 设备状态联动是否实现了？当前只在注释里说明，未跨 Service 调用。
- 领域事件是否用 `@TransactionalEventListener(AFTER_COMMIT)`？用普通监听器会有事务不一致风险。
- 已完成工单返修，是新建工单还是改老单？必须是新建，终态不可回退。
- 状态枚举 code 是否和前端字典对齐？漏配会导致状态下拉框空白。
- 非法流转的异常信息是否带 from/to？不带的话现场无法定位。
- 并发冲突的错误码是否单独定义？复用 1_003_401 会让用户误以为"状态不对"，其实是"被人抢先改了"。
- 维修工单删除接口是否该保留？已完成的工单不应该允许物理/逻辑删除，会破坏历史。
