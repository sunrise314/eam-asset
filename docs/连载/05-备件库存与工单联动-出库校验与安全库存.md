# 备件库存与工单联动：出库校验与安全库存

## 一、场景：月底盘库，少了 47 个轴承

2026 年 11 月 30 日，月底盘库。库管老周拿着盘点表，一格一格对货架，对到 A 库 01-03 时停住了：主轴轴承账面 30 套，实际数出来 27 套。少了 3 套。

王主任让他把整个月的账翻一遍。老周的账本是一本横线本，每一页一个备件，写"日期、领用人、数量、结存"。翻完主轴轴承那一页，11 月一共 6 笔领用，加起来 15 套；期初 42 套，42 减 15 等于 27，和实物对得上。问题出在"期初 42"这个数——上个月底盘库的时候，账上写的是 45。

再往前翻，10 月领了 8 套，9 月领了 11 套，每月的账都"大概对得上"，但把三个月的领用加起来，和年初至今的出库总量差了 47 套。这 47 套去哪了？老周说不清。领料条子有的写了名字没写数量，有的写了数量没写设备，还有几张压在抽屉底下忘了登记。李师傅说"我记得领过"，但记不清是 3 套还是 5 套。

这不是老周不负责，是流程有洞。**库存变动没有和业务单据绑定**：领料是"人到库房、报个数、拿走"，账本是"事后补记"，中间没有任何强制的校验和记录。漏记一次，账实就偏一次；偏了之后没人发现，因为账本只记"当前数量"，不记"每一次为什么变"。

我后来给王主任算了一笔账：47 套主轴轴承，按采购价 280 元一套，是 1.3 万；但这只是账面损失。更麻烦的是，因为账上显示"还有 30 套"，采购没补货，等到 12 月中旬一台加工中心真需要换轴承时，库房只剩 2 套，又断货了——**账实不符的代价，最后都落在停机时间上。**

这一章讲备件模块怎么解决这个问题：为什么必须有流水表、出库怎么校验、安全库存怎么预警、高并发怎么防超卖、以及备件和设备的关系怎么表达。

## 二、为什么必须有流水表，而不是只改库存字段

最省事的做法是只留一张 `eam_spare_part` 表，出库时 `stock = stock - 3`，完事。很多小系统就是这么做的。它的问题不在"算错了"，而在"算错了查不出来"。

一张只有当前库存的表，能回答"现在有多少"，回答不了这四个问题：

- 这批货是谁领的？
- 用在哪台设备、哪张工单上？
- 这个月这个备件消耗了多少？
- 账面和实物对不上，是哪几笔出的问题？

所以 `eam_spare_record` 不是"额外的表"，它是库存的**账本**。`eam_spare_part.stock` 只是账本的"当前余额"，`eam_spare_record` 才是"每一笔流水"。两者必须同时存在，而且必须同时更新。

| 维度 | 只改 stock | stock + 流水 |
|------|-----------|-------------|
| 当前库存 | 有 | 有 |
| 谁领的 | 无 | `operator` |
| 用在哪 | 无 | `biz_order_no` 关联工单 |
| 月消耗量 | 要月底盘库倒推 | `SUM(quantity) WHERE type=2` |
| 账实差异定位 | 查不出 | 逐笔对流水 |
| 误操作修正 | 直接改数，无痕 | 反向流水冲正，留痕 |
| 成本归集 | 做不到 | 按工单/设备归集 |
| 审计 | 不通过 | 通过 |

流水表的设计有三个铁律，第 2 章提过，这里结合代码再讲一遍。

**第一，`quantity` 恒为正数，方向由 `type` 表达。** `EamSpareRecordType` 三个值：1 入库、2 出库、3 退库。不要用"入库 +5、出库 -5"的有符号数量，因为那样所有统计都变成 `SUM(quantity)`，一旦有人把 type 和符号搞混，就会出现"入库 5、出库 5、总和 0"的诡异结果。无符号数量 + 显式类型，方向永远清楚。

**第二，流水只增不改。** `EamSpareRecordService` 只有 `createRecord`、`getRecord`、`getRecordListByPartId`、`getRecordPage`，没有 `updateRecord`，也没有 `deleteRecord`。错了怎么办？用反向流水冲正：出库错了就入库一笔，备注写"冲正，原因 XXX"。这样历史永远完整，审计能看到"错了—改了"的全过程，而不是"看起来一直是对的"。

**第三，`stock` 只能由出入库改变。** 这条规则写在 `updateSparePart` 的注释里，也写在代码里：

```java
// service/sparepart/EamSparePartServiceImpl.java（节选）
@Override
public void updateSparePart(EamSparePartSaveReqVO updateReqVO) {
    validatePartExists(updateReqVO.id());
    EamSparePartDO updateObj = new EamSparePartDO();
    updateObj.setId(updateReqVO.id());
    updateObj.setPartNo(updateReqVO.partNo());
    updateObj.setName(updateReqVO.name());
    updateObj.setSpec(updateReqVO.spec());
    updateObj.setUnit(updateReqVO.unit());
    // 注意：更新主数据不动 stock，库存只能由出入库流水改变
    updateObj.setSafetyStock(updateReqVO.safetyStock());
    updateObj.setAssetIds(updateReqVO.assetIds());
    updateObj.setLocation(updateReqVO.location());
    updateObj.setRemark(updateReqVO.remark());
    sparePartMapper.updateById(updateObj);
}
```

注意 `updateObj` 里**没有 `setStock`**。前端就算在表单里传了 `stock`，这个接口也不会写。这是"用代码结构强制规则"——不是靠文档说"请不要改库存"，而是让改库存这条路根本不存在。

但这里有个缺口要诚实指出：`createSparePart` 是允许直接设 `stock` 的（`part.setStock(createReqVO.stock() != null ? ... : 0)`）。这意味着"期初库存"是直接写进 `stock` 的，没有对应的入库流水。所以建账第一天，`stock` 和流水就对不上。正确的做法是把期初库存也写成一条入库流水（`type=1`，`bizOrderNo` 填"期初建账"），或者加一个 `OPENING` 类型。演示版本没做，这是"账实对不上"的又一个隐式来源。

## 三、inbound / outbound：改库存和写流水必须同生共死

核心代码在 `EamSparePartServiceImpl`，两个方法：

```java
/**
 * 入库。退库（维修剩余件返还）复用本方法，bizOrderNo 带原出库单号即可对冲。
 */
@Override
@Transactional(rollbackFor = Exception.class)
public EamSparePartDO inbound(Long partId, Integer quantity, String bizOrderNo, String operator) {
    EamSparePartDO part = getSparePart(partId);
    part.setStock((part.getStock() != null ? part.getStock() : 0) + quantity);
    sparePartMapper.updateById(part);
    writeRecord(partId, EamSpareRecordType.IN.getCode(), quantity, bizOrderNo, operator);
    return part;
}

/**
 * 出库。库存不足直接抛 1_003_301，不允许扣成负数。
 *
 * 并发取舍：演示仓库先读后写；商用高并发应改原子 SQL
 * UPDATE eam_spare_part SET stock = stock - #{quantity} WHERE id = #{id} AND stock >= #{quantity}，
 * 影响行数为 0 即库存不足，避免两个并发出库都读到旧库存导致超卖。
 *
 * 低库存预警：后端不内嵌告警通道（无 MQ/通知依赖），把最新 stock/safetyStock 随返回值带出，
 * 前端比对 stock < safetyStock 即亮预警；商用可在此发领域事件接通知中心。
 */
@Override
@Transactional(rollbackFor = Exception.class)
public EamSparePartDO outbound(Long partId, Integer quantity, String bizOrderNo, String operator) {
    EamSparePartDO part = getSparePart(partId);
    int stock = part.getStock() != null ? part.getStock() : 0;
    if (stock < quantity) {
        throw ServiceExceptionUtil.exception(ERROR_CODE_STOCK_NOT_ENOUGH, stock, quantity);
    }
    part.setStock(stock - quantity);
    sparePartMapper.updateById(part);
    writeRecord(partId, EamSpareRecordType.OUT.getCode(), quantity, bizOrderNo, operator);
    return part;
}

private void writeRecord(Long partId, Integer type, Integer quantity, String bizOrderNo, String operator) {
    EamSpareRecordDO record = new EamSpareRecordDO();
    record.setPartId(partId);
    record.setType(type);
    record.setQuantity(quantity);
    record.setBizOrderNo(bizOrderNo);
    record.setOperator(operator);
    spareRecordService.createRecord(record);
}
```

### 3.1 两个 ErrorCode

类顶部定义了两个错误码：

```java
private static final ErrorCode ERROR_CODE_NOT_EXISTS = new ErrorCode(1_003_300, "备件不存在: id={}");
private static final ErrorCode ERROR_CODE_STOCK_NOT_ENOUGH = new ErrorCode(1_003_301, "备件库存不足: 当前库存={}, 需出库={}");
```

`1_003_301` 这个消息模板带了两个占位符，抛的时候传 `stock` 和 `quantity`，前端拿到的是"备件库存不足: 当前库存=2, 需出库=3"，而不是干巴巴的"操作失败"。库管看到这句话，立刻知道"差 1 个，要么少领，要么等采购"。**错误信息要带上下文，这是工业软件和玩具系统的区别之一。**

`1_003_300` 是"备件不存在"，`1_003_302` 是"流水不存在"（在 `EamSpareRecordServiceImpl` 里）。三个错误码连号，前缀都是 `1_003_`，第三段是模块内序号。这种编码方式在芋道里很常见，好处是"看错误码就知道哪个模块出的问题"。

### 3.2 为什么必须 `@Transactional(rollbackFor = Exception.class)`

`outbound` 做了两件写操作：改 `stock`、插流水。这两件事必须同生共死。

- 如果改完库存、插流水失败（比如数据库连接断了），库存少了但流水没有——月底对账又对不上，而且不知道这 3 个件去哪了。
- 如果先插流水、改库存失败，流水说"出了 3 个"，库存没变——账面虚高，下次还能再出 3 个，超卖。

加上事务，两件事要么都成功，要么都回滚。这是"库存和流水必须一致"的最基本保障。

`rollbackFor = Exception.class` 不能省。Spring 默认只对 `RuntimeException` 和 `Error` 回滚，受检异常（`Exception` 的子类但不是 `RuntimeException`）不回滚。虽然这里的异常都是运行时异常，但显式写 `rollbackFor = Exception.class` 是个好习惯——以后有人加了 `throws IOException`，事务行为不会莫名其妙地变。

## 四、事务内校验 + 扣减：为什么不能先查后扣

`outbound` 的顺序是：**查 → 校验 → 扣 → 写流水**，全部在一个事务里。

有人会问：既然都加了事务，为什么还会有并发问题？事务不是万能的吗？

事务保证的是 ACID，但默认的隔离级别（PostgreSQL 是 READ COMMITTED，MySQL 默认 REPEATABLE READ）下，"读"和"写"之间仍然可能被其他事务插入。看这个时间线（库存 8，两个请求各出 5）：

| 时刻 | 事务 A | 事务 B | 数据库 stock |
|------|--------|--------|-------------|
| T1 | 读 stock=8 | | 8 |
| T2 | | 读 stock=8 | 8 |
| T3 | 校验 8 >= 5 通过 | | 8 |
| T4 | | 校验 8 >= 5 通过 | 8 |
| T5 | 写 stock=3，提交 | | 3 |
| T6 | | 写 stock=3，提交 | 3 |

两个请求都成功了，实际出了 10 个，账面只剩 3 个。少掉的 5 个就是"超卖"。事务没有拦住，因为两个事务读的都是"当时已提交的最新值"（8），写的时候也没有互相看见。

这就是 READ COMMITTED 下的经典"读-改-写"竞态。要解决，有三条路：

**方案 A：悲观锁。** 在查询时加 `SELECT ... FOR UPDATE`，锁住这一行，事务 B 必须等 A 提交才能读。缺点是持锁时间长，热点备件会把并发度压成串行。

**方案 B：原子 SQL。** 把"校验"和"扣减"合成一条 UPDATE：

```sql
UPDATE eam_spare_part
SET stock = stock - #{quantity}, update_time = NOW()
WHERE id = #{id}
  AND deleted = FALSE
  AND stock >= #{quantity}
```

这条 SQL 在数据库内部对行加锁，`stock >= quantity` 的判断和 `stock - quantity` 的写入是原子的。影响行数为 1 表示扣减成功，为 0 表示库存不足（或备件不存在）。不会出现两个事务都成功的情况。

**方案 C：乐观锁。** 给备件表加 `version`，扣减时 `WHERE version = ?`，冲突就重试。缺点是热点备件冲突率高，重试次数多，反而更慢。

对备件扣减这种"写多、冲突必须失败而不是重试"的场景，**方案 B 是最优解**。当前演示仓库用的是"先读后写"（方案 A 的简化版，但没加 `FOR UPDATE`），注释里已经明确写了这是取舍，商用要改成原子 SQL。

商用改造的 Mapper 方法大致是这样（**非本仓库现有代码，是改造方向**）：

```java
// 商用扩展示意：不是本仓库现有代码
@Update("UPDATE eam_spare_part SET stock = stock - #{quantity}, update_time = NOW() " +
        "WHERE id = #{id} AND deleted = FALSE AND stock >= #{quantity}")
int deductStock(@Param("id") Long id, @Param("quantity") Integer quantity);
```

Service 里：

```java
// 商用扩展示意：不是本仓库现有代码
int rows = sparePartMapper.deductStock(partId, quantity);
if (rows == 0) {
    EamSparePartDO part = getSparePart(partId);   // 为了拿到当前库存拼错误信息
    throw ServiceExceptionUtil.exception(ERROR_CODE_STOCK_NOT_ENOUGH, part.getStock(), quantity);
}
writeRecord(partId, EamSpareRecordType.OUT.getCode(), quantity, bizOrderNo, operator);
```

注意执行顺序：**先扣减，再写流水**。因为扣减会拿行锁，后面的流水插入在同一个事务里；如果流水插入失败，事务回滚，扣减也回滚。反过来"先写流水再扣减"也行，但扣减失败时要靠事务回滚流水，日志里会先出现一条"看起来成功"的流水，排查时容易误判。先做"可能失败的那一步"，失败就早退，逻辑更干净。

## 五、安全库存预警：为什么放在返回值里，而不是后端直接告警

`outbound` 返回的是 `EamSparePartDO`，Controller 转成 `EamSparePartRespVO`，里面带 `stock` 和 `safetyStock`：

```java
// controller/admin/sparepart/EamSparePartController.java（节选）
@PostMapping("/outbound")
@Operation(summary = "备件出库（库存不足报错；返回最新备件，前端比对 stock < safetyStock 亮预警）")
public CommonResult<EamSparePartRespVO> outbound(@RequestParam("partId") Long partId,
                                                 @RequestParam("quantity") Integer quantity,
                                                 @RequestParam(value = "bizOrderNo", required = false) String bizOrderNo,
                                                 @RequestParam(value = "operator", required = false) String operator) {
    return success(toRespVO(sparePartService.outbound(partId, quantity, bizOrderNo, operator)));
}
```

前端的逻辑是：拿到返回值，如果 `stock < safetyStock`，把这一行标红，弹一个"库存不足，请及时补货"的提示。

为什么不在后端直接告警（发短信、发钉钉、写告警表）？三个理由。

**第一，没有基础设施依赖。** 这个模块只依赖芋道的基础框架，没有接 MQ、没有接通知中心。如果为了一个预警去引一套消息队列，等于为了一个功能拖进来一个中间件，部署、运维、监控全要跟着上。演示版本刻意不背这个包袱。

**第二，告警渠道是"基础设施"，不是"业务逻辑"。** 发短信还是发飞书，是运维配置；"库存低于安全线"才是业务规则。把渠道写进 Service，等于把业务逻辑和运维绑死。正确的做法是 Service 发一个领域事件 `StockBelowSafetyEvent`，通知中心去订阅，想发什么渠道发什么渠道。

**第三，前端比对能让用户"当场看见"。** 库管出库完，页面立刻标红，这是最有效的提醒。后端发短信是异步的，可能延迟几分钟，也可能被当成垃圾短信忽略。对于"这次出库之后库存不够了"这种即时场景，前端提示更直接。

但前端比对也有明显的代价：

| 方案 | 优点 | 缺点 | 适合 |
|------|------|------|------|
| 前端比对返回值 | 零依赖、即时、实现简单 | 用户不刷新就看不到；每个入口都要写一遍；无法通知不在场的人 | 演示、单机、库管当场操作 |
| 后端发领域事件 + 通知中心 | 渠道可配、能通知采购、可留痕 | 要引 MQ/通知中心，链路长，排查复杂 | 商用、多角色协同 |
| 定时扫描低库存清单 | 不依赖出库动作、能覆盖"没出库但低于安全线"的情况 | 有延迟（分钟级）、要额外的调度任务 | 商用、日报/晨会 |

注意第三种：**"低于安全库存"不一定发生在出库那一刻。** 比如安全库存从 3 调到 5，当前库存 4，没出库，但已经低于安全线了。前端比对只在出库/入库的返回值里做，这种情况就漏了。所以商用版本最好是"事件 + 定时扫描"双保险：出库触发实时提醒，每天凌晨再扫一遍全量低库存清单。

回到种子数据：SP-SEAL-002 的 `stock = 2`，`safety_stock = 5`，本来就已经低于安全线。如果再出库 1 个，`stock = 1`，前端比较 `1 < 5`，标红；再出库 2 个，`1 < 2`，直接抛 1_003_301。这个数据是特意配的，就为了演示"预警"和"拒绝"两个分支。

## 六、备件与设备的关联：assetIds JSONB 的用法与局限

第 2 章讲过 `asset_ids` 为什么用 JSONB 数组，这里讲它怎么用、哪里会疼。

`EamSparePartDO` 里：

```java
/** 适用设备 ID 列表（JSONB），如 [1,2] */
@TableField(typeHandler = JacksonTypeHandler.class)
private List<Long> assetIds;
```

前端展示"这个备件能用在哪些设备"时，拿 `assetIds` 去匹配设备列表，一次查询就够。写入时，表单里勾选设备，传一个 ID 数组，`JacksonTypeHandler` 自动序列化成 `[1,2]` 存进 JSONB。

种子数据里：

- SP-BEAR-001（主轴轴承）`asset_ids = [1,2]`，适用于数控车床和加工中心。
- SP-SEAL-002（液压密封件包）`asset_ids = [3]`，只适用于注塑机。

这个设计在小规模下很舒服。但三种查询会疼：

**第一种：查"这台设备用哪些备件"。**

```sql
SELECT * FROM eam_spare_part
WHERE asset_ids @> '[3]'::jsonb
  AND deleted = FALSE;
```

`@>` 是"包含"操作符，语义正确。但没有 GIN 索引时，这是全表扫描 + 逐行解析 JSON。备件几百个时没感觉，几千个时明显，几万个时就是事故。

解法是加 GIN 索引：

```sql
CREATE INDEX idx_eam_spare_part_asset_ids
    ON eam_spare_part USING GIN (asset_ids);
```

加了索引之后，`@>` 能走索引，查询从 O(n) 降到接近 O(log n)。但注意：GIN 索引对写入有开销，每次更新 `asset_ids` 都要重建索引项。备件主数据更新频率低，这个代价可以接受。

**第二种：查"这个备件用在哪台设备的哪个部位"。**

JSONB 数组只能表达"有关系"，表达不了"关系是什么"。如果业务需要记录"这个轴承装在主轴前端""这个密封件装在液压泵出口"，数组就不够了。得拆关联表：

```sql
CREATE TABLE eam_spare_asset (
    part_id         BIGINT NOT NULL,
    asset_id        BIGINT NOT NULL,
    install_position VARCHAR(64),   -- 装配位置
    quantity_per_asset INT,         -- 单机用量
    PRIMARY KEY (part_id, asset_id)
);
```

**第三种：设备报废后的残留。** `asset_ids` 里存的是设备 ID，没有外键。设备报废或删除后，ID 还留在数组里，查出来是"幽灵设备"。JSONB 数组不会报错，也不会自动清理。商用版本需要定期跑一致性校验，或者干脆改成关联表 + 外键。

所以 `assetIds` 的适用边界很清楚：**关系弱、只读展示、规模小、不需要记录关系属性**。超过这个边界，就该拆表。这不是"JSONB 好不好"的问题，是"反范式的收益能不能覆盖它的代价"的问题。

## 七、流水和工单：为什么用字符串弱关联

`eam_spare_record.biz_order_no` 存的是工单号字符串，比如 `RO-20261108-001`，没有外键指向 `eam_repair_order.id`。

为什么不用外键？因为流水不只挂维修工单。它可能挂：

- 维修工单：`RO-20261108-001`
- 采购入库单：`PO-20261101-003`
- 退库单：原出库工单号
- 盘点调整：`CHECK-20261130`
- 期初建账：`OPENING-2026`

如果建外键，就得建四五个可空的外键列，或者建一张"业务单据类型 + 单据 ID"的多态关联表。前者让表变宽、查询变复杂；后者是典型的"多态关联反模式"，查起来要 UNION。

用字符串统一表达"这笔流水属于哪个业务动作"，简单、灵活、够用。代价是没有引用完整性：

- 工单号填错了，系统不知道。比如把 `RO-20261108-001` 写成 `RO-20261188-001`，流水照样插入，但对账时挂不上工单。
- 工单被删了，流水还在，`biz_order_no` 指向一个不存在的单。
- 统计"这张工单领了多少件"时，只能按字符串匹配，没有索引就会慢。所以要建索引：

```sql
CREATE INDEX idx_eam_spare_record_biz
    ON eam_spare_record(biz_order_no);
```

这个取舍的本质是：**强关联保证正确性，弱关联保证灵活性。** 流水是"审计日志"，它的第一诉求是"记下来"，不是"保证关联对象存在"。如果为了外键把采购入库、退库、盘点都挡在门外，那是本末倒置。

商用版本可以在"应用层"补强关联：出库接口加一个可选的 `repairOrderId` 参数，如果传了，先校验工单存在且状态是"维修中"，再写流水，`biz_order_no` 从工单查出来填。这样既保留了字符串字段的灵活性，又在"从工单发起领料"这条主链路上做了校验。

还可以更进一步：维修工单完工时，检查"这张单有没有领料记录"。如果没有，提示"本单未领料，确认无需备件？"。这是"流程闭环"层面的校验，比数据库外键更贴合业务。

## 八、真实数据：2 个备件、1 条出库流水

`eam-init.sql` 里的备件种子数据：

| id | part_no | 名称 | 规格 | unit | stock | safety_stock | asset_ids | location |
|----|---------|------|------|------|-------|--------------|-----------|----------|
| 1 | SP-BEAR-001 | 主轴轴承 | SKF 7010C | 套 | 8 | 3 | [1,2] | A库-01-03 |
| 2 | SP-SEAL-002 | 液压密封件包 | HTF160 通用 | 包 | 2 | 5 | [3] | A库-02-01 |

一条出库流水：

| 字段 | 值 | 说明 |
|------|----|------|
| part_id | 2 | 液压密封件包 |
| type | 2 | 出库 |
| quantity | 1 | 领 1 包 |
| biz_order_no | RO-20261108-001 | 挂在注塑机维修工单上 |
| operator | 李四 | 维修领料人 |

这条流水和工单、设备是咬合的：工单 `RO-20261108-001` 修的是设备 3（EQ-INJ-001 注塑机），备件 2 的 `asset_ids = [3]` 也指向设备 3，流水 `part_id = 2`、`biz_order_no = RO-20261108-001`。三条记录串起来，就是"注塑机坏了 → 开了维修工单 → 领了 1 包密封件"的完整链路。

### 8.1 走一遍 API

**场景一：再出库 1 包密封件。**

```text
POST /api/admin/eam/spare-part/outbound?partId=2&quantity=1&bizOrderNo=RO-20261110-001&operator=李四
```

当前 `stock = 2`，`2 >= 1`，校验通过，`stock` 变成 1，写一条 `type=2`、`quantity=1` 的流水。返回的 `EamSparePartRespVO` 里 `stock=1`、`safetyStock=5`，前端比对 `1 < 5`，标红预警。

**场景二：再出库 2 包。**

```text
POST /api/admin/eam/spare-part/outbound?partId=2&quantity=2&bizOrderNo=RO-20261111-001&operator=李四
```

当前 `stock = 1`，`1 < 2`，抛 `1_003_301`，返回"备件库存不足: 当前库存=1, 需出库=2"。库存不变，流水不写。

**场景三：入库 5 包补货。**

```text
POST /api/admin/eam/spare-part/inbound?partId=2&quantity=5&bizOrderNo=PO-20261112-001&operator=老周
```

`stock = 1 + 5 = 6`，写一条 `type=1`、`quantity=5` 的流水。返回 `stock=6`，`6 >= 5`，预警解除。

**场景四：对账。**

```text
GET /api/admin/eam/spare-part/get?id=2
```

`stock = 6`。流水表里这个备件现在有三条：种子那条出库 1、场景一出库 1、场景三入库 5。用公式核对：

```text
期初 3（种子数据补了 1 条出库，所以出库前是 3）
- 出库 1（种子）
- 出库 1（场景一）
+ 入库 5（场景三）
= 6
```

和 `stock = 6` 对上了。这就是流水的价值：**任何一个数字，都能用流水倒推出来；任何一笔差异，都能定位到具体的时间、人、单。**

### 8.2 一个必须指出的负数漏洞

当前 `inbound` 和 `outbound` **都没有校验 `quantity > 0`**。这意味着：

- `inbound(partId, -5, ...)`：`stock + (-5)`，库存减少 5，流水记一条 `type=1`、`quantity=-5` 的入库。账面看起来"入库了 -5"，实际是出库。
- `outbound(partId, -5, ...)`：`stock < -5` 为 false，校验通过，`stock - (-5)`，库存**增加** 5，流水记一条 `type=2`、`quantity=-5` 的出库。

一个负数参数就能绕过所有校验，把库存改反。这是演示仓库的真实缺陷，必须在商用前补上：

```java
// 商用改造：数量必须为正
if (quantity == null || quantity <= 0) {
    throw ServiceExceptionUtil.exception(ERROR_CODE_QUANTITY_INVALID, quantity);
}
```

这类问题在"参数校验"里很常见：大家记得校验"库存够不够"，忘了校验"数量是不是正数"。而后者更危险，因为它能绕过前者。**所有参与运算的外部参数，都要先做符号和范围校验。**

## 九、商用化检查清单（备件版）

- `quantity` 是否校验为正整数？当前没有，负数能反转库存方向。
- 出库是否改成原子 SQL？当前先读后写，并发会超卖。
- 入库/出库是否在事务内？当前有 `@Transactional(rollbackFor = Exception.class)`，保持。
- 期初库存是否也写入库流水？当前 `createSparePart` 直接设 `stock`，流水的期初对不上。
- `assetIds` 是否加了 GIN 索引？没加的话反向查询全表扫。
- 设备报废后，`assetIds` 里的残留 ID 谁清理？
- 安全库存预警是否只在出库时比对？调高安全库存导致的低库存会漏报。
- `biz_order_no` 是否建了索引？按工单查领料记录会用到。
- 流水是否真的"只增不改"？Controller 层不要暴露 update/delete。
- 退库是否复用 `inbound`？当前设计是复用，`bizOrderNo` 填原出库单号对冲。
- 备件删除时，有流水的备件是否允许删？外键会拦住物理删除，逻辑删除要额外判断。
- 低库存清单要不要定时扫描？前端比对覆盖不到"没出库但低于安全线"的情况。
- 维修工单完工时，是否校验"有没有领料"？当前没有，工单和备件是松耦合。
- 备件成本是否归集到设备/工单？当前流水有 `biz_order_no`，但没有金额字段，算不了钱。

- 0 次故障时，MTBF 返回什么？返回 0 会让看板显示"这台设备最差"，返回 null 才是诚实。
